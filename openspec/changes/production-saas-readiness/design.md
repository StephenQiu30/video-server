## Context

当前系统已经具备本地 MVP 能力，但公网内测会引入新的风险：开放注册可能被滥用，下载任务会消耗带宽和存储，预签名链接存在泄露窗口，生产部署需要密钥、备份、日志、HTTPS 和健康检查兜底。上线级 SaaS 的核心不是增加复杂功能，而是把“可控、可验收、可回滚、可解释”补齐。

第一版上线基线已经确认：

- 小范围内测 SaaS。
- 免费配额，不接入支付。
- 单机 Docker Compose + Nginx/TLS。
- 不做 AI 摘要、平台专用解析、Cookie 托管、支付会员和 K8s。

## Goals / Non-Goals

**Goals:**

- 保留现有 React + Umi + Ant Design Pro、FastAPI、RQ、PostgreSQL、Redis、MinIO / S3、yt-dlp、FFmpeg / ffprobe 技术栈。
- 增加注册控制，避免公网环境完全开放注册。
- 增加用户免费配额、任务并发、文件大小、保留时间和总存储限制。
- 增加最小管理员能力，用于查看用户、查看任务、调整配额、禁用用户和处理滥用。
- 建立单机 Compose + Nginx/TLS 部署基线，并补齐生产环境变量、备份恢复和健康检查。
- 建立上线验收门禁，确保 API、前端、下载、合规、安全和运维均可验证。

**Non-Goals:**

- 不接入支付、会员、订阅、发票或账单。
- 不做团队/组织权限。
- 不做 K8s、服务网格或复杂多地域高可用。
- 不托管用户平台 Cookie。
- 不做平台专用解析或 DRM、付费墙、会员内容绕过。
- 不在本变更中实现 AI 摘要、问答、字幕总结等二期能力。

## Decisions

1. **上线形态采用小范围内测 SaaS**

   第一版公网部署不开放大规模注册。注册入口必须支持关闭或邀请码控制，并允许管理员禁用异常用户。

2. **配额采用免费内测配额**

   不接入支付。每个用户拥有可配置的每日任务数、并发数、最大文件大小、文件保留时间和总存储占用限制。默认值保持保守，避免资源被单个用户耗尽。

3. **部署采用单机 Compose + Nginx/TLS**

   第一版优先让系统可在一台云服务器稳定运行。Nginx 负责 HTTPS、反向代理和基础安全头；Compose 负责 Web、API、Worker、PostgreSQL、Redis、MinIO 的编排。

4. **生产化必须有可验证门禁**

   每一项上线能力都必须能通过脚本、接口响应、日志或文档证据验收。不能只写“已支持”，必须说明如何验证。

## Risks / Trade-offs

- [Risk] 小范围内测仍可能被滥用 -> Mitigation：注册控制、接口限流、用户配额、禁用用户和高风险内容拒绝。
- [Risk] 单机部署存在单点风险 -> Mitigation：第一版接受单机约束，但必须补齐备份恢复、健康检查和可回滚部署文档。
- [Risk] 免费配额缺少商业闭环 -> Mitigation：先验证产品主链路和合规边界，支付订阅后续单独立项。
- [Risk] 管理端能力膨胀 -> Mitigation：只做用户、任务、配额、禁用和滥用处理，不做复杂运营后台。

## Migration Plan

1. 收尾 M1 未完成项，保证本地 MVP 验收闭环不被生产化任务打断。
2. 补齐注册控制、用户配额和管理员兜底能力。
3. 补齐限流、审计、日志脱敏、过期清理和失败治理。
4. 补齐单机 Compose + Nginx/TLS 部署基线。
5. 补齐 CI/CD、备份恢复、监控和上线验收文档。
6. 通过公网内测验收门禁后，再评估支付、团队权限或扩展部署方式。

## Open Questions

- 第一批内测用户规模和默认邀请码发放方式尚未确定；实现时默认使用可关闭注册和可选邀请码，避免锁死单一路径。
- 域名、证书来源和云服务器规格尚未确定；部署文档以通用单机 Compose + Nginx/TLS 为基线。
