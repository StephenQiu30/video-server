# 审稿方法与优先级

## 先核事实，再做创作判断

服务端负责场景覆盖、顺序与 JSON 结构等可机械校验的条件。AI 对因果、角色选择、节奏与表达的判断属于可讨论的审稿意见；不能把它写成已经由程序证明的事实。对未知、明显省略、角色误信和可能有意的留白，准确说明范围。

每项有效的修改建议都要让作者知道：

1. 当前文本里哪一种行动、信息或状态导致了问题；需要指出可辨认的场景区段或人物关系，不贴内部 ID 列表。
2. 这一问题怎样损害理解、悬念、人物能动性、情绪回报或连续性；不使用“AI 味”“不够电影感”等不可核对的标签。
3. 修改后应恢复什么结果，以及哪些已成立的事实或选择需要保留；不强制指定唯一改法。

只有文本明确矛盾、会使故事因果断裂或关键人物选择失效的问题才排在前面。普通润色和类型口味放在后面；如果只是创作偏好，不把它说成缺陷。多个场景呈现同一机制时合并为一项全局建议，逐场结果保留局部表现，不复制同一句批评 129 次。

## 输出取舍

- `priority_revisions` 是创作者打开报告最先需要的决策清单，控制在少量高影响、相互独立的条目；没有充分依据时为空。
- `strengths` 记录值得保留的具体结构、角色行动或表达机制，解释效果；不是为平衡批评而凑数。
- `dialogue_findings` 只放对白特有的问题或有效做法；如果根因是人物目标或事件设计，应在修改建议中指向根因。
- `scenes[].findings` 只放该场独有且可执行的观察；`purpose`、`conflict`、`turn` 和 `pacing` 已说明的事实不再重复写入发现。
- `synopsis` 是剧情事实的压缩，不掺入评价；诊断放在结构、人物、对白和建议中。

审稿结论不能冒充作者接受、法务判断或制作验收。用户上传的原文仍是唯一可核对的故事来源。
