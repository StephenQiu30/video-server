## 1. 评审发现与修复状态

以下缺陷描述及固定 SHA 链接记录评审基线；三个问题均已完成代码修复。修复后的验证见第 6 节，提交状态以 Git 为准，本报告不代表已部署。

### [P1] 退出时使正在执行的会话刷新失效 — video-app/lib/features/auth/application/auth_session_controller.dart:132

后台请求触发刷新后，用户仍可执行退出；`logout()` 清空本地凭据，但刷新返回后直接调用 `_accept()`，重新写入 Refresh Credential 并进入 `signedIn`。如果服务端已完成轮换、只是响应延迟，退出提交的是旧 Refresh Credential，服务端删除旧会话也不能撤销新凭据。这使已经完成的退出被迟到响应撤销，切换账号时也可能覆盖新账号。应为会话操作增加代次校验，退出/清空时立即使旧操作失效，并处理旧刷新结果的撤销；不能只取消 UI 的等待。

证据：[刷新和接纳结果](https://github.com/StephenQiu30/video-app/blob/a3d2f48bf4e835af3bf90ef765c8239d0051b1ee/lib/features/auth/application/auth_session_controller.dart#L125)，[服务端轮换与按 token 删除](../../backend/app/crud/auth_repository.py)。本次用真实 Controller、内存凭据仓库和可控刷新响应复现：`signedOut → 迟到刷新 → signedIn`，凭据重新出现。现有认证测试覆盖正常退出与刷新失败，未覆盖该交错顺序；实现中的刷新单飞也不能阻止退出后的旧结果写回。

最小验收：刷新已发出时退出，再返回旧刷新结果，仍保持未登录且安全存储为空；若随后登录另一个账号，旧成功/失败响应都不能影响新会话。

修复：退出时立即使旧会话操作失效；串行处理安全存储的写入和清空，丢弃并尽力撤销迟到凭据。认证请求在返回、刷新和重放前检查发起时的会话代次，旧请求不能清除新账号。见 [App 006 验收](../../../video-app/docs/acceptance/006-原生认证与应用导航验收.md)。

### [P2] 丢弃分析操作之前发出的迟到轮询结果 — video-app/lib/features/analysis/application/analysis_controller.dart:171

`_poll()` 保存旧状态后等待网络，取消/删除/重试只取消下一次 Timer，不能撤销已发出的查询。操作完成后，旧查询仍通过 `current.copyWith(job: next)` 覆盖当前状态并重新安排轮询。本次复现了“取消成功后重新显示 running”；同一写回路径也没有操作代次保护。服务端取消并未被撤销，但用户会看到过时进度与错误操作入口。应在操作开始时递增代次，写回前同时检查目标、代次及服务端版本，保护成功和失败两条回调。

证据：[轮询写回与 Timer 取消](https://github.com/StephenQiu30/video-app/blob/a3d2f48bf4e835af3bf90ef765c8239d0051b1ee/lib/features/analysis/application/analysis_controller.dart#L164)。本次直接调用真实 Controller，挂起一次 running 查询，完成取消，再放回旧查询，观察到 `cancelled → running`。现有分析测试覆盖顺序轮询及取消，未覆盖响应乱序。

最小验收：取消、删除、人工重试期间返回旧查询的成功或失败结果，均不得覆盖操作后的状态；终态不因旧响应恢复轮询。

修复：操作、重建和销毁统一使旧请求失效；轮询成功/失败均检查代次，同一任务拒绝 runNo 或 version 倒退。见 [App 014 验收](../../../video-app/docs/acceptance/014-视频AI智能分析入口验收.md)。

### [P2] 为分片上传增加接收超时和用户取消入口 — video-app/lib/features/upload/data/multipart_uploader.dart:93

上传使用独立的 `Dio(BaseOptions(followRedirects: false))`，未继承 API 客户端的连接/接收超时；单片只设置 `sendTimeout`。对象存储或代理收到请求体后一直不返回响应头时，发送超时不能结束接收等待，控制器持续 busy，上传按钮一直禁用，页面也没有取消入口。应设置连接、发送、接收及整个上传的有限预算，并让用户能取消；任何分片失败时也应及时取消其余分片，避免 `Future.wait` 等待尚未结束的请求后才进入清理。

证据：[独立上传客户端与请求配置](https://github.com/StephenQiu30/video-app/blob/a3d2f48bf4e835af3bf90ef765c8239d0051b1ee/lib/features/upload/data/multipart_uploader.dart#L40)，[上传界面](https://github.com/StephenQiu30/video-app/blob/a3d2f48bf4e835af3bf90ef765c8239d0051b1ee/lib/features/upload/presentation/upload_intake_panel.dart)。本次以本机 HTTP 夹具接收 4 字节请求体后保持连接，设置 500ms 发送/会话预算，1 秒后 Future 仍未结束，显式取消才退出。该实测证明缺少应用接收期限，不把 1 秒观测夸大成无限时长实测。

最小验收：连接失败、发送停滞、响应头停滞、单片失败和手动取消都能在规定预算内结束，进入可重试状态，并尽力清理服务端上传会话。

修复：连接/发送/接收分别最多 15 秒/2 分钟/30 秒；分片阶段最多 15 分钟且受会话到期时间约束，哈希至完成的总预算为 30 分钟。分片失败立即取消其余请求，已知资源的服务端清理最多等待 5 秒；界面提供中英文取消入口。各上传阶段绑定原会话，创建请求在认证重放时复用同一个幂等键。见 [App 016 验收](../../../video-app/docs/acceptance/016-原生文件上传与媒体组件体验验收.md)。

## 3. 可用性评估

### 初次评审实际检查

- 现有 Web `http://127.0.0.1:8101/` 返回 200；API `/health/ready` 返回 `ok`。只证明本机访问和健康检查成功。
- 浏览器实际走过首页 → 登录 → 注册 → 返回登录；空登录提交出现邮箱/密码字段错误，Tab 能进入邮箱输入框。

- 首页主要讲开源、自托管、Worker 和部署；对当前开源定位是合理的。若推出托管 ToC，普通用户需要先看到“能处理什么、拿到什么、要等多久、额度多少”，目前仍会被引向部署文档和 GitHub。
- 登录界面没有找回密码，注册和页脚没有面向托管服务的隐私/服务条款入口；与当前 API 只提供注册、登录、刷新、退出、资料修改的范围一致。

初次评审未创建真实账号、上传用户文件、执行平台下载或消耗 AI 额度；后续修复验证单独记录于第 6 节。未进行登录后页面的完整浏览器回归、暗色主题完整检查、读屏审计或 iOS/Android 真机测试。已有历史 E2E 和签名构建记录值得保留，但不能视为本次重跑结果。尤其 App 019 仍记录最新 Release 的真机安装受设备/Xcode 支持限制。

| 收费前，免费试用可延后 | 没有订单、支付回调、权益发放、退款与对账闭环；现有 quota 是准入记录 | 产品确认收费后再实现一种套餐、一种支付渠道和一套服务端权益；重复回调幂等，退款/取消规则明确 | 一笔真实测试订单经过支付、到账、消费、退款/撤销；客户端不能自行授予权益；渠道规则另行按首发市场核验 |

### 两处需要特别讲清的现有行为

**日处理量按上界预留，不是实际下载字节。** 默认单次下载上界为 20 GiB，再加 2,000,000 字节封面预算，日处理预算为 100 GiB。因此没有其他任务时，第五次远程下载申请就会触及日字节预算；取消、失败或删除也不退还已准入的日处理量。按“每天 50 个任务”理解会误导用户。这是 [当前配额设计](../design/006-上线产品能力补全设计.md) 的有意策略，不作为错误扣费缺陷；应调整试用参数并解释“实际存储”和“处理预算”的不同，暂不建设精细计费系统。

**个人部署 Provider 不等于消费者身份绑定。** [权益判断](../../backend/app/workers/runner/entitlements.py) 的腾讯/优酷个人分支由 Provider 和 `OPERATOR_MANAGED` 模式决定，[媒体解析](../../backend/app/services/downloads/inspect_media.py) 调用 Runner 时只传 URL，没有把产品用户的身份绑定为平台账户。032 的个人用途是已确认范围，本次不把该设计报成回归；但将同一配置搬到多用户托管环境前必须关闭该线路或另行建立明确授权方案。首版关闭即可，不必设计每用户 Cookie 托管或通用授权平台。

### 商店账户删除依据

2026-09-08 核验的官方要求：支持创建账户的 App，Apple 要求能在 App 内发起整账户删除；Google Play 要求 App 内删除路径及外部可用的删除请求网页。仅停用账户或退出登录不满足这项要求。见 [Apple 账户删除说明](https://developer.apple.com/support/offering-account-deletion-in-your-app/) 和 [Google Play 账户删除说明](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en)。具体服务地区尚未确定，本报告不作某个国家/地区的完整合规验收结论。

## 5. 建议的交付顺序与范围控制

1. **先收紧试用范围。** 三个 App 缺陷已完成代码修复；继续选择本地上传和少量已验证公开来源，配置统一试用限额和注册准入。
2. **再完成一次真实上线演练。** 沿用 006/030 验收，记录 HTTPS/代理、出口隔离、对象获取、重启恢复、备份恢复、并发限额和告警送达；补最小支持入口与用户告知。
3. **开放注册前补账户闭环与首次成功体验。** 邮箱验证、密码恢复/修改、注销、额度展示和示例流程一起验收。先做 Web 公测可减少首发设备面；App 仍须完成自身门槛。
4. **有付费需求后再做收费。** 不把复杂订阅、积分、优惠券、分销或多支付渠道作为免费试用的前置条件。

当前无需增加 Kubernetes、拆更多微服务、引入第二套任务状态/消息系统、做通用工作流编辑器、团队协作权限、社交社区、离线媒体库、常驻后台下载、推送体系或追求全平台媒体覆盖。现有 FastAPI、PostgreSQL、Outbox、Worker 与 Web/Flutter 边界足以支撑第一阶段；新增抽象应由真实瓶颈触发。
