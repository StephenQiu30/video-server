# 剧本解析格式与报告结构调研

> 调研日期：2026-08-17

## 1. 结论

当前项目的剧本分析结果已经具备“全局结论 + 逐场景证据”的基础，但报告仍然把编辑审阅结果、生产拆解结果和原文结构混在一个较薄的 Markdown 页面里。首期应采用下面的边界：

1. **输入格式**：先把 DOCX、PDF、TXT、Markdown 和 Fountain 规范化为 UTF-8、LF 换行的 canonical screenplay，再按可识别的剧本元素保存有序字符区间。
2. **分析格式**：使用稳定的 `source_scene_id` 作为唯一证据坐标；全局字段不能脱离逐场景证据；逐场景结果必须按源场景原顺序完整覆盖。
3. **报告格式**：报告是 editorial coverage（故事审阅报告），不伪装成 production breakdown（制片拆解）。第一版报告固定为“阅读摘要 → 故事概览 → 结构与节奏 → 人物 → 逐场景 → 对白 → 优势 → 优先修改 → 证据说明”。
4. **生产拆解**：场景标题、角色表、地点、道具、服化道、音效和视效属于下一层 production breakdown 数据，不能在当前没有证据时由模型臆造。
5. **质量原则**：不显示未经计算的评分，不把模型的泛泛判断伪装成事实；每项结论都显示证据场景 ID，空结果明确显示“没有独立发现”。

## 2. GitHub 与公开规范调研

### 2.1 Fountain：输入层应保留类型化元素

[Fountain 官方语法](https://fountain.io/syntax/)把 Character、Dialogue、Parenthetical、Section、Synopsis 等作为可识别的剧本标记，并强调在无法确定时保留原文，而不是静默丢弃文本。这个原则适合我们的导入 Worker：规范化可以增加结构信息，但不能改变 canonical 原文。

[Fountain.js](https://github.com/mattdaly/Fountain.js/)的解析输出采用 `scene_heading`、`action`、`character`、`parenthetical`、`dialogue`、`transition` 等 typed token，而不是把所有行都输出为一类文本。

[screenplay-tools](https://github.com/wildwinter/screenplay-tools)同样将 Fountain/FDX 转成 Heading、Action、Character、Parenthetical、Dialogue、Transition 等事件，并在回调层将角色、括注和对白聚合。这验证了“类型化元素 + 场景级聚合”比全文字符串切片更适合作为后续分析输入。

### 2.2 ScreenJSON：结果层需要稳定身份和结构优先

[ScreenJSON specification](https://screenjson.com/specification/)采用结构优先的 JSON：根对象有稳定的 `id`、版本、标题和语言；角色集中声明并通过稳定身份在场景中复用；场景包含 heading、body、cast 和生产相关分类；slugline 还可以拆成 context、setting、time 和 modifiers。

当前项目已经有稳定的规范化 `scene-{序号}-{摘要}` ID、场景字符范围和严格的结果校验，因此不需要复制 ScreenJSON 的全部字段；应继续沿用稳定 ID，并逐步补充可由原文确定的 heading/元素类型，而不是让模型重新发明场景身份。

### 2.3 行业 coverage 与 production breakdown 应分开

[Script coverage](https://en.wikipedia.org/wiki/Script_coverage)通常覆盖 concept、structure、story development、characters、dialogue 和 writing style，目标是给创作者可执行的审阅意见。

[Script breakdown](https://en.wikipedia.org/wiki/Script_breakdown)则是把剧本拆成道具、地点、服化道、特效等生产元素，服务于预算、排期和拍摄准备。[Screenplayer](https://www.screenplayer.co.uk/)公开介绍的能力也把 scene-by-scene breakdown、character/location/production elements 与 logline、summary、coverage 分成不同能力。

因此，当前 `screenplay-analysis` 结果应继续作为 coverage；如果以后增加 production breakdown，应新建独立的结果契约或明确的报告章节，不能把缺乏原文证据的生产字段混进故事分析。

## 3. 当前项目与目标格式的差距

| 方面 | 当前状态 | 优化方向 |
| --- | --- | --- |
| 原文结构 | 已保存 heading/action/character/parenthetical/dialogue 区间 | 增加 transition、section、synopsis、shot 等可识别类型；未知内容仍保留为 action |
| 场景身份 | `source_scene_id` 稳定且按顺序校验 | 保持为唯一证据坐标，不允许模型生成新场景 ID |
| 全局分析 | logline、synopsis、structure、characters、dialogue、strengths、revisions | 报告中显式分层，并注明证据覆盖范围 |
| 逐场景分析 | purpose、conflict、turn、pacing、findings | 报告中按“场景序号 + source ID”展示，避免只显示无语义的场景标题 |
| 报告语言 | Markdown 标签仍以英文为主，结构偏薄 | 使用稳定中文章节名，补充摘要指标、阅读边界和证据说明 |
| 事实边界 | 服务端已校验引用，但报告未解释引用含义 | 统一显示证据说明；不增加模型没有提供的评分或制作事实 |
| 长剧本 | 已有确定性分块和汇总流程 | 保持分块结果只负责局部场景，汇总结果只负责全局结论，最终服务端按原顺序合并 |

## 4. `screenplay-analysis` 稳定报告契约

```text
# 标题
报告类型 / 输出语言 / 逐场景覆盖数 / 主要人物数

## 一、阅读摘要
## 二、故事概览
### Logline
### Synopsis
## 三、结构与节奏
### 幕结构
### 关键转折
### 节奏判断
## 四、人物分析
## 五、逐场景分析
## 六、对白与写作
## 七、文本优势
## 八、优先修改建议
## 九、证据说明
```

约束：

- `scenes` 必须覆盖全部源场景且保持原顺序；这项由服务端验证，不由报告渲染器猜测。
- 所有结构、人物、对白、优势和修改项都必须引用至少一个已存在的源场景 ID。
- `priority_revisions` 的数组顺序就是修改优先级；当前不额外生成 P0/P1 等模型未提供的等级。
- 统计数字只使用服务端可确定的数量；不生成“可信度”“质量分数”或市场结论。
- Markdown 只承载已校验结果，不执行模型返回的链接、HTML、代码或指令。
