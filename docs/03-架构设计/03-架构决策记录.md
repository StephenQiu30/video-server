## ADR-001：前端技术栈

## 状态

已接受。

## 决策

前端采用 React + Umi + TypeScript，并使用 Ant Design Pro。实现时优先复用 ProLayout、ProTable、ProForm 和任务工作台模式。

## 影响

前端更适合构建任务台、表格、表单和管理型工作流。Umi 与 Ant Design Pro 的常见组合降低了工作台搭建成本。

## ADR-002：后端技术栈

## 状态

已接受。

## 决策

后端采用 FastAPI + Python 3.12。

## 影响

后端可以直接集成 yt-dlp、RQ、PostgreSQL 客户端和对象存储 SDK，并通过 OpenAPI 文档支撑前后端并行。

## ADR-003：下载与音视频处理

## 状态

已接受。

## 决策

下载内核采用 yt-dlp，音视频处理采用 FFmpeg / ffprobe。所有调用必须通过下载内核适配层进入，不允许散落在业务控制器中。

## 影响

首版依赖成熟下载生态，但必须接受平台规则变化造成的解析失败。系统需要保留清晰的失败原因和升级路径。

## ADR-004：任务队列

## 状态

已接受。

## 决策

后台任务采用 RQ + Redis。

## 影响

下载任务由 Worker 执行，API 只负责创建任务和查询状态。后续可以扩展多队列、优先级和多 Worker。

## ADR-005：数据库

## 状态

已接受。

## 决策

数据库采用 PostgreSQL。

## 影响

任务、用户、历史、元数据和后续审计可以使用统一关系数据库管理。部署需要在 Docker Compose 中提供 PostgreSQL 服务。

## ADR-006：文件存储

## 状态

已接受。

## 决策

文件存储采用 MinIO / S3 兼容对象存储。

## 影响

MVP 即按对象存储接口设计，适合私有部署和后续迁移到云对象存储。需要在任务完成、过期清理和下载授权中处理对象 key。

## ADR-007：M1 访问模式

## 状态

已调整。

## 决策

M1 阶段采用本地单用户模式：解析、任务和下载链接接口自动归属到默认本地用户，用于优先跑通核心下载闭环。JWT 注册登录、用户隔离、管理员和配额能力归入生产化计划，不作为当前本地 MVP 的默认 API 或前端入口。

## 影响

本地 MVP 不再被登录注册阻塞，前端默认展示首页、工作台和任务历史；合规边界保留在文档、错误提示和 smoke 检查中，不再作为主导航页面。公网或小范围内测 SaaS 前仍必须重新设计并启用鉴权、限流、配额和管理员兜底，并通过 `production-saas-readiness` 单独验收。

## ADR-009：项目目录结构

## 状态

已接受。

## 决策

项目结构已调整为双仓库：`video-server` 保留 `apps/api`、`apps/worker`、`packages/shared` 和根目录 Docker 部署文件；`video-web` 独立承载 React 前端。

## 影响

前端、后端、Worker、共享契约和部署边界清晰，适合按仓库独立开发、测试和发布。

## ADR-010：下载限制

## 状态

已接受。

## 决策

MVP 默认限制为：单任务最大 2GB、最长 2 小时、全局并发 2、单用户并发 1、文件保留 24 小时、预签名 URL TTL 15 分钟。

## 影响

默认值偏保守，优先保护本地和私有部署资源。后续可通过环境变量调整，并在生产化阶段引入用户配额。

## ADR-011：OpenSpec 变更管理

## 状态

已接受。

## 决策

M1 MVP 骨架实现使用 OpenSpec 变更 `bootstrap-mvp-foundation` 管理。

## 影响

后续实现必须围绕 proposal、design、specs、tasks 推进，完成后运行 `openspec validate --all`，并在交付前更新任务状态。

## ADR-012：M1 下载交付方式

## 状态

已接受。

## 决策

M1 下载链接由后端生成短期签名 API URL，前端不再直接打开 MinIO / S3 预签名 URL。API 校验签名、任务状态和文件保留期后，从私有对象存储流式返回文件，并使用附件下载响应。

## 影响

该方式避免浏览器访问 `host.docker.internal` 或对象存储内部地址，保留短期链接语义，同时继续保证前端不持有 MinIO 管理密钥。生产 SaaS 阶段仍需叠加用户鉴权、限流和审计。

## ADR-013：本机单用户 B 站下载登录态

## 状态

已接受。

## 背景

M1 当前目标从“只守最小通用边界”调整为“本机单用户真实下载可访问的 B 站内容”。B 站公开页面在未登录或风控场景下可能需要浏览器登录态，单纯调用 yt-dlp 公开视频解析不能稳定满足本机使用需求。

## 决策

M1 允许本机 Worker 在显式配置 `YTDLP_COOKIES_FROM_BROWSER=chrome` 时，通过 yt-dlp 的浏览器登录态读取能力使用本机 Chrome 登录态完成下载。该能力只在 Worker 下载进程中使用，不通过 API 接收 Cookie，不由前端上传 Cookie，不写入数据库，不输出 Cookie 路径或 Cookie 内容到日志。

## 影响

`npm start` 默认启动本机 API；需要读取本机浏览器登录态时，使用 `npm run dev:worker` 或 `npm run dev:all` 启动本机 Worker。Docker 仅作为部署方式，不再混合启动本机 Worker。若 Chrome 登录态不可读，任务应失败为可诊断的中文原因。该例外不等同于公网 SaaS Cookie 托管；上线级 SaaS 仍禁止 Cookie 托管、付费墙绕过、DRM 规避和会员内容绕过，除非另起 OpenSpec 与合规审查。

## ADR-014：前端脚手架与页面容器

## 状态

已接受。

## 背景

当前 M1 前端应优先服务下载核心流程，不需要营销型 SaaS 页面或自定义视觉包装。项目已确认使用 React、Umi、TypeScript 和 Ant Design Pro，因此页面结构应回到官方脚手架和 ProComponents 的默认能力。

## 决策

前端 UI 以 Ant Design Pro / Umi Max 脚手架为实现基线。页面布局统一使用 ProLayout、PageContainer、ProCard、ProForm、ProList、ProTable 等组件；主内容宽度、页面间距和容器外壳不得由自定义 CSS 随意控制。

## 影响

前端重构时必须先保留当前稳定提交，再迁移页面。重生成后必须证明链接解析、清晰度选择、SSE 进度、下载文件、重试和任务历史能力不退化。自定义 CSS 只用于少量兼容状态，不作为主布局系统。

## ADR-010：多视频源与清晰度下载策略

## 状态

已接受。

## 背景

用户需要支持 B 站之外的公开视频源，并通过选择较低清晰度减少文件体积和下载等待时间。yt-dlp 已提供多平台 extractor 和 format selector，继续复用通用适配层可以满足本地 MVP，同时避免引入高维护、高合规风险的平台专用解析。

## 决策

M1 多视频源支持限定为 yt-dlp best-effort 公公开视频解析和下载。解析响应展示来源识别，并生成推荐、最高 1080p、最高 720p、最高 480p、最高 360p 等清晰度预设。清晰度预设只选择平台已有视频流，不做后端转码压缩。抖音、小红书、TikTok 等平台不读取 Cookie，不做专用绕过解析。

## 影响

前端需要说明多视频源不是永久可用承诺；平台未提供对应清晰度时必须提示不可用或自动降级。合规检查允许出现明确视频源名称，但继续禁止 Cookie 托管、DRM 规避、付费墙绕过、会员内容绕过和敏感日志泄露。

## ADR-008：首版延后能力

## 状态

已接受。

## 决策

AI 摘要二期再做；平台专用解析首版不做，只预留插件口。

## 影响

MVP 聚焦视频解析、格式选择、任务下载、状态反馈、历史和合规提示，避免过早扩大范围。
