# 后端上线级工程化升级设计

更新时间：2026-05-23

## 1. 设计目标

本设计用于把当前 `video-server` 从“可本机运行、可内测验证”的后端，升级为“小范围公网部署可控”的上线级服务。升级重点不是继续堆平台数量，而是补齐生产启动门禁、安全基线、可观测性、任务可靠性和运维验收闭环。

## 2. 当前能力审计

| 能力域 | 当前状态 | 主要风险 | 优先级 |
| --- | --- | --- | --- |
| 账号与任务归属 | 已有 JWT、GitHub OAuth、用户状态、任务归属校验 | FastAPI 默认 401/403 错误结构与业务 `AppError` 不完全统一 | P1 |
| 配额与并发 | 已有日配额、用户并发、全局并发、存储配额 | 缺少解析接口级别限流；恶意用户可高频调用 `/api/parse` 消耗平台请求 | P0 |
| 解析平台 | 已有平台画像、B 站与国内短视频适配、错误分类 | 真实平台 smoke 依赖人工 token 和样例维护 | P1 |
| 下载任务 | 已有 Worker、进度、取消、重试、过期清理、对象存储 | Worker 缺少任务级 request/correlation id；失败原因与解析错误分类尚未完全统一 | P1 |
| 健康检查 | 已有 `/health` 和 `/ready` | `/ready` 会检查队列 worker，在扩缩容/滚动发布时可能导致短暂 degraded，需要明确部署策略 | P1 |
| 日志 | 生产环境已有 JSON 日志与粗粒度敏感词脱敏 | 缺少请求 ID、安全响应头、访问日志结构化字段 | P0 |
| 生产配置 | 有 `.env.production.example` 与 `scripts/validate_prod_env.py` | 应用启动本身没有拦截默认密钥；CI 没有强制跑 Docker config 和生产 env 模板校验 | P0 |
| Docker 部署 | API、Worker、Postgres、Redis、MinIO compose 已具备 | API healthcheck 只打 `/health`，不能覆盖依赖就绪；生产 env 文件缺失时体验依赖脚本说明 | P1 |
| CI 门禁 | 已有测试 CI | 没有执行 `npm run docker:config`、生产 env 模板校验、脚本语法检查 | P0 |
| 文档 | 产品、架构、验收、合规文档较完整 | 缺少工程化升级路线和每个上线门禁的 owner/验收命令 | P0 |

## 3. 方案比较

### 方案 A：P0 工程化最小闭环

内容：补齐生产配置启动拦截、请求 ID 与安全响应头、CI 生产门禁、解析接口轻量限流设计。

优点：风险低，能快速提升上线可信度；适合当前已有 MVP 架构。  
缺点：不立即解决全部 Worker 可靠性和监控指标深度。

### 方案 B：可观测平台化

内容：引入 Prometheus 指标、OpenTelemetry trace、结构化访问日志、任务全链路 correlation id。

优点：排障体验更接近正式 SaaS。  
缺点：改动面更大，需要部署监控组件，容易超过当前阶段必要复杂度。

### 方案 C：任务系统重构

内容：重新设计任务状态机、下载执行器、重试策略、死信队列、平台适配器隔离。

优点：长期可靠性最好。  
缺点：会触碰 Worker、DB、API 契约，适合在 P0 门禁稳定后单独做。

## 4. 推荐设计

推荐采用“方案 A 先落地，方案 B/C 分阶段推进”。

第一阶段只处理上线前最容易出事故的系统边界：

- 生产启动门禁：生产环境禁止默认 JWT、默认 MinIO、默认数据库/Redis 密码、开放注册无邀请码。
- 请求安全基线：每个响应都有 `X-Request-ID`，生产响应追加 `X-Content-Type-Options`、`Referrer-Policy`、`X-Frame-Options` 等安全头。
- CI 门禁：默认 CI 必须覆盖单元测试、仓库结构校验、Docker Compose config、生产 env 模板负向校验、脚本语法。
- 解析限流：在不引入复杂网关前，先落地进程内 per-user `/api/parse` 限流；多实例部署时再升级 Redis-backed 限流。

第二阶段补可观测性：

- 请求日志包含 request id、method、path、status、duration_ms。
- Worker 任务事件带 correlation id。
- `/api/admin/metrics` 增加失败分类、队列年龄、成功率、存储用量。

第三阶段补任务可靠性：

- 下载 Job 幂等化。
- 死信/长期失败任务清理。
- 平台错误分类与 Worker 下载错误分类统一。

## 5. 架构边界

- `app/core/config.py` 继续负责配置读取，不直接承载复杂校验。
- 新增 `app/core/production.py` 负责生产配置门禁，可被应用启动和测试直接调用。
- 新增 `app/middleware/request_context.py` 负责 request id、安全响应头和基础访问日志。
- 后续如实现限流，新增 `app/services/rate_limit.py` 和 `app/deps_rate_limit.py`，避免把限流逻辑塞入路由。
- CI 工程化只修改 `.github/workflows/ci.yml`、`scripts/validate-repository.sh` 和必要的脚本，不改变业务行为。

## 6. 验收标准

- 本地 `npm test` 通过。
- CI 能在无真实 `.env.production` 的情况下用 `.env.production.example` 完成 Compose config 渲染。
- 生产配置校验能证明模板含占位符时会失败，真实生产环境必须替换后才能启动。
- `/health` 响应包含请求 ID 与安全头。
- 所有新增行为都有红绿测试记录。

## 7. 计划自审结论

审查后确认需要规避以下逻辑漏洞：

- 生产 DB/Redis 默认密码必须解析 URL password 字段，不能对整段 URL 做字符串包含判断，否则用户名、库名中的 `video` 会误判。
- 限流测试必须使用独立 limiter 实例，路由接入需要可重置或可注入，避免测试间共享全局状态造成偶发失败。
- CI 的生产 env 校验应采用负向门禁：`.env.production.example` 保留占位符时必须失败，证明模板不会被误当成可上线配置。
- Docker config 校验可以临时复制 `.env.production.example` 为 `.env.production`，但执行后必须清理，不能把真实或临时 env 提交。
- 请求 ID middleware 不应吞异常；业务异常仍交给现有 `AppError` 或 FastAPI 默认异常处理。

## 8. 非目标

- 本轮不引入 Kubernetes、Helm、Prometheus、OpenTelemetry 服务端或复杂网关。
- 本轮不重构数据库迁移体系为 Alembic。
- 本轮不实现支付、团队、多租户计费或用户 Cookie 托管。
- 本轮不把真实平台 smoke 放进默认 CI。
