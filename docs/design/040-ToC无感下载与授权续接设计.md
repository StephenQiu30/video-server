## 1. 审查发现：先修正授权链路的正确性

以下每项对应 BACKLOG 同号 P7 任务；不是把所有下载失败都归因于登录。没有通过运行中的生产会话复现截图，不能认定其中某一项就是截图的唯一根因。

### [P1] F01 为生产 API 接通授权控制目录 — `docker-compose-prod.yml:143`

生产配置新增 `PROVIDER_AUTHORIZATION_QUEUE_ROOT`，但 API 没有开发 Compose 中的 control bind mount。按当前生产文件启动时，宿主安装的 marker、请求和响应目录不可见，`begin()` 会返回未安装，浏览器授权无法开始。补齐受限控制通道，而不是挂载整个浏览器或快照目录。

### [P1] F02 分离宿主初始化与 API 队列读写权限 — `backend/app/workers/runner/provider_authorization_queue.py:164`

API 入队、读结果、取消都会调用 `prepare_authorization_runtime()`，后者会 chmod 宿主创建的目录，包括 0700 的 sources；请求本身又以 API 身份创建为 0600。当 API 容器 UID 与宿主 Agent UID 不同且挂载保留 POSIX 所有权时，API chmod 或宿主读取会被拒绝。同 UID 的临时目录单测不覆盖此部署。初始化只由目录所有者执行，跨进程读写必须有明确、最小权限契约，不以全局 chmod 777 修复。

### [P1] F03 在完整写入后才发布授权请求 — `backend/app/workers/runner/provider_authorization_queue.py:165`

请求直接以最终 `.request` 名称创建，再写内容；消费者发现文件时可能读到 0 字节，随后将其视为非法并删除。生产者最终写完一个已被取消链接的文件，事务只能等待超时。使用同目录临时文件、完整写入与 fsync 后原子发布，消费者不消费临时文件。

### [P1] F04 用条件更新保护授权终态 — `backend/app/services/provider_authorization.py:192`

`get()` 与 `cancel()` 都在读取 pending 后无条件写 status。GET 读到成功结果后暂停、取消先落库、GET 再写入的顺序，会把 cancelled 改回 authorized，恢复已被用户取消的流程。内存并发复现确认这一结果。终态迁移需要版本检查或 CAS，取消和过期不能被迟到结果覆盖。

### [P1] F05 在成功保存结果之后再确认消费 — `backend/app/services/provider_authorization.py:190`

当前先删除 Agent 响应，再写 Redis；若该次 Redis 写失败，下次轮询既没有响应也没有终态，成功授权永久丢失。故障注入已复现“响应不存在、记录仍 pending”。保存结果、恢复事件与确认消费应可幂等重放，失败不能丢失唯一结果。

### [P1] F06 使关闭授权框失效所有在途回调 — `frontend/src/components/providers/provider-authorization-dialog.tsx:84`

关闭只清理 interval，不失效已发出的 GET；迟到 authorized 仍会调用 `onAuthorized()`。POST 未完成时关闭，因为 transaction 还是 null，也不会取消随后创建的事务。为请求增加 generation/取消标记；迟到 POST 结果应补偿取消，迟到 GET 不得恢复任务，取消权威仍在服务端。

### [P1] F07 在等待用户授权时继续服务其他会话请求 — `backend/app/workers/runner/provider_cookie_agent.py:446`

初始 refresh 队列清空后，Agent 阻塞在 `authorization.result()`；授权可能等待至十分钟截止。在同一个按需 LaunchAgent 仍运行时，新来的 probe/refresh 没有后续 drain，其他平台可能随之超时。保留有界工作循环或将等待改为可重入的短步骤，不为每个请求新建常驻服务。

### [P1] F08 将本地来源可读与平台授权通过分开 — `backend/app/workers/runner/provider_cookie_agent.py:543`

新事务只根据本地 `_export_from_source()` 的 OK 就写 authorized；过期但本地格式仍有效、已被上游撤销的材料也会触发前端“已完成授权”并重试。应先报告 source_available，再用当前身份和批准路线做有界平台验证；平台验证通过仍不等于媒体交付成功。

### [P1] F09 限制普通用户修改宿主共享授权来源 — `backend/app/api/routes/providers.py:64`

新接口仅要求登录，事务按 user 隔离，但落地的是全宿主唯一的 `<provider>.source`，请求没有用户凭证域。多用户部署中，一个普通账号可打开宿主专用浏览器、切换其他用户使用的来源。现阶段至少限制为明确批准的本机部署管理员；面向个人用户的授权必须独立绑定 owner，不能把事务归属检查当作会话隔离。

### [P1] F10 为授权队列设置准入和并发上限 — `backend/app/workers/runner/provider_cookie_agent.py:475`

新接口每次创建新 token，无活跃事务去重；Agent 以待处理请求数作为线程数，并可为每个 dedicated 请求打开浏览器。多标签重复点击或连续请求即可产生无界线程、并发浏览器。按 owner/provider/source 合并活跃事务，增加全局上限、每 Provider 串行发布及队列背压。

### [P2] F11 按受限域收集完整的会话作用域 — 已移除的扩展原型

`getAll({url: 'https://根域/'})` 只返回匹配该 URL 的 Cookie，遗漏 `www` 等子域的 host-only Cookie，以及非根路径 Cookie；即使 Chrome 已登录，也可能得到不完整材料。改为批准域过滤并保留 host/path/store 等必要语义，不能扩大到整个浏览器。Chrome 官方对 domain、url 的区别见 §12。

### [P2] F12 不让空值的可选 Cookie 删除整个快照 — `backend/app/workers/runner/provider_browser_bridge.py:210`

所有 value 使用禁止空串的 `_text()`；一个空值可选 Cookie 会导致整个批次异常，并进入 `sync_message()` 的删除旧快照分支。合成数据复现确认有效 SID 加空值字段会删除旧材料。合法空值应按 Cookie 语义处理；畸形更新、明确退出登录和权限撤销必须分开，不能以解析异常代替撤销事件。

### [P2] F13 只向有对应能力的平台提供 Chrome 授权 — `frontend/src/components/providers/provider-authorization-dialog.tsx:41`

新组件对视频号以外的所有 Provider 都展示 Chrome 流程；现有状态页也向 cookie_file 的腾讯视频、优酷传入此组件，而服务只接受 CHROME_PROFILE 平台。这些按钮会稳定返回不支持。由服务端动作能力决定展示，文件来源不能被一个通用按钮伪装成浏览器授权。

### [P2] F14 为视频号状态页提供真实动作 — `frontend/src/components/providers/provider-authorization-dialog.tsx:242`

视频号按钮仅执行可选 `onAuthorized`。`provider-status-item.tsx:112` 没有传入该回调，用户点击后没有请求、状态刷新或说明。解析页的受控重试与状态页的维护动作应分开定义；没有可执行动作时不要显示可点击的空操作。

### [P2] F15 保存 CLI 选择的专用浏览器来源 — `backend/app/workers/runner/provider_cookie_agent.py:364`

CLI 成功后只保存 current_chrome 来源，而 `drain_requests()` 的缺省来源已改成 current_chrome。新安装按文档完成 dedicated_chrome 授权后，Agent 仍可能去找不存在的当前浏览器快照。所有成功的显式来源选择都要一致发布，并以实际后续 refresh 验证，不只检查 CLI 退出码。

### [P2] F16 将操作截止时间与结果保留期限分开 — `backend/app/services/provider_authorization.py:156`

Redis key TTL 与授权 deadline 相同；真实 Redis 到期会先删除 owner/status，`get()` 返回 404，通常无法进入预期 expired 分支，也无法向 Agent 发取消。现有 FakeRedis.expire 不执行过期，未覆盖这一情况。操作停止时间独立于结果保留窗口，增加超时收敛和残留文件 GC。

### [P2] F17 等待可验证的同步结果再使用新来源 — `frontend/src/lib/provider-authorization.ts:77`

浏览器同步是无回执 postMessage，调用方随即发起解析；首次同步较慢或失败时，Runner 仍可能读到旧/缺失快照。扩展 `syncAll()` 还吞掉所有失败并返回 ok，不能作为同步证明。以 request_id、provider、revision 关联 ACK，有限等待；失败进入后台状态，不能无限卡住页面。

### [P2] F18 使用有界活性探针判断 Agent 可用 — `backend/app/workers/runner/provider_authorization_queue.py:121`

新 `agent_ready()` 只检查 `.agent-installed` 固定文件。launchd 未加载、wrapper 失效或宿主进程无法运行时文件仍在，API 仍创建 pending，页面长期等待一个不会被处理的事务。安装状态和运行可达分别报告，用有时限的非秘密请求/应答验证控制通道。

### 总体判断与本轮证据

当前变更尚不适合以“平台无感下载已解决”验收。桥接改变了 Cookie 读取责任主体，但没有完成请求可靠交接、有效访问验证、持久任务续接和最终文件交付。

- 定向后端测试：四个文件共 **27 passed**，范围是授权服务、授权文件队列、Native Messaging 桥、Cookie Agent。
- 定向前端测试：`download-page.test.tsx`、`paid-content-inspection.test.tsx` 共 **26 passed**。
- 额外内存实验：F04、F05、F12 均复现；没有连接实际 Redis、读取真实 Cookie 或写入业务数据。
- F01–F03、F06–F11、F13–F18 为调用链/配置审查证据，尚需对应集成或浏览器回归；不把推导写成已实机复现。
- 未运行全仓测试、生产镜像构建、跨 UID 挂载验收、24 平台真实下载。上述单测通过不抵消缺陷，也不能证明媒体可交付。

## 2. 产品目标：一次提交，自动推进，必要时只补一次动作

普通流程：用户粘贴链接，选择或沿用明确展示的下载选项，点击一次“下载”；系统创建可恢复的意图，自动解析、使用既有批准能力、下载、校验并给出文件。不因匿名路径的一次失败立即弹授权框。

真正需要用户操作时，保留原链接、格式偏好、任务归属和进度，展示具体动作；授权完成后系统续接同一意图，不让用户重新粘贴、重新解析或创建重复任务。

“无感”的边界：

- 自动化系统内部的同步、受支持的刷新、有限重试、排队、续接；不自动取得用户从未授予的权限。
- 首次安装本机连接器、首次平台同意、账号切换、撤销后重新授权和平台强制验证不伪装成后台成功。已有授权且仍有效时不重复打扰。
- Chrome 已登录只代表浏览器具有某种访问状态，不证明当前执行上下文可下载。Cookie、JS 执行环境、平台令牌、出口、权益和媒体 URL 都有各自约束。
- 公开 metadata 可读、视频可播放、文件分片 206、任务提交 200 均不能代替完整制品验证。
- 不要求额外常驻机器；不引入 Go、另一个任务编排产品或第二套下载引擎。纯网页无法自动拥有本机浏览器权限；本机桥是可选且需安装的能力，不是全用户的启动前置。

## 5. 持久意图与状态所有权

### 5.1 最小数据增量（字段设计，尚未建表）

`download_intent` 放在既有 downloads 业务域，保存：`id`、`owner_id`、`idempotency_key`、`request_fingerprint`、规范化 source、选项快照、批准的访问策略引用、`state`、`version`、`next_attempt_at`、截止时间、`authorization_id`、`inspection_id`、`job_id`、稳定 `reason_code`、创建/更新时间。

- 唯一约束 `(owner_id, idempotency_key)`；同 key、不同请求指纹返回冲突。双击、网络重发复用 key；用户明确新建任务使用新 key，不按 URL 永久去重。
- 不存 Cookie、密码、原始 bearer token、带签名媒体地址或整份上游响应。访问上下文仅持有现有受控引用/版本。
- 这是创建 job 之前的短流程，不是第二个下载任务表。`handed_off` 后 job 的执行进度、重试次数、制品和失败由现有 job 唯一持有，API 聚合投影给用户。
- 取消、恢复和交接使用 version/CAS；创建 job、绑定 job_id 与 outbox 应在一个业务事务中提交，或通过既有仓储的幂等交接协议实现等价效果。重放不能生成两个 job。
- 保存 source 时沿用现有 URL 校验、SSRF 防护和敏感参数脱敏；快照过期不代表可无限保留敏感原始 URL。

### 5.2 状态迁移

| 当前状态        | 条件/事件                    | 下个状态           | 用户感知                            |
| --------------- | ---------------------------- | ------------------ | ----------------------------------- |
| accepted        | Worker 获得准备租约          | resolving          | 正在准备下载                        |
| resolving       | 已批准路线解析成功、选项完整 | handed_off         | 交接既有下载任务                    |
| resolving       | 短时网络/上游限流，可重试    | waiting_retry      | 自动恢复中；显示下次时间            |
| resolving       | 需要真实用户动作             | action_required    | 保留任务，只展示必要动作            |
| waiting_retry   | 到期且仍有预算               | resolving          | 不要求再次点击                      |
| action_required | 对应授权验证成功且意图未取消 | resolving          | 自动继续同一任务                    |
| 任一非终态      | 用户取消或业务截止           | cancelled / failed | 停止并给出真实原因                  |
| handed_off      | 后续事件                     | 保持交接结果       | 从 job 投影排队/下载/校验/完成/失败 |

首次点击前不解析私人内容、不预下载。若产品仍保留“仅解析”按钮，明确它只预览；只有用户选择“下载”才创建可自动交付的意图。合集多项、超出默认配额、收费选择和无法确定的候选需明确选择，不以自动化隐藏批量操作。

## 6. 自动访问决策：无感但不越权

每次尝试根据当前 owner、Provider policy、内容类别、有效批准范围和执行环境决定路线。策略先行，不是失败后无限枚举抓取方式。

1. 执行已批准且当前可用的路线。公开内容无需凭证则直接获取；已经为该用途批准的受控来源可按 policy 使用，不必每次故意先失败一次。
2. 暂缺材料时，在已有同一授权范围内等待同步 ACK 或执行平台允许的刷新；使用 single-flight 合并并发刷新。
3. 新材料必须校验来源、账号身份、权益基线、版本与时效。无法确认同一主体，不静默继续，也不把账号切换视为普通 Cookie 轮换。
4. 有限重试仍失败时根据原因停止、等待冷却或请求用户动作。不得从 public 自动升级至未经批准的 operator 身份，不切其他账号、未知代理或改变内容权限。
5. metadata 与 media 分别执行访问证明；媒体阶段签名 URL 失效可在同一授权和配额内重新解析，不新建重复任务。上下文变更遵守 inspection 冻结规则，不用新身份执行旧证明。

对于无需 metadata 才能确定下载计划的已批准直链，可走既有相应路径；普通媒体仍先取得必需的格式/内容证明。不能为了“一步下载”跳过内容准入。

### 6.1 授权与同步元数据

授权绑定最小包含 owner/部署管理域、provider、来源类型、允许用途、受控 subject 标识、grant version、verified_at、expires_at（未知不等于永久）、撤销状态。浏览器快照额外绑定 device/source epoch、单调 revision、synced_at 和保留时限。

- 当前宿主共享来源暂只允许部署管理员维护；个人用户授权隔离未落地前，不开放普通用户修改宿主身份。管理员授权不自动变成任意用户的内容访问许可。
- 连接器只同步已启用、已批准的平台。安装扩展不默认收集八个平台；增加平台时明确同意，撤销后停同步并失效对应材料。
- 按 Provider/source 串行发布或拒绝旧 revision，退出登录产生撤销版本；晚到的旧同步不能覆盖退出事件。session Cookie 没有 expirationDate，也必须受快照时效和来源活性约束。
- 临时桥接故障可以保留未失效旧材料，标记 stale；已撤销、已过期、身份漂移不得继续使用。普通 API/前端只看状态，不返回原始凭据。
- 平台无官方刷新机制时不杜撰 refresh token；仅在批准的本地浏览器来源中同步实际变更。平台仍需验证时诚实显示一次动作。

### 6.2 授权事务协议

事务绑定 `intent_id + owner + provider + source + nonce + expected_epoch/version + deadline`，回调 origin/redirect 由固定配置校验。只持有事务 token 不能修改别人的来源。

`pending → source_available → verifying → authorized | action_required | failed | expired | cancelled`。来源可读不是 authorized；平台验证成功只说明当前批准访问，仍需媒体下载验收。实现时统一调整 Pydantic 枚举和所有消费端，不手改生成 API。

结果先幂等持久化，状态更新和“恢复意图”事件可靠提交，再 ACK Agent；取消/超时拥有终态保护。重复、乱序、跨账号和旧 generation 回调均不能恢复任务。操作 deadline 与结果保留 TTL 分开；清理器只回收终态、无活跃引用的记录和文件。

## 7. 托管来源、本机通道与部署

ToC 默认链路使用部署方维护的单平台来源，普通客户端不安装扩展、不持有平台 Cookie，也不参与 Runner 选路。Runner 每次操作重新打开只读来源，因此部署方可通过 Secret volume 或 secret controller 原子轮换，不需要重建镜像或重启容器。本机 Agent 只保留为个人本地部署的可选导入适配器，不要求额外服务器，也不进入普通用户请求路径。无授权、无扩展时核心 API/页面仍应启动并处理可公开取得的内容。

- 短期修复现有 control 队列，明确创建者、请求写者、消费者、结果读者及权限。API 不应 chmod 宿主私有目录，也不挂载快照/密钥。
- 使用原子发布、不可预测事务 ID、大小限制、过期校验、固定目录、无 symlink 文件操作和幂等消费。只有非秘密控制消息可跨 UID 共享；若所需部署不能安全共享，则采用明确认证的本机 IPC，不用放宽整个目录权限兜底。
- 安装标识、活性探针、来源就绪、上游可访问是四个独立状态。活性不可达快速给出部署状态；不能让用户做无效登录。
- 授权等待不占住所有同步通道。采用有界并发、每 Provider 单飞、公平调度；所有子进程有 deadline 和清理。
- Dev/Prod 同一控制协议但显式配置不同部署能力；macOS 原型不能声明 Linux 原生 Chrome 桥已经支持。非支持环境显示部署限制，不提供必失败的动作。
- 新机自动完成可重建配置与能力探测；凭据不随 Git 迁移。业务意图可恢复不意味着第三方身份可以无授权复制到另一台机器。

## 8. API、交互与统一错误处理

### 8.1 契约提案

在现有 API 版本/路由规范下新增“创建意图、读取意图、取消意图”三个操作，授权创建支持关联 intent。具体路由名实施时按现有 schema 统一，不维护另一份手写 Swagger。

响应至少包含：意图 ID、version、阶段、关联 job、稳定原因、`next_action`、下一次尝试时间和有限进度。`next_action` 为受约束的动作类型与参数，不是任意外部 URL；`none / authorize / verify_on_platform / choose_source / choose_format / contact_operator / view_limit` 等枚举由实际能力裁剪。

FastAPI 注解和 Pydantic 生成 `/openapi.json`，再运行现有 `@umijs/openapi` 流程生成客户端；补 schema diff、状态枚举及错误响应测试。Next.js 页面不自行从 hostname + 错误字符串推断权限。

### 8.2 页面行为

- 常态：解析框、下载选项、一个明确主按钮；提交后显示任务状态和取消，不先显示红色失败再由用户修复系统内部同步。
- 可恢复中：同一块状态显示“正在恢复连接/等待平台响应”，公开合理等待时间；没有人为百分比和无截止转圈。
- 需要动作：任务内持久显示原因和一个主动作。只有用户点击时打开官方 Radix/shadcn Dialog 或平台授权页；不自动弹窗、抢焦点或反复打开登录。
- 完成动作：服务端恢复同一 intent，页面自动订阅/轮询；刷新、关闭后重新进入仍能继续观察。瞬时结果用 Sonner，待操作/失败详情保留在任务状态区。
- 网络短暂中断：前端恢复观察，不创建新事务；采用有界退避，达到观察上限提示重新连接。关闭弹框、取消授权与取消下载是不同操作，文案明确。
- 统一 `design.md` 的无装饰外框、左侧内容基线、neutral token、官方组件焦点和错误语义。官方交互控件不为“无边框”而丢失可访问性。
- 后台制品完成不等于已写入用户 Downloads。浏览器自动保存受用户手势/策略限制时提供“获取文件”；不得将后台 ready 宣称为本地保存成功。

### 8.3 原因与恢复动作

| 原因                                            | 系统动作                     | 用户动作                       |
| ----------------------------------------------- | ---------------------------- | ------------------------------ |
| 同一授权材料轮换/短时失步                       | 同步、校验、有限重试         | 无                             |
| 网络故障/429/上游暂时不可用                     | 统一退避，遵守 Retry-After   | 等待或取消                     |
| 首次授权/明确撤销/主体变化                      | 暂停对应意图                 | 一次授权或确认主体             |
| 平台要求挑战                                    | 暂停，保留上下文             | 在平台完成验证；不保证一次成功 |
| Agent/扩展缺失、队列权限、解析器配置错误        | 给出部署级诊断，隔离平台状态 | 部署者处理；不要求普通用户重登 |
| DRM、无访问权、删除、地区限制、超出批准内容范围 | 终止并保留稳定原因           | 查看限制或换合法内容           |

## 9. 预算、大文件与可观测性

以下数字是待实测调整的初始产品预算，不是当前性能承诺：

- 页面提交目标 2 秒内拿到持久意图；长解析在 Worker，不占 HTTP 连接直到完成。
- 本机同步 ACK 初始预算 5 秒；平台实际验证沿用已有有界 Runner 配置，不等同于 5 秒内验证成功。
- 一次自动恢复最多两次可恢复尝试，计入统一持久预算；不得叠加前端、Agent、Worker、Runner 各两次变成指数放大。遇 Retry-After 以服务端排期为准。
- 交互授权沿用十分钟操作窗口作为初始值；结果另保留有限窗口用于查询和幂等确认，建议初始 24 小时，按隐私保留规范最终配置。
- 大文件沿用业务下载大小/时长/空间/总时限；另区分无进度超时和总期限。支持安全 Range 的来源可按已有任务续传，重新签名后必须重新确认资源身份；不支持则在原任务有界重试。
- Canary 的 300 秒观察截止记为 observation_timeout，继续查询同一 job 或按测试策略明确取消；不能直接记录 provider 下载失败，更不能无限放宽业务截止。

记录不含凭据的 intent/job/request correlation ID、阶段、原因、route、context generation、重试次数、授权动作次数、最终制品验证。统计一次提交完成率、无需动作完成率、动作后自动续接率、授权假阳性率、P95 阶段耗时。分母明确排除/单列不支持内容，不通过隐藏失败提升成功率。

## 10. 实施顺序与完成门槛

1. **P7 正确性修复**：优先部署通道、跨 UID、原子发布、终态/CAS、可靠 ACK、取消、调度和 owner 权限；修复误报和无效 UI。每个 F 独立回归，不以重写全系统替代。
2. **P8.1–P8.3 最小纵向能力**：持久意图、幂等交接、既有授权复用和自动恢复，先接三个问题平台；不新增替代下载引擎。
3. **P8.4–P8.5 产品与契约**：统一动作/错误、自动生成客户端、页面生命周期恢复；再覆盖平台状态和所有入口。
4. **P8.6–P8.7 验收**：同宿主 clean-room、部署重启和 24 平台 metadata/media 矩阵。保留公开成功、需要动作、部署不可用、不支持四类真实结果，未通过不能勾选完成。

## 11. 验收矩阵

| 场景                                | 必须证明的结果                                               |
| ----------------------------------- | ------------------------------------------------------------ |
| 匿名公开内容                        | 一次下载提交，真实文件完成；没有不必要的授权请求             |
| 已批准有效来源                      | 无授权弹窗，不重复选择身份；同一上下文完成文件               |
| 正常轮换/同步较慢                   | 同一 intent 自动恢复；不以旧快照先宣告成功                   |
| 上游已撤销但本地材料仍可读          | 不返回假 authorized；只发出准确必要动作                      |
| 完成必要授权                        | 同一 intent 继续且只生成一个 job，无需重新粘贴               |
| GET/POST/回调乱序、取消竞态         | 终态不被复活，无孤儿授权，无重复下载                         |
| Redis 写失败/消费者重启/outbox 重放 | 成功结果不丢失、事件可恢复，job 幂等                         |
| 并发多用户/多标签/多 Provider       | 不串账号、不切他人来源、有界并发，一个平台等待不饿死其他平台 |
| 退出登录/旧同步晚到/桥失联          | 撤销版本不被旧快照覆盖，过时材料不被误报有效                 |
| 同步数据边界                        | 覆盖子域、path、合法空值、不同 store；不采集未批准平台       |
| API 容器 UID 不同/Dev 与 Prod       | 实际安装到请求、结果全环可达；API 不接触快照或密钥           |
| 关闭页面/刷新/重启核心服务          | 可查询同一意图/任务；有序续接，不要求重取 Cookie             |
| 大于观察预算的文件                  | 仍能观察原 job；完整文件才算成功，停止观察不等于平台失败     |
| 桌面/390px/明暗主题                 | 对齐、焦点、取消、状态恢复和必要动作可操作                   |

24 平台从现有 registry/固定 canary 矩阵枚举，不另建容易漂移的“全部支持”清单。每平台采用批准的公开固定样本并记录访问策略、环境、metadata、media、任务 ID、耗时、稳定错误、文件校验；音视频以 ffprobe 的容器/流/时长等验证，图库按对应格式验证。测试账号、文件、授权材料隔离；清理只针对本次创建且无活跃任务的测试资源，不删用户数据。

## 12. 官方依据与解释边界

- [Chrome cookies API](https://developer.chrome.com/docs/extensions/reference/api/cookies)：domain 与 url 查询作用不同；store、hostOnly、path 和 session Cookie 需保留其作用域语义。这支持 F11 及来源隔离设计，不证明任一平台会接受导出的材料。
- [Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)：浏览器扩展与已安装本机宿主通信，需要声明权限与允许来源；不能据此宣称纯网页可零安装读取浏览器授权。
- [yt-dlp PO Token Guide](https://github.com/yt-dlp/yt-dlp/wiki/PO-Token-Guide)：平台访问所需的证明具有独立上下文。不能把令牌/客户端问题全部包装成用户登录失效；也不把第三方 API 的元数据权限当作媒体下载授权。

## 13. GitHub 竞品复核与可扩展落地（2026-09-22）

本节纠正“每台客户端安装浏览器扩展”的错误产品边界。调研对象均采用服务端下载引擎，浏览器能力至多是可选辅助入口：

- [yt-dlp](https://github.com/yt-dlp/yt-dlp/blob/master/README.md) 将站点差异放在 extractor/plugin，认证通过 netrc、Cookie 文件或可选的 `--cookies-from-browser` 注入；后者依赖本地 keyring，不能作为 Web 产品的普遍前置条件。
- [MeTube](https://github.com/alexta69/metube/blob/master/README.md) 是 yt-dlp 的自托管 Web 层，下载选项可由服务端文件配置并热加载；浏览器扩展/bookmarklet 只负责把链接送到服务端，服务端处理不依赖每个访问设备安装扩展。
- [Pinchflat](https://github.com/kieraneglin/pinchflat/blob/master/README.md) 使用自包含服务端任务处理，Cookie 与自定义 yt-dlp 参数都是可选部署配置，不属于每个终端的登录流程。
- [Cobalt](https://github.com/imputnet/cobalt/blob/main/docs/api-env-variables.md) 使用服务注册表、可选 `COOKIE_PATH`、可禁用服务、Redis 与多实例配置；其 Cookie manager 由主进程加载受限服务集合并分发给 Worker，YouTube 的 PO Token/visitor data 由独立 session service 定期刷新。可借鉴的是“来源适配器 + 服务端共享 + Worker 隔离”，不是复制其解析实现或把公共实例当作依赖。

FrameFetch 据此采用三层来源：

1. `anonymous`：公开链接默认由服务端 Provider Profile/yt-dlp plugin 解析，YouTube PO Token sidecar 属于可重建的运行能力，不是用户身份。
2. `deployment_managed`：需要平台身份但仅处理部署方已批准公开用途的路线，从 `PROVIDER_SESSION_DIR/<provider>/cookies.txt` 读取单平台 `0600` 来源；容器只读挂载，每次操作重新读取，修订变化生成新 context generation，并由 Redis 租约限制同一凭据并发。
3. `local_agent`：按 Provider 隔离的 Chrome 与 Access Agent 仅作为个人部署的可选授权/诊断适配器。它不能出现在普通 ToC 用户的解析前置流程。

已落地的第一阶段：YouTube、抖音、Reddit Operator Runner 从本机 Agent 队列切换为同一 `PROVIDER_SESSION_DIR` 契约；前端解析不再唤醒浏览器桥，恢复动作改为服务端托管线路；视频号因元宝动态会话仍保留专用 adapter。生产中可将该目录指向 Docker/Kubernetes Secret、加密持久卷或外部 secret controller 的只读投影，多 Runner 继续使用既有 Redis 凭据租约，不共享可写 Cookie 目录。

该方案不承诺绕过平台验证：首次建立或撤销后的身份仍需由部署方通过平台允许的流程取得；真正的“无感”是一次部署授权服务所有合法公开请求，而不是让应用伪造账号、跨用户共享私人权益或永久恢复已撤销会话。后续集中凭据 Broker 只有在出现多主机部署需求时才实现；其接口复用现有 `ProviderCookieSync`，不能在当前单机 Compose 中提前增加第二套数据库或下载引擎。
