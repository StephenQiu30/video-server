# 总体技术设计

## 1. 背景

新版文档体系将项目重新收束为“个人自部署的视频下载器”主线，技术设计必须服务这个边界：FastAPI 提供接入，Redis Queue 解耦执行，Worker 调用 `yt-dlp`，Postgres 管理状态，MinIO 保存产物。

## 2. 目标

1. 建立清晰的 API、Worker、Queue、DB、Storage 边界。
2. 为 5 个功能点 PRD 提供统一的技术真相源。
3. 定义可扩展但不过度设计的数据模型。

## 3. 非目标

- 不设计 AI 摘要、PDF 报告或字幕提取主链路。
- 不设计多租户 SaaS 账号体系。
- 不引入超出 MVP 需要的微服务拆分。

## 4. 核心内容

### 4.1 总体架构

系统由 5 个核心边界组成：

1. `FastAPI API`
   负责接收 URL、创建任务、查询任务、签发下载链接。
2. `Redis Queue`
   负责 API 与执行层解耦。
3. `Worker`
   负责调用 `yt-dlp`、抽取元数据、上传 MinIO、回写状态。
4. `Postgres`
   保存任务、事件、平台画像与产物索引。
5. `MinIO`
   保存主视频、封面和元数据文件。

### 4.2 主数据流

`提交 URL -> API 校验 -> Postgres 建任务 -> Redis 入队 -> Worker 下载 -> MinIO 保存 -> Postgres 更新状态 -> API 返回详情与下载链接`

### 4.3 目录与模块边界

建议沿用当前仓库运行时组织方式：

```text
apps/api/app/
apps/worker/worker/
packages/shared/video_downloader_shared/
```

模块职责：

- `routers/`：协议层，仅处理请求响应
- `schemas/`：Pydantic 契约
- `services/`：业务编排
- `repositories/`：数据库读写
- `worker/jobs/`：异步任务入口
- `worker/adapters/`：`yt-dlp`、MinIO、Redis 封装
- `shared/`：状态枚举、错误码、DTO、常量

### 4.4 数据库设计

#### 表 1：`download_tasks`

核心字段：

- `id`（UUID 字符串主键）
- `user_id`（外键 → `users`）
- `source_url`
- `title`
- `cover_url`
- `duration_seconds`
- `format_id`
- `format_label`
- `retry_of_task_id`（自引用外键）
- `attempt_no`
- `state`（`QUEUED`/`RUNNING`/`SUCCEEDED`/`FAILED`/`CANCELED`）
- `progress`
- `failure_code`
- `failure_reason`
- `output_filename`
- `object_key`（MinIO 对象路径）
- `object_size`（BigInteger，字节）
- `expires_at`（UTC 过期时间）
- `ai_summary`、`ai_mindmap`、`ai_status`、`ai_error`
- `enhanced_status`、`subtitle_data`、`video_metadata`
- `created_at`、`updated_at`

产物索引直接存储在 `download_tasks` 表上（`object_key`、`object_size`、`expires_at`），不使用独立的 `task_artifacts` 表。

#### 表 2：`task_events`

核心字段：

- `id`
- `task_id`（外键 → `download_tasks`）
- `state`
- `message`
- `created_at`

#### 表 3：`platform_profiles`

核心字段：

- `id`
- `platform_id`
- `display_name`
- `platform_category`
- `enabled`
- `compliance_note`
- `supports_download`
- `supports_thumbnail`
- `supports_metadata`
- `created_at`
- `updated_at`

### 4.5 表关系

- `download_tasks 1 -> N task_events`
- `platform_profiles 1 -> N download_tasks`

实际索引：

- `download_tasks(state, created_at)`
- `download_tasks(user_id, created_at)`
- `download_tasks(retry_of_task_id)`
- `download_tasks(ai_status)`
- `task_events(task_id, created_at)`

### 4.6 状态机

任务状态固定为：

- `QUEUED`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELED`

约束：

1. 只有 Worker 可以把任务从 `QUEUED` 推进到 `RUNNING`。
2. 只有主视频成功归档后才能进入 `SUCCEEDED`。
3. 过期产物不引入新状态：任务保持 `SUCCEEDED`，通过 `failure_code = "retention_expired"` 和 `object_key = NULL` 标识。

### 4.7 错误语义

统一错误码（`failure_code`）：

- `invalid_url` — URL 校验失败
- `unsafe_url` — 安全地址被拒绝
- `unsupported_platform` — 不支持的平台
- `platform_restricted` — 平台受限
- `platform_rate_limited` — 平台限流
- `download_failed` — 下载失败
- `storage_upload_failed` — MinIO 上传失败
- `retention_expired` — 产物已过期清理
- `queue_unavailable` — 队列不可用
- `task_timeout` — 任务超时
- `not_found` — 任务不存在
- `invalid_state` — 状态不允许操作
- `rate_limited` — 请求限流
- `limit_exceeded` — 配额超限

### 4.8 MinIO 对象结构

对象 key 模式：

```text
users/{user_id}/tasks/{task_id}/{filename}
```

该模式保证按用户隔离、按任务聚合、文件名保持原始扩展名。

### 4.9 API 端点

- `POST /api/tasks` — 创建下载任务
- `GET /api/tasks` — 任务列表（支持 `state` 筛选）
- `GET /api/tasks/stream` — SSE 任务流
- `GET /api/tasks/{task_id}` — 任务详情
- `POST /api/tasks/{task_id}/cancel` — 取消任务
- `POST /api/tasks/{task_id}/retry` — 重试任务
- `GET /api/tasks/{task_id}/events` — 任务事件
- `GET /api/tasks/{task_id}/download-link` — 预签名下载链接
- `GET /api/tasks/{task_id}/pdf` — PDF 报告导出
- `POST /api/parse` — URL 解析与格式列表
- `GET /api/auth/me` — 当前用户信息
- `GET /health` — 存活检查
- `GET /ready` — 就绪检查

## 6. 验收门禁

- 设计覆盖 5 个 PRD 的技术边界。
- 数据库、状态机、对象存储和 API 边界清晰且不互相矛盾。
- 每个计划文档都能从本设计中找到明确技术依据。

## 7. 风险与边界

增强产物（AI 摘要、字幕、视频元数据）字段已直接存储在 `download_tasks` 表上。如果未来产物类型大幅增加，可考虑拆分为独立的 `task_artifacts` 表。

## 8. 待确认问题

- 是否在首版引入独立的任务事件接口。
- 是否为 `platform_profiles` 采用代码配置优先、数据库同步为辅。
