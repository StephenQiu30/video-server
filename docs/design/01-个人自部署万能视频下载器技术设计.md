# 总体技术设计

## 1. 背景

新版文档体系将项目重新收束为“个人自部署的视频下载器”主线，技术设计必须服务这个边界：FastAPI 提供接入，Redis Queue 解耦执行，Worker 调用 `yt-dlp`，Postgres 管理状态，MinIO 保存产物。

## 2. 目标

1. 建立清晰的 API、Worker、Queue、DB、Storage 边界。
2. 为 5 个功能点 PRD 提供统一的技术真相源。
3. 定义可扩展但不过度设计的数据模型。

## 3. 非目标

- 不设计 AI 摘要、PDF 报告或字幕提取主链路。
- 不设计多租户 SaaS 账号体系。
- 不引入超出 MVP 需要的微服务拆分。

## 4. 核心内容

### 4.1 总体架构

系统由 5 个核心边界组成：

1. `FastAPI API`
   负责接收 URL、创建任务、查询任务、签发下载链接。
2. `Redis Queue`
   负责 API 与执行层解耦。
3. `Worker`
   负责调用 `yt-dlp`、抽取元数据、上传 MinIO、回写状态。
4. `Postgres`
   保存任务、事件、平台画像与产物索引。
5. `MinIO`
   保存主视频、封面和元数据文件。

### 4.2 主数据流

`提交 URL -> API 校验 -> Postgres 建任务 -> Redis 入队 -> Worker 下载 -> MinIO 保存 -> Postgres 更新状态 -> API 返回详情与下载链接`

### 4.3 目录与模块边界

建议沿用当前仓库运行时组织方式：

```text
apps/api/app/
apps/worker/worker/
packages/shared/video_downloader_shared/
```

模块职责：

- `routers/`：协议层，仅处理请求响应
- `schemas/`：Pydantic 契约
- `services/`：业务编排
- `repositories/`：数据库读写
- `worker/jobs/`：异步任务入口
- `worker/adapters/`：`yt-dlp`、MinIO、Redis 封装
- `shared/`：状态枚举、错误码、DTO、常量

### 4.4 数据库设计

#### 表 1：`download_tasks`

核心字段：

- `id`
- `source_url`
- `normalized_url`
- `platform_id`
- `status`
- `progress`
- `title`
- `author`
- `duration_seconds`
- `video_object_key`
- `thumbnail_object_key`
- `video_filename`
- `video_size_bytes`
- `error_code`
- `error_message`
- `retry_count`
- `expires_at`
- `created_at`
- `updated_at`
- `started_at`
- `finished_at`

#### 表 2：`task_events`

核心字段：

- `id`
- `task_id`
- `event_type`
- `from_status`
- `to_status`
- `message`
- `payload_json`
- `created_at`

#### 表 3：`task_artifacts`

核心字段：

- `id`
- `task_id`
- `artifact_type`
- `object_key`
- `filename`
- `mime_type`
- `size_bytes`
- `checksum`
- `status`
- `expires_at`
- `created_at`

#### 表 4：`platform_profiles`

核心字段：

- `id`
- `platform_id`
- `display_name`
- `platform_category`
- `enabled`
- `compliance_note`
- `supports_download`
- `supports_thumbnail`
- `supports_metadata`
- `created_at`
- `updated_at`

### 4.5 表关系

- `download_tasks 1 -> N task_events`
- `download_tasks 1 -> N task_artifacts`
- `platform_profiles 1 -> N download_tasks`

建议索引：

- `download_tasks(status, created_at)`
- `download_tasks(platform_id, created_at)`
- `task_events(task_id, created_at)`
- `task_artifacts(task_id, artifact_type)`

### 4.6 状态机

任务状态固定为：

- `queued`
- `running`
- `succeeded`
- `failed`
- `canceled`
- `expired`

约束：

1. 只有 Worker 可以把任务从 `queued` 推进到 `running`。
2. 只有主视频成功归档后才能进入 `succeeded`。
3. `expired` 不表示下载失败，只表示产物已清理。

### 4.7 错误语义

建议统一错误码：

- `INVALID_URL`
- `UNSAFE_URL`
- `UNSUPPORTED_PLATFORM`
- `PLATFORM_RESTRICTED`
- `PLATFORM_RATE_LIMITED`
- `DOWNLOAD_FAILED`
- `STORAGE_UPLOAD_FAILED`
- `TASK_NOT_FOUND`
- `TASK_ALREADY_FINISHED`

### 4.8 MinIO 对象结构

建议对象 key：

```text
downloads/{yyyy}/{mm}/{dd}/{task_id}/video/{filename}
downloads/{yyyy}/{mm}/{dd}/{task_id}/thumbnail/{filename}
downloads/{yyyy}/{mm}/{dd}/{task_id}/metadata/metadata.json
```

### 4.9 API 建议

- `POST /api/tasks`
- `GET /api/tasks`
- `GET /api/tasks/{task_id}`
- `POST /api/tasks/{task_id}/cancel`
- `POST /api/tasks/{task_id}/retry`
- `GET /api/tasks/{task_id}/download`
- `GET /api/platforms`

## 6. 验收门禁

- 设计覆盖 5 个 PRD 的技术边界。
- 数据库、状态机、对象存储和 API 边界清晰且不互相矛盾。
- 每个计划文档都能从本设计中找到明确技术依据。

## 7. 风险与边界

如果未来引入字幕、音频或 AI 产物，需要扩展 `task_artifacts`，而不是把新字段堆进 `download_tasks` 主表。

## 8. 待确认问题

- 是否在首版引入独立的任务事件接口。
- 是否为 `platform_profiles` 采用代码配置优先、数据库同步为辅。
