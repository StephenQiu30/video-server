# 017 其他短视频平台分阶段接入设计

- 状态：PeerTube 实例白名单与完整视频分析证明门禁已实施；真实授权样本 E2E 待执行
- 日期：2026-08-12
- 前置设计：`docs/design/005-多平台Provider策略设计.md`、`docs/design/010-Codex与Claude CLI视频分析设计.md`、`docs/archive/016/016-中国短视频平台支持设计.md`
- 前置调研：`docs/research/005-其他短视频平台接入调研.md`

## 1. 目标

在不削弱下载安全、内容授权和完整视频分析质量的前提下，分阶段扩展其他主流短视频与社交视频平台。新增平台必须复用现有下载、MinIO、RabbitMQ、AI Agent、数据库报告、MD/DOCX 制品、WebSocket 和原任务重试链路。

当前 Phase 2 已实现通用探针结果表、定时执行器、动态状态聚合、PeerTube 精确实例白名单，以及对既有完整视频 Agent 任务链的持久化证明。默认不配置第三方目标或 PeerTube 实例，也不批准任何新增平台。只有 metadata、完整媒体、完整视频 Agent/报告证明均新鲜，并在 `PROVIDER_VERIFIED_KEYS` 显式批准后，新增平台才能提升为 `verified`。AcFun、Rutube、VK Clips、Dailymotion 和 NicoNico 已退出产品范围，相关域名明确拒绝，不能落入 Generic 解析器。

## 2. 不变原则

1. Agent 接收完整视频文件，不以固定抽帧替代视频输入。
2. 本设计的匿名/受控服务端 Provider 只处理公开、非 DRM、用户有权处理的内容；平台保护媒体走独立官方授权或用户设备 Edge Agent 路径。
3. 不调用公共第三方解析 API，不引入 MITM、账号自动化、私有签名生成或地域绕过。
4. URL 登记、extractor 存在、metadata 成功、整文件成功和 Agent 分析成功是五个独立状态。
5. 新平台优先使用固定 yt-dlp extractor；只有上游不满足且第一方公开页可稳定验证时才实现仓库可信插件。
6. carousel、图集和一个帖子多个视频在领域模型支持多资产 manifest 前 fail closed，不能静默只取第一个视频。
7. 重试沿用原 download/analysis/task 记录、尝试号和 WebSocket 主题，不创建新的业务任务。

## 3. 分阶段路线

| 阶段 | 平台 | 交付 | 状态变化条件 |
| --- | --- | --- | --- |
| A：现有 Profile 补证据 | TikTok、YouTube Shorts、Instagram Reels、Facebook Reels、X、Reddit、Pinterest、Vimeo、微博 | 正负 canary、完整下载、错误分类、状态聚合 | 完整 E2E 后从 `unknown/access_required` 升级 |
| B：上游 extractor 新 Profile | 批准实例 PeerTube、Snapchat Spotlight | 域名/路径 Profile、重定向、canary、UI 状态 | 新鲜授权样本完整 E2E 后登记 |
| C：受控会话 | 西瓜视频/头条视频 | 最小会话、Secret 生命周期、固定出口、短链 | 匿名或 operator-managed 路径稳定后登记 |
| D：可信插件候选 | Likee、Threads、好看视频、Kwai 国际版 | 独立 extractor、身份约束、负例、许可证记录 | 上游不可用且第一方公开页方案通过评审 |
| 独立路径 | 微信视频号、红果短剧 | 用户设备 Edge Agent + Artifact Import，当前仍为 `unsupported` | 按 `docs/design/019-用户设备EdgeAgent与媒体制品导入设计.md` 独立实施和验收 |
| 暂缓 | ShareChat/Moj/Josh/Roposo/Chingari/Lemon8 | 明确 `unsupported` | 找到安全、许可清晰、可维护的第一方路径后重审 |

阶段 A 优先于增加新平台。否则平台列表会增长，但用户仍无法知道哪些平台今天真正可用。

## 4. Provider 能力契约

后续实施应为平台 Profile 或等价 capability catalog 明确以下事实：

| 字段 | 含义 |
| --- | --- |
| `content_kinds` | 首期允许的 `single_video`；不默认允许 carousel、playlist、live |
| `path_patterns` | 可接受的第一方单视频路径，不只按 hostname 放行 |
| `redirect_hosts` | 短链可跳转的第一方域名集合 |
| `access_modes` | `anonymous` 或受控 `operator_managed`，普通 API 不接收 Cookie |
| `instance_scope` | 固定平台或明确 allowlist 实例，PeerTube 必填 |
| `canary_suite` | metadata、完整下载、负例和 Agent E2E 套件 |
| `support_status` | `unknown/verified/degraded/access_required/unsupported` |
| `evidence_at` | 最近一次状态证据时间，而非永久能力承诺 |

URL 完成重定向后必须重新执行 SSRF 校验、Provider 归类和路径 admission。Generic fallback 永远不携带 Provider 会话。

## 5. 已登记平台设计

### 5.1 TikTok

- 复用现有 `tiktok` Profile 和固定 yt-dlp，不新增 “TikTok Shorts” Provider。
- 首期只接受单视频 URL；photo/carousel 返回稳定的多资产不支持错误。
- 匿名路径优先；如需要 `sid_tt`，只能通过 005 定义的 allowlist Secret 生命周期进入独立 Runner。
- WAF、出口/区域、private、内容删除和 extractor regression 分开分类。
- 不新增自研设备指纹轮换或私有签名实现。

### 5.2 YouTube Shorts

- Shorts 只是 YouTube 内容入口，继续使用 `youtube` Profile、PO Token/EJS 和受控会话设计。
- `/shorts/{id}` 规范化后必须保留原视频身份；不新建平台统计维度。
- 当前出口仍为 `access_required`，在 Cookie、PO Token、EJS 和 IP challenge 分别通过前不提升状态。

### 5.3 Instagram/Facebook Reels

- 复用现有 Profile；单 Reel 是首期唯一新增 canary 类型。
- Instagram carousel 和 Facebook 多附件帖子 fail closed，不能静默选第一项。
- 登录墙与 private/follow-only 内容必须区分；运维账号不得授予额外内容权益。
- 完整视频制品仍由 ffprobe 验证音视频轨和时长，不能直接把 CDN URL 交给 Agent。

### 5.4 X、Reddit、Pinterest、Vimeo、微博

- 每个平台先增加公开单视频正例、图片/不可用负例和完整下载 canary。
- Reddit processing 状态允许在统一预算内延迟重试；private/quarantine 不重试。
- Pinterest 图片 Pin、微博图文和 X 相册在多资产模型前明确拒绝。
- Vimeo 密码页、私有页和 Referer 限制不能合并成普通 extractor 错误。

## 6. 上游 extractor 新 Profile 设计

### 6.1 PeerTube

PeerTube 是协议/软件生态，不是单一受控域名。不能注册 `*.peertube` 或允许任意用户输入实例后直接抓取。

- 运维通过 `PEERTUBE_ALLOWED_INSTANCES` 显式配置批准的 DNS hostname；首版只允许默认 HTTPS 端口，不接受 scheme、端口、IP 或通配符。
- 首版对外使用统一 `peertube` Profile，实例证据由独立 `target_id` 隔离；实例级配额与熔断是后续扩展项。
- DNS 解析和每次重定向都执行私网、link-local、回环和保留地址阻断。
- manifest、segment、thumbnail 和字幕的所有后续 URL 必须继续经过 egress policy。
- 实例关闭、软件升级或证书异常只影响该实例，不降级整个 Provider 集群。

当前实现 key 使用 `peertube`，API 对外展示 “PeerTube”；不得把未在白名单中的实例交给 generic fallback 当作已支持 PeerTube。

### 6.5 Snapchat Spotlight

- 只允许 `snapchat.com/spotlight/{id}` 的公开 Spotlight。
- 不支持 Story、账号主页、好友内容和登录态。
- 上游旧样本 404，因此新增 Profile 前必须先获得授权新鲜样本。
- 页面返回的 story/video id、content URL 与用户输入 id 必须一致。

建议 Profile 在 canary 完成前保持未登记研究状态。

## 7. 西瓜视频受控会话设计

### 7.1 URL 与入口

首期研究入口：

- `www.ixigua.com/{id}` / `www.ixigua.com/video/{id}`
- `v.ixigua.com/{share-code}`
- `m.toutiao.com/{share-path}`，仅允许最终跳转到批准的西瓜/头条视频详情页

短链最终 host、作品 id 和内容类型必须重新校验。跳到首页、文章、图集或外部域名时终止。

### 7.2 会话

固定 extractor 明确要求 Cookie，即使不一定登录。首期按以下顺序验证：

1. 第一方页面能否建立无账号、请求内临时 Cookie jar。
2. 如果必须由运维提供最小站点 Cookie，则使用 005 的 `operator_managed` Secret、tmpfs 独占副本、单账号低并发和轮换状态机。
3. 普通 API、数据库、日志、WebSocket 和报告中永远不出现 Cookie。
4. 不把登录账号、会员权益或客户端签名作为“公开内容”能力的一部分。

若匿名 bootstrap 无法稳定复现且只能依赖高频手工 Cookie，状态保持 `access_required`，不伪装为已支持。

### 7.3 媒体

- 只接受页面显式公开的完整视频表示。
- 动态视频/音频分离流必须完整合并。
- 不处理文章、图集、直播或付费内容。
- 媒体 URL 短 TTL，下载前必须 re-inspect，不能把 CDN URL 持久化为长期事实。

## 8. 可信插件候选设计

### 8.1 Likee

- 只读取第一方页面明确声明的 canonical 媒体 URL。
- 不采用现有上游通过字符串替换推导“无水印”URL的逻辑。
- 视频 id、作者路径、最终页面和媒体对象必须绑定。
- 用户主页、批量列表和已删除内容不纳入首期。

### 8.2 Threads

- 只处理第一方 post/embed 中恰好一个视频的帖子。
- 图片或多个媒体条目返回 `provider_multi_asset_unsupported`。
- 不把图片和视频拼成一个下载 parts 列表，不把一个 carousel 伪装成单视频。
- Lux 仅作为页面形态参考；新插件独立实现并遵循本仓库许可证。

### 8.3 好看视频

- 旧社区实现只作为历史证据；先用新鲜授权样本确认当前第一方页面 schema。
- 只接受带作品身份的 HTTPS 媒体，不依赖无边界的通用正则。
- 若页面必须依赖客户端私有接口、签名或公共解析站，则保持 unsupported。

### 8.4 Kwai 国际版

- 建立独立 Provider，不与国内 `kuaishou-public-v1` 共用域名和状态。
- 首先确认 `kw.ai`/Kwai 第一方分享链、地域可用性和 canonical 媒体身份。
- 不实现去水印、地域绕过或客户端逆向。
- 某一地域出口无法访问时标记 `access_required/degraded`，不自动轮换匿名代理。

## 9. 错误与状态

| 场景 | 稳定错误 | 重试 |
| --- | --- | --- |
| 图片/carousel/多视频帖子 | `provider_multi_asset_unsupported` | 否 |
| 公开链接过期或已删除 | `provider_link_unavailable` | 否 |
| 需要最小平台会话 | `provider_access_required` | 会话恢复后重试原任务 |
| 会话已失效 | `provider_session_expired` | 轮换后重试原任务 |
| 出口/WAF/平台 challenge | `egress_challenged` | 统一预算内有限重试 |
| 页面 schema 变化 | `extractor_regression` | canary 降级，不在单请求无限重试 |
| 任意实例/不可信后续 URL | `unsafe_media_url` | 否 |
| DRM、private、会员、购买、geo 绕过请求 | 既有权益/DRM 错误 | 否 |

平台状态遵循 005 的 canary 聚合与恢复迟滞。单次 metadata 成功不能把状态设置为 `verified`。

## 10. 完整视频与 AI 链路

```text
Inspection
  → Provider/Profile/AccessContext
  → download 前 re-inspect
  → 完整视频与音频下载/合并
  → ffprobe + SHA-256
  → MinIO 原始视频制品
  → RabbitMQ analysis message（同一 analysis_id）
  → Agent 读取完整视频
  → 分镜/高光/视觉资产报告
  → 数据库持久化
  → MinIO MD/DOCX
  → WebSocket 推送同一 task/analysis 状态
```

分析重试只增加原 `analysis_id` 的 attempt，并复用已经校验的输入制品；只有原视频制品缺失或哈希不一致时才重新下载。重试不会新建业务任务。

## 11. 验收门槛

每个平台或实例必须分别通过：

1. URL 匹配、规范化、重定向收敛、身份一致和格式映射测试。
2. 图片、carousel、过期、private、DRM、geo 和 schema 负例。
3. 新鲜授权样本 metadata canary。
4. 完整文件下载、ffprobe 音视频轨/容器/时长和 SHA-256 验证。
5. download 前 re-inspect 与选中格式稳定性验证。
6. MinIO 视频制品、RabbitMQ、完整视频 Agent、数据库报告、MD/DOCX 和 WebSocket E2E。
7. 原任务重试行为和幂等性验证。
8. Provider 状态页与 API 一致，桌面/移动布局不溢出。
9. 全量本地质量门禁、Compose smoke 与 GitHub Actions 通过。

## 12. 实施顺序

1. 为现有 Profile 建真实完整下载 canary，不新增平台代码。探针控制面已实施；授权目标与真实执行待逐平台配置。
2. 实施批准实例 PeerTube；白名单代码已完成，真实样本证据待配置。
3. 获取 Snapchat 新鲜授权样本并决定是否直接登记上游 extractor。
4. 设计并验证西瓜视频最小会话与短链，不开放普通 API Cookie。
5. 复验 Rumble、Tumblr、Bluesky 的出口和 schema。
6. 按业务需求依次评审 Likee、Threads、好看视频、Kwai 可信插件。
7. 多资产 manifest 上线后再扩展 Instagram carousel、Threads carousel、微博图文和 Pinterest 图片集合。

## 13. Phase 2 实现边界（2026-08-11）

已实现：

- append-only `provider_canary_results` 记录 metadata、media、analysis 三类阶段，以及 Provider、Profile、访问模式、结果、稳定错误码、时延、引擎提交、出口引用和客户端引用；不存储目标 URL、Cookie 或异常文本。
- 新增 `provider-canary` Compose 服务。目标仅从 Secret 类型配置读取，只接受 HTTPS、无 URL credentials、Provider 与域名匹配的显式目标；默认 `[]` 时不访问第三方。
- metadata 默认每 6 小时、media 默认每天执行。media 使用 Runner 的 download 前 re-inspect、完整选中表示下载、ffprobe/SHA-256 合同，完成后清理共享工作区；不是固定抽帧探针。
- `GET /api/providers` 从最近结果动态计算 `degraded/blocked/rate_limited/access_required`。新增 Profile 必须同时具备最近 5 次下载层 4 次成功、最近 2 次连续成功、6 小时内 metadata、26 小时内 media、7 天内 analysis 证明以及 `PROVIDER_VERIFIED_KEYS` 显式批准，才能从 `unknown` 提升。
- 新增 `peertube-approved-instance-v1`；PeerTube 非白名单实例及非单视频路径 fail closed。AcFun、Rutube、VK Clips、Dailymotion 和 NicoNico 的域名统一 fail closed。
- 新增显式 attestation 命令，按 `analysis_job_id` 反查同一条真实链路：成功下载与完整制品、ffprobe 轨道元数据/SHA-256、当前 Agent run、严格分镜/高光结果、数据库当前报告、未过期 MinIO Markdown/DOCX 和 WebSocket 恢复事件。独立 `video-canary` 只读身份对原视频/MD/DOCX 执行 HEAD 与大小校验；加密源 URL 只在进程内解密并与授权 target 精确比对。
- analysis 阶段不能写入定时下载探针配置，防止 metadata 请求被误记为 Agent E2E；只能由 attestation 命令根据持久化事实产生。
- 既有原任务重试继续复用 `analysis_job`，仅追加 `analysis_run`，不创建新的业务任务。

未实现/未验证：

- PeerTube 已完成批准实例 Framatube 的完整 metadata + 下载闭环（`e457a276` succeeded、ffprobe/SHA-256 一致），但 Agent/报告/Canary 证明尚未执行，`peertube` 仍不批准 `verified`。
- Snapchat Spotlight 已完成 metadata、最小完整媒体下载与 ffprobe/SHA-256 验证，`snapchat` 已登记 `verified`；西瓜视频仍需要受控会话；Likee/Threads/好看/Kwai 等可信插件候选仍在研究队列。
- Facebook、Twitch、Pinterest 视频 Pin、微博、优酷和腾讯视频的严格单视频/Clip Profile 已通过当前版本验证；YouTube、Reddit 因访问挑战保持 `access_required`，TikTok 因当前 extractor 网页响应回归保持 `degraded`。登记不等于实时可用，以 `/providers` 或 `GET /api/providers` 为准。
- 因所有范围内平台尚未全部真实通过，017 文档不得归档。只有 API 中要求归档的平台全部为 `verified`、Acceptance 记录授权证据与 CI 提交并显式标记 `accepted` 后，`python -m app.workers.canary.archive --apply` 才会带回滚地把四份文档移动到 `docs/archive/017/` 并更新索引；失败或部分状态一律 fail closed。
## 14. 真实分享链接与多平台会话增强（2026-08-11）

### 14.1 分享 URL 规范化

- PeerTube 的 watch/embed/w 路径同样在实例白名单和路径校验之后删除页面状态参数；任意实例不会因该规范化进入受支持集合。

### 14.2 每 Provider 独立受控会话

API、下载 Worker 和 Canary 使用 `RUNNER_OPERATOR_BASE_URLS` 按 Provider key 路由，不再把所有受控请求发给一个共享会话池。每个 operator Runner 必须同时满足：

1. `RUNNER_OPERATOR_SESSION_VERSIONS` 恰好一个 Provider；
2. Profile 显式声明 `operator_managed`、Cookie 域白名单和并发上限；
3. 账号基线已确认，Runner 最大并发为 1；
4. Secret 只读挂载，操作期间仅在独占 tmpfs 生成 `0600` 副本；
5. access context 的 Provider key 与下载路由一致，不能跨 Provider 复用。

当前 allowlist 包含 YouTube、TikTok、Vimeo、X、Instagram、Facebook 与 Reddit。默认仍只有匿名 Runner；未配置对应 endpoint/Secret 时不会自动获得登录态。Compose 的 `provider-operator` profile 提供一个可配置的额外隔离 Runner，生产可按相同边界部署多个 endpoint。

### 14.3 稳定失败语义

`Account authentication is required`、Vimeo login 和 fresh-cookie 错误归为 `credential_required`，允许路由到已配置的对应 Provider operator Runner。TikTok 当前真实返回的 `Unexpected response from webpage request` 与 rehydration schema 失败归为 `extractor_regression`，不会再伪装成无信息的 `inspection_failed`，也不会在单请求内无限重试。

### 14.4 当前真实能力边界
