# 邮箱身份与持久化基础设施设计

## 1. 背景与目标

现有 Plan 001 以安装令牌和文本 `owner_id` 为边界，不能满足邮箱用户、跨设备会话和持久化资产要求；现有对象存储只停留在通用 S3 Port，尚未冻结 MinIO、对象一致性或恢复方法。

本设计冻结以下基础前置能力：邮箱注册、验证、登录、退出和密码重置；UUID 用户 owner；PostgreSQL 业务真相、Redis 可重建加速层、MinIO 私有对象层、SMTP 投递层；对象 Saga、备份恢复及生产门禁。Plan 001 及后续下载、AI、PDF 必须在本基础 Acceptance 通过后继续。

非目标：社交登录、手机号、MFA、团队/角色、公开分享、永久媒体库、自研密码算法、自研邮件协议、跨数据库分布式事务或替换现有合规来源策略。

## 2. ADR 与技术选型

| ADR | 决策 | 冻结结论 |
| --- | --- | --- |
| `ADR-005-01` | 运行时与业务数据库 | Python 3.13.x、FastAPI `>=0.139.2,<1`、Pydantic `>=2.13.4,<3`；PostgreSQL 17.10、SQLAlchemy `>=2.0.51,<2.1`、Alembic `>=1.18.5,<2`、psycopg `>=3.3.4,<4`；PostgreSQL 是唯一业务真相 |
| `ADR-005-02` | 身份实现 | FastAPI Users 15.0.5 + SQLAlchemy Adapter 7.0.0 + DatabaseStrategy + CookieTransport；密码用 pwdlib 0.3/Argon2id，邮箱用 email-validator 2.3 |
| `ADR-005-03` | 异步与实时 | Redis Open Source 8.2.7（本项目选择 AGPLv3 许可路径）+ redis-py `>=6.4,<7` + Celery `>=5.6.3,<6`；Redis 丢失不得丢业务事实 |
| `ADR-005-04` | 对象存储 | MinIO S3-compatible Server + MinIO Python SDK 7.2.20，经 `ObjectStorage` Port 隔离；禁止业务层导入 SDK |
| `ADR-005-05` | 邮件与 CSRF | PostgreSQL mail outbox + Celery mail queue + aiosmtplib 5.1.2 + Jinja2 3.1.6；签名 double-submit 使用 fastapi-csrf-protect 1.0.7；SMTP/CSRF 库都不是状态真相 |
| `ADR-005-06` | 用户主键 | 沿用 FastAPI Users UUID mixin 的应用侧 UUID4；PostgreSQL 以 `UUID PRIMARY KEY` 和同型非空 FK 强制完整性，不自定义第二套 ID 生成器 |
| `ADR-005-07` | 跨存储一致性 | PostgreSQL 事务 + outbox + 幂等对象 Saga；不伪造 PostgreSQL/MinIO 原子事务 |
| `ADR-005-08` | 恢复 | pgBackRest + WAL/PITR；MinIO 版本化与异故障域副本；Redis 从 PostgreSQL/outbox 重建 |
| `ADR-005-09` | 邮件 token 加密 | cryptography `>=49.0,<50` 的 AES-256-GCM；96-bit 随机 nonce、版本化 AAD/key ID 和外部注入 keyring；不自研密码算法或可变 envelope |

FastAPI Users 已进入维护模式，但继续提供安全和依赖维护，且覆盖 UUID、SQLAlchemy、注册、验证、重置、Cookie 与数据库会话。MVP 接受其稳定性，封装在 `IdentityProvider` Port 后；每季度复核安全公告及继任工具，业务模型和 HTTP 契约不得依赖其内部类型。

FastAPI 请求使用 SQLAlchemy `AsyncSession`，Celery worker 与需要显式事务锁的命令继续使用同步 Engine；两者统一使用 psycopg 3，不再引入 asyncpg。`pyproject.toml` 保存上述受控范围，`uv.lock` 固定实际版本，生产禁止运行时自动升级。fastapi-csrf-protect 只在 Python 3.13、FastAPI/Starlette 当前锁版集成测试通过后启用；项目使用其 header-only 严格模式，不启用 flexible/body token。每个 unsafe route 通过共享 FastAPI dependency 显式调用库校验，路由清单测试拒绝任何漏挂；若不兼容，Plan 必须退回 review 重新选择成熟 Adapter，不能现场自研 CSRF 协议。

## 3. 数据职责与不变量

| 组件 | 保存内容 | 明确禁止 |
| --- | --- | --- |
| PostgreSQL | 用户、会话、验证/重置 delivery intent 与审计、mail/job outbox、Job/Event、Source/Format、资产元数据、AI 文档、删除状态 | 把大视频、音频、PDF 二进制塞入行；依赖 Redis/MinIO 推断业务状态 |
| Redis | Celery broker、SSE wake、短 TTL 缓存、登录/邮件限流、分布式短租约 | 用户、会话、Job 终态、对象元数据或 AI 结果的唯一副本 |
| MinIO | 视频、音频、上传、转写文件、思维导图 SVG、PDF 等二进制对象 | 用户邮箱、源 URL、标题、owner 或业务状态作为 key/metadata |
| SMTP | 发送验证、重置和安全通知 | 保存用户状态、生成授权结论或决定 outbox 是否成功 |

Redis 使用 AOF `everysec` + RDB 和 `noeviction`，所有非 broker key 必须有 TTL；该持久化只缩短恢复时间，不提升为业务备份。Celery 消息只传 UUID/opaque ID。broker 被清空后，reconciler 扫描 PostgreSQL 中无有效 worker lease 的非终态 Job，并用新 delivery attempt 重新武装 outbox；worker 幂等收敛重复消息。

## 4. 邮箱身份与 HTTP 契约

`users` 至少包含 `id UUID`、FastAPI Users Adapter 兼容的唯一 `email`、`hashed_password`、`is_active`、`is_verified` 与 UTC 时点。`email-validator` 只做语法与规范化，`check_deliverability=false`；规范化后按产品 case-insensitive policy 写入唯一 `email`，不做 Gmail dot/plus 等供应商折叠，地址真实性只由验证邮件证明。密码为 12–128 字符，交给 pwdlib Argon2id 哈希和自动升级，任何日志不得记录邮箱全文、密码、Cookie 或 token。

端点冻结为：`GET /api/v1/auth/csrf`、`POST /api/v1/auth/register`、`POST /api/v1/auth/verification/request`、`POST /api/v1/auth/verify`、`POST /api/v1/auth/login`、`POST /api/v1/auth/logout`、`POST /api/v1/auth/password/forgot`、`POST /api/v1/auth/password/reset`、`GET /api/v1/users/me`。CSRF bootstrap 返回 200 `{csrf_token}`、`Cache-Control: no-store` 与配对 Cookie，不读取或泄露账户状态；register/request/forgot 返回相同 202 防枚举；verify/login/logout/reset 成功为 204，me 为 200。未验证邮箱不得登录。

所有 POST 只接受 `application/json`，204 无响应正文；FastAPI Users 默认 OAuth2 form wire 不对外暴露。请求/成功/业务错误冻结如下，表外共同错误为 CSRF 403 `REQUEST_CSRF_REJECTED`、Origin/Host/Fetch Metadata 403 `REQUEST_ORIGIN_REJECTED`、content type 415 `CONTENT_TYPE_UNSUPPORTED`、限流 429 `AUTH_RATE_LIMITED` 和保护层不可用 503 `AUTH_PROTECTION_UNAVAILABLE`：

| API | JSON 请求 | 成功正文 | 特有错误 |
| --- | --- | --- | --- |
| `GET /auth/csrf` | 无 | `{"csrf_token":"<raw>"}` | 无；secret 缺失时应用拒绝启动 |
| `POST /auth/register` | `email,password,locale` | 202 `{"status":"accepted"}` | 422 `AUTH_EMAIL_INVALID/AUTH_PASSWORD_INVALID` |
| `POST /auth/verification/request` | `email,locale` | 同形 202 | 422 `AUTH_EMAIL_INVALID` |
| `POST /auth/verify` | `token` | 204 | 400 `AUTH_TOKEN_INVALID` |
| `POST /auth/login` | `email,password` | 204 + session Cookie | 401 `AUTH_INVALID_CREDENTIALS`；403 `AUTH_EMAIL_NOT_VERIFIED` |
| `POST /auth/logout` | 空 JSON object | 幂等 204 + clear session/CSRF Cookie | 无 |
| `POST /auth/password/forgot` | `email,locale` | 同形 202 | 422 `AUTH_EMAIL_INVALID` |
| `POST /auth/password/reset` | `token,new_password` | 204 + revoke sessions + clear Cookie | 400 `AUTH_TOKEN_INVALID`；422 `AUTH_PASSWORD_INVALID` |
| `GET /users/me` | 无 | `{"id":"<uuid>","email":"<normalized>","is_verified":true}` | 401 `AUTHENTICATION_REQUIRED/AUTH_SESSION_EXPIRED` |

`locale` 只接受受支持的 BCP 47 catalog key；unknown 为 406 `LOCALE_UNSUPPORTED`。generic 202 的状态、content type、schema 和账户相关 header 完全一致，投递错误只进入 operator health。每个 endpoint 的 Pydantic request/response/Problem schema必须进入 OpenAPI，未知字段拒绝，密码永不回显。

浏览器会话使用 PostgreSQL DatabaseStrategy 的随机 opaque token，7 天绝对到期；退出、禁用用户或密码重置撤销相关会话。生产 Cookie 为 `__Host-video_session`，固定 `Secure; HttpOnly; SameSite=Lax; Path=/` 且无 Domain。fastapi-csrf-protect 生成 40 字符 raw token 与带时间戳签名的配对 Cookie：raw token 只在 bootstrap JSON 和 Web 内存中，生产 `__Host-video_csrf` 固定 `Secure; HttpOnly; SameSite=Lax; Path=/`、无 Domain、`Max-Age=3600`；unsafe route 从 `X-CSRF-Token` 读取 raw token 并由库验证签名配对与 1 小时有效期，再检查 exact Host/Origin 与 Fetch Metadata。exact Host 只与启动时必填的 `TRUSTED_API_AUTHORITY` 比较；该值来自受审部署配置，必须是单一 `host[:port]`，不能从 Host/Forwarded/X-Forwarded 请求头推导，重复或不规范 Host 直接拒绝。该开源库不提供数据库会话绑定，本项目不得作此声明；登录、注销、密码重置和会话轮换清除旧配对值，下一次 mutation 前必须重新 bootstrap，旧 header 与缺失、过期或轮换后的 Cookie 配对失败。只有显式 loopback development profile 可把两种 Cookie 改为 `video_session_dev`/`video_csrf_dev` 且非 Secure；该 profile 在非 loopback 绑定时拒绝启动。

canonical error code 还包括 `REQUEST_CSRF_REJECTED`、`CONTENT_TYPE_UNSUPPORTED`、`AUTH_PROTECTION_UNAVAILABLE`、`LOCALE_UNSUPPORTED` 和仅供 operator health 使用的 `EMAIL_DELIVERY_UNAVAILABLE`。外部 detail 不泄露邮箱是否存在；Redis 限流不可用时，登录、注册、验证请求和忘记密码 fail closed 为可重试 503，已有会话只读认证仍以 PostgreSQL 为准。

## 5. Mail outbox

`auth_mail_intents` 保存 `id UUID`、`user_id`、`purpose`、递增 `generation`、状态、token digest/有效期与时点；不保存明文 token，唯一键为 `(user_id,purpose,generation)`。token 由 FastAPI Users CSPRNG/JWT 产生并具有高熵，digest 固定为原始 token UTF-8 bytes 的 SHA-256 lowercase hex，不复用 AES key 或另建隐式 HMAC key。状态为 `PENDING → ENQUEUED → CONSUMED`，新 generation 会把旧的未消费 generation 标为 `SUPERSEDED`。重发验证与忘记密码对命中的用户先提交 intent，再在显式 intent 上下文调用 FastAPI Users 生成 token；项目 callback 在单一 PostgreSQL 事务中锁定 current intent、写唯一 `mail_outbox`、保存 digest 并置 `ENQUEUED`。事务提交前崩溃不会留下 outbox 或状态，提交后两者必然同时可见；reconciler 在 1 分钟内锁定仍为 PENDING 的同一 intent、重新生成 token 并执行同一原子命令，不依赖用户是否已验证来猜测请求。

FastAPI Users SQLAlchemy Adapter 的注册流程先提交用户事务，再执行 post-commit callback，因此初次用户提交与 verification intent 之间仍存在不可伪装成原子的间隙；周期 scanner 只对“未验证用户且无有效验证 generation”补建 intent。除此之外，项目拥有的 intent/outbox 写入不允许部分提交。项目不挂载库默认 verify/reset router：facade 复用 FastAPI Users 的 JWT codec、UUID parser、密码校验与 pwdlib hasher，先验证 current 非 superseded digest/claims，再调用项目 PostgreSQL command。verify command 在一项事务中锁用户和 intent、置 `is_verified=true`、消费 generation 并写审计；reset command 在一项事务中锁用户和 intent、写新 Argon2id hash、删除该用户全部 DatabaseStrategy token、消费 generation 并写审计。commit 前崩溃全部回滚，commit 后四类事实全部可见；不把 session revoke 或 intent consume 放在 post-commit hook。不存在邮箱不创建 intent，但通过限流、统一 envelope 和有界响应时间类别保持 generic 202。

`mail_outbox` 只含 intent/用户 UUID、模板 ID、locale、去重键、`token_format/key_id/nonce/ciphertext`、状态、attempt 和时点。token format v1 固定 cryptography AES-256-GCM、每行 CSPRNG 96-bit nonce；exact AAD framing 依次包含 `video-server:mail-token:v1`、`token_format`、`key_id`、intent UUID、purpose、generation 与 UTC expiry，每段使用长度前缀 UTF-8 bytes。`MAIL_TOKEN_ACTIVE_KEY_ID` 与 `MAIL_TOKEN_KEYS` 由 secret manager/环境注入，key ID 唯一且每把 key 解码后恰为 32 bytes；缺失 active key、未知 key ID、重复 key material 或错误长度时启动/解密 fail closed。新写入只用 active key，旧 key 仅保留解密；轮换先加入新 key 并切 active，再在事务中重加密仍需投递的引用行。dispatcher 向 Celery 只发送 `mail_id`；worker 读取 current 用户地址，经 STARTTLS/TLS SMTP 发送，成功后在同一 CAS 中置 `SENT` 并把 format/key ID/nonce/ciphertext 全部清空。`SUPERSEDED` 立即 crypto-shred；`DEAD_LETTER` 和其他未投递 token 最迟在 expiry 清空，清理后不得人工重放旧 token。数据库约束拒绝部分 material；只有引用计数为零的旧 key 才能从配置移除。可恢复错误指数退避，最多 10 次；永久失败进入 `DEAD_LETTER` 并告警，不回滚已创建用户。模板禁止远程资源和任意 HTML，验证 token 1 小时、重置 token 30 分钟且一次成功或新 generation 后失效。

验证与重置链接只从启动时必填的 exact `PUBLIC_WEB_ORIGIN` 构造。production 只接受无 path/query/fragment 的 HTTPS origin；development 只额外接受 loopback HTTP。链接固定为 `{origin}/verify-email#token={percent-encoded-token}` 与 `{origin}/reset-password#token={percent-encoded-token}`，不得读取请求 `Host`、`Forwarded`、`X-Forwarded-*` 或 Origin 拼接；hostile-header 测试必须证明邮件链接不变，防止 reset-link poisoning。

## 6. MinIO 对象 Saga

对象 key 使用随机 opaque UUID 分片，不含 owner、文件名、邮箱或 Source。bucket 默认私有，服务账号最小权限，TLS + 服务端加密，禁止 public ACL；API 只签发最长 15 分钟的 GET/PUT URL，绝不返回内部 key。

状态机为 `PENDING → UPLOADING → READY → DELETING → DELETED`，上传失败可进入 `FAILED` 后按幂等键重试：

1. PostgreSQL 原子创建 `media_assets(PENDING)`、Job event 与 outbox。
2. worker 以 asset UUID/attempt fencing claim，multipart 上传并流式计算 SHA-256。
3. complete 后执行 HEAD，核对 object version、size、content type 与 SHA-256；只有同一 PostgreSQL 事务可置 `READY` 并追加事件。
4. 崩溃或超时保留可重试事实；sweeper abort 过期 multipart，并删除无 READY 引用的孤儿对象。
5. 删除先置 `DELETING` 并发 outbox；worker 删除全部版本/副本并确认不可读后置 `DELETED`。已有 presigned URL 因对象删除失效。

MinIO 不可用时不创建虚假 READY；PostgreSQL 在上传完成前不可用会产生孤儿但不丢业务记录，reconciler 按 asset ID 与对象 inventory 收敛。任何 checksum/version 不一致进入 `FAILED` 和安全错误，不自动信任对象。

## 7. 备份、恢复与持久化目标

- PostgreSQL：pgBackRest 每周 full、每日 differential、连续 WAL 归档到独立加密故障域，保留 30 天；系统默认生产目标 RPO ≤5 分钟、RTO ≤2 小时。
- MinIO：生产门禁关闭后使用 bucket versioning + 独立集群单向复制，源/目标版本匹配，并纳入同一 RPO ≤5 分钟、RTO ≤2 小时目标。活跃对象删除必须复制 delete，并清除全部版本；离线加密备份最多 30 天滚动淘汰。
- Redis：AOF/RDB 放持久卷，但无业务 RPO 承诺；清空后 15 分钟内从 PostgreSQL/outbox 恢复可处理队列和 SSE，缓存/限流自然重建。
- SMTP：无状态恢复；PostgreSQL mail outbox 驱动重投。恢复演练必须使用隔离目标，先校验 PG FK/outbox，再校验 MinIO HEAD/SHA-256，最后开放 API。

生命周期固定为：原始媒体创建后最多 24 小时；用户未显式保存的结果最多 7 天；用户显式保存的输出保留至用户删除。恢复不得把 `DELETED` 或已到期资产重新暴露为 READY；备份中的已删除数据仅在加密隔离域保留并在删除后最长 30 天淘汰，不能直接挂载为服务存储。开发 compose 使用命名卷，但命名卷不算备份或 Acceptance 证据。

## 8. 迁移、回滚与失败路径

基础 migration 先创建 UUID users/session/mail/asset 表，再把所有 owner FK 改为 UUID。当前文本 installation owner 无可靠邮箱映射：空库可升级；发现任何非测试 owner 数据时 migration 必须以命名 preflight fail closed，要求显式导出/用户映射，不生成占位用户。迁移完成后禁止无 FK 的 owner、安装 token 和双身份兼容路径。

数据库 schema 回滚只允许尚无新用户/资产数据时降级；已有新数据时回滚应用版本而不降 schema。MinIO/SMTP/Redis 故障均保持 PostgreSQL 中可恢复状态并有稳定错误码；秘密缺失、bucket public、Redis eviction policy 错误、WAL/replication 落后或 MinIO 版本未批准时生产健康检查失败。

## 9. MinIO 归档风险与生产门禁

MinIO 官方仓库于 2026-04-25 被归档并只读。MVP 仍按用户要求选择 MinIO；`RELEASE.2025-09-07` 缺少后续官方安全修复，明确禁止继续使用。开发/CI 只能从官方 `RELEASE.2025-10-15T17-29-55Z`、commit `9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a` 的干净 source tree 构建内部镜像；MinIO 切片开始前必须冻结构建定义、base digest、自产 image digest、provenance、SBOM 与 CVE 结果，禁止 `latest` 或第三方镜像。该 source build 只关闭开发 artifact 门禁，不构成生产批准，也不得私自长期 fork 修补形成无人负责的发行版。

生产启用前必须完成三选一决策：采用受支持的 AIStor/维护发行版并完成产品与许可证批准；由负责人书面接受归档 OSS MinIO 的 AGPL、漏洞响应与升级风险并批准精确 digest；或由用户放宽 MinIO 限定后重新评审维护中的 S3-compatible 实现。当前三者均未完成，因此 `AC-OBJ-001`/`AC-DR-001` 的生产部分固定为 `blocked`，不以本地上传成功替代生产结论。
