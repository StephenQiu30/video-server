- 状态：评审结论与修复路线；不替代代码验收

## 1. 评审结论

当前实现是**成熟度远高于同类项目的架构**：声明式 Provider Catalog + 策略注册表 + 插件继承式 extractor + 物理隔离 Runner + HMAC 认证 + 纵深 URL 准入 + 进程组隔离 + 每插件测试 + 架构边界测试，且设计文档本身就是威胁建模，实现与意图高度一致。

结论分三层：

- **架构设计：优秀**，无需重构。
- **可维护性：高，但 session/cookie 子系统存在明显重复**（同一逻辑复制 3 份），这是投入最小、收益最直接的清理点。
- **高可用性：骨架扎实，但有 4 个真实缺口**——多数已在 `005` 的「仍待生产验收」中被诚实标注；另有若干本次评审新发现的错误语义与防护盲区。

下文每条标注**验证状态**，区分「本次已直接读码核验」与「子代理报告、实施前需复核」。行号为评审当日快照，实施时以当前代码为准。

## 2. 已核验的可靠性问题（按优先级）

### P1

1. **消息级重试恰好一次，恢复依赖外部 DLX 绑定** — `download/consumer.py:46,51`
   `process_delivery` 对执行异常 `nack(requeue=not bool(message.redelivered))`：首次投递 requeue，第二次投递失败即 `requeue=False`。消费者以 `declare_queue(..., passive=True)`（`consumer.py:109-111`）被动绑定，队列的 `x-dead-letter` 参数声明在拓扑定义里、不在消费者内。**结论**：下载任务的二次失败会 dead-letter 到 DLQ，`app/workers/dlq/` 提供审计重放；但「恰好重试一次」本身没有跨投递计数，且队列是否真的绑定了 DLX、`dlq` 重放与 `sweeper` 的三层恢复（`download/sweeper.py`：queued/lease/retry）是否重复计数不可见。**建议**：确认下载队列 DLX 绑定存在；并把「重试预算」集中到一处可观测的状态（见 §6.2）。

2. **孤儿 workspace 目录无文件系统回收** — `download/sweeper.py`
   sweeper 只做 DB 三层恢复（`recover_stale_queued` / `reclaim_stale` / `release_ready_retries`），**没有任何 `runner_workspace_root` 的文件系统扫描**；`{task_id}-*` 目录只在 handler 显式调用 `SharedWorkspaceCleaner` 时清理。Runner 进程被 SIGKILL/硬崩溃时会遗留目录 → 磁盘泄漏。**建议**：sweeper 增加年龄基 GC（见 §6.4）。

3. **`is_ready()` 只探测第一个 provider** — `runner/provider_sessions.py:67-72`
   `provider, version = next(iter(self._versions.items()))` 只取第一个平台。当前由 `settings.py` 强制「operator runner 恰好一个 provider + `max_active_tasks=1`」兜底，影响有限；一旦放开多 provider 会漏报会话失效。同函数 `:70` 的 `assert self._cookie_sync is not None` 在 operator 未配 cookie 源时抛 `AssertionError`（500）而非受控 4xx。

### P2

4. **校验失败状态码语义错位** — `runner/verification.py`
   无视频流、宽高/码族/时长超限全部抛 `media_validation_failed` 且一律 `status=502`（`:38,44,48,51,75,77,82,86,88,91,94,99,104,106`）。时长超 `max_duration` 是内容/策略拒绝，应为 4xx；与 `gallery.py:86` 用 422 表达同类「产物非法」不一致，导致 5xx（基础设施）与 4xx（内容）在同一错误码下混淆，污染监控与重试判定。**建议**：产物非法统一 4xx，基础设施失败保留 5xx。

5. **canary 错误码有损折叠** — `canary/service.py:74,308`
   `_RUNNER_ERROR_ALIASES` 把 `egress_challenged` / `pot_*` 压成 `media_validation_failed`，`service.py:308` 又以 `.get(exc.code, "runner_failed")` 兜底。结果「风控验证码 / POT 服务挂 / 凭证过期」三类根因在 canary 证据里不可区分。**建议**：删除折叠，保留 `provider_errors.py` 的细粒度稳定错误码。

6. **冷却无退避/滞回、原因硬编码** — `repositories/providers/route_cooldowns.py:126-173`
   `block()` 的 `reason_code="provider_rate_limited"` 硬编码（`:130`），`finish()` 不写 reason；失败冷却固定 `now + DEFAULT_COOLDOWN`（`:170`）无 jitter/指数退避，恢复后无滞回 → 存在「冷却→探测成功→解禁→再失败→再冷却」抖动。**建议**：冷却加指数退避 + jitter + 连续 N 次成功才清零滞回，并把 `reason_code` 与稳定错误码落库。

7. **状态证据只投影成功** — `repositories/providers/status_evidence.py:169`
   下载证据 SQL 只取 `DownloadJobRow.status == "succeeded"`。这符合「成功才算正向可用证据」的基线设计（见 `media-source-strategy.md`），但意味着平台开始回归时「最近下载」信号不会立刻恶化，只能等 canary 兜底。**建议**：状态视图补充「近期失败 + 稳定错误码」的负向信号，用 `context_generation_id` 过滤噪声（见 §6.5）。

## 3. 可维护性债务（本次核验计数）

session/cookie 子系统过度切分 + 复制粘贴，安全敏感逻辑重复实现已开始漂移：

| 重复逻辑 | 已核验位置 |
| --- | --- |
| `_no_follow()` 3 份定义 | `provider_cookie_sync.py:275`、`provider_session_files.py:116`、`provider_cookie_queue.py:237`（另有 `chrome_provider_cookies.py` 等内联 `O_NOFOLLOW`） |
| 原子写 `_atomic_write_*` 3 份 | `provider_cookie_agent.py:192`(plist)、`:305`(response)、`provider_session_maintainer.py:370`(json) |
| Cookie 域 allowlist 匹配 2 份 + host 匹配 | `provider_cookie_export.py:67`、`provider_session_files.py:108`（`provider_registry.py:169,181` 为 URL host 匹配，属另一职责） |
| Netscape Cookie 解析/校验拆分 | `provider_cookie_export`（写）、`provider_cookie_file`（读+过期过滤+`\x00` 检查）、`provider_session_files._validate_netscape_cookie`（仅校验）——规则已不一致 |

**安全敏感风险**：`provider_session_maintainer.py:89,273` 把 Cookie 的**未加盐 sha256** 写进 `state.json`，与 `provider_sessions.py:158` 刻意用 HMAC 避免「无盐凭证哈希」的做法不一致。此类权限校验/symlink 防护重复逻辑一旦某处漏改即是安全洞，是清理的正当理由。

## 4. 评审发现、实施前需复核

以下来自子代理报告，本次未逐一读全文件，行号/定性需在实施前复核：

- **canary scheduler DB 写入保护不完整**：`canary/scheduler.py:78-83` 的 `run()` 仅 `except TimeoutError`；`run_due()` 的 try/except 只包住 `context_for`。`service.execute()` 内的 `repository.save()` 是否在保护范围内需复核——DB 瞬时故障可能冒泡杀死 canary worker。
- **`classify_provider_failure` 覆盖不全**：`runner/commands.py:87,421` 仅在 `failure_context is not None` 时分类；probe/remux/public_asset 是否以 `failure_context=None` 构造命令需复核，若是则这些阶段的 provider 限流/封禁退化为通用 502。
- **首次探测冷却竞态**：`route_cooldowns.py:56-61` `acquire_route` 对不存在 route 返回 `version=None` 不建行，而 `finish()` 遇 `row is None` 抛错；是否成立取决于 `provider_route_admission` 是否先 `block()` 建行，需复核。
- **Cookie 队列 ack 超时不匹配**：`provider_cookie_queue.py:26` ack 超时 1.0s vs `provider_cookie_sync.py:31` 客户端总超时 20s，可能产生虚假 503。
- **浏览器会话失效检测**：`provider_sessions.py` 浏览器来源路径 `credential_version_id` 静态 `"browser"`，每次操作重取是正确语义，但需确认「Cookie 轮换失败」能被 `provider_errors.py` 归为 `credential_expired` 而非 `provider_link_unavailable`。

## 5. 已声明的设计缺口（非本次新发现）

以下在 `005`「仍待生产验收」中已诚实标注，仍是当前高可用上限，本次评审确认其仍成立：

1. **跨副本分布式租约未实现**——operator runner 靠 `RUNNER_MAX_ACTIVE_TASKS=1` + 单进程 `Semaphore(1)` + 单 provider 约束并发；**单副本内是安全的**，但意味着 operator 会话是单点 + 串行吞吐，无法水平扩展。注意：这不是单进程 semaphore 的 bug，是「多副本无协调」的缺口。
2. **429 `Retry-After` / 跨层总预算 / POT 刷新 / 出口 cooldown 未实现**——yt-dlp 内重试、runner、worker requeue、canary 四层可能重试相乘。
3. **账号权益漂移自动停用未实现**——有 inspect 时 fail-closed 的权益防火墙兜底，但缺「漂移即停用 credential version」的安全网。
4. **Phase 2 用户 Credential Broker/Vault 与 gallery-dl 未实现**。
5. **跨 Provider redirect 后的重新 admission/context 未完成**——Generic 仍依赖 yt-dlp 内部重定向。

## 6. 修复方案与优先级

按投入产出排序。① 投入最小、收益最直接，建议先做；①② 可在同一批改动落地。

### 6.1 阶段一：抽共享安全模块，消灭重复（可维护性，先行）

把 session/cookie 子系统的安全敏感逻辑收敛为两个内聚模块：

- `_secure_file`：`O_NOFOLLOW` 打开、原子写（`os.replace`+fsync）、私有目录 fstat 校验、`_no_follow`。
- `netscape_cookie`：解析/序列化/校验**唯一实现**，统一过期过滤、`\x00` 检查、域名 allowlist 匹配。

顺带把 `provider_session_maintainer.py:89,273` 的未加盐 sha256 换成与 `provider_sessions.py:158` 一致的 HMAC。把 `provider_cookie_*` / `provider_session_*` 10+ 个文件按职责收敛为少数文件。

**验收**：`grep` 确认 `def _no_follow`、`def _atomic_write_*`、allowlist 匹配各只剩一处；`provider_session_maintainer` 不再写未加盐 sha256；既有 runner 测试（每插件 + 架构边界）全绿；`ruff`/`mypy`/`pytest` 通过。

### 6.2 阶段二：收敛错误语义与重试/冷却状态（P1/P2 正确性）

1. **统一错误分层**：`verification`/`gallery`/`collection` 的「产物非法」统一 4xx，基础设施失败保留 5xx；`classify_provider_failure` 覆盖 probe/remux/public_asset（补传 `failure_context`）。
2. **跨层冷却预算**：以 `(provider, egress_affinity, error_class)` 为 key 的单一冷却状态横跨 yt-dlp 内重试/runner/worker/canary；遵守 `Retry-After`；冷却加指数退避 + jitter + 滞回（连续 N 次成功才清零）；`block()`/`finish()` 落库 `reason_code` + 稳定错误码。
3. **删除 canary 有损折叠**：去掉 `_RUNNER_ERROR_ALIASES`，`canary_internal_error` 只用于探测代码自身 bug，不落为平台失败证据。
4. **确认下载队列 DLX**：核实 `download` 队列绑定 DLX 且 `dlq` 重放与 sweeper 不重复计数；若未绑定则补上。

**验收**：同一错误码在「平台失败」与「产物非法」间不再混淆；canary 证据可区分验证码/POT/凭证三类根因；冷却状态可追溯原因；消息二次失败进入 DLQ 而非静默丢失。

### 6.3 阶段三：分布式凭证租约协调器（最高优先的 HA 改进）

用 Redis `SET NX + TTL + 心跳续租` 实现跨副本凭证租约，替代「单副本 + 并发 1」：

- 每个 operator runner 领取 `{provider}:{credential_version}` 租约后才执行下载，过期自动释放。
- 同一 provider 跑多 runner 副本做热备，靠租约保证「同一凭证同一时刻只有一人用」。
- 若短期接受单点，则在文档里把「operator 会话 = 单副本 SPOF」写成显式决策并加监控告警。

**验收**：两个 operator runner 副本并发请求同一凭证时只有一个能拿到租约；租约持有者崩溃后租约到期被另一副本接管。

### 6.4 阶段四：文件系统孤儿回收 + 会话失效检测补全

- sweeper 增加 `runner_workspace_root` 的年龄基 GC：扫描 `{task_id}-*` 目录，超过阈值（如 24h）且无对应活跃任务则回收；让「重试不需重下载」的 info_json 复用有明确生命周期。
- `is_ready()` 改为按 provider 校验而非 `next(iter(...))`；operator 未配 cookie 源的 `assert` 改为受控 4xx。
- 确认浏览器会话的 `credential_expired` 与 `provider_link_unavailable` 分类不混淆。

### 6.5 阶段五：状态证据对称 + 权益漂移停用

- `status_evidence` 纳入真实下载**失败**证据（带稳定错误码 + `context_generation_id` 过滤），让平台回归秒级可见，同时不把用户侧个别链接失效误判为平台故障。
- 落实 `005` 的「权益漂移自动停用」：inspect attestation 检测到账号权益与基线不一致即 disable 对应 `credential_version`。

## 7. 非目标（维持既有边界）

- 不重构 Provider Catalog / Strategy Registry / extractor 插件继承体系——它们是对的。
- 不在本编号中开放任意 yt-dlp/gallery-dl 参数、多用户凭据上传或自动化登录。
- 不把「单副本 operator 会话」在实现分布式租约前当作已解决。
