# 15-中心化单服务运行时修复计划

## 目标

将 video-server 从 API/Worker 双业务入口收敛为一个中心化后端应用服务，保持 Redis/RQ 内部队列与 MinIO/S3 统一交付。

## 背景

当前 Dockerfile、Compose、启动脚本和代码入口仍强化 `api` 与 `worker` 两个业务入口。对个人自部署场景，这导致：

- 需要管理两个容器生命周期
- 两次镜像构建
- 两套健康检查
- 无法在单进程内保证队列消费者与 API 同生命周期

## 变更范围

### 核心变更

| 文件 | 变更内容 |
|------|---------|
| `apps/api/app/runtime.py` | 新建，中心化入口 |
| `Dockerfile` | 合并为单 target `app` |
| `docker-compose.yml` | 合并为单 service `app` |
| `docker-compose.prod.yml` | 合并为单 service `app` |
| `scripts/start.sh` | 移除独立 worker 模式 |
| `apps/api/app/routers/health.py` | 增加 `queue_consumer` 检查 |

## 非目标

- 不移除 Redis/RQ
- 不改为 API 同步执行下载
- 不引入 Kubernetes 多副本调度
- 不改造前端页面
- 不在 API/DB 中暴露本地临时路径

## 验收标准

1. Dockerfile 只有一个业务 target：`app`
2. Compose 中只有一个业务 service：`app`，基础设施服务保留 `postgres`、`redis`、`minio`
3. `python -m app.runtime` 能同时启动 API 和队列消费者
4. 任务创建后进入 Redis/RQ，并由同一 `app` 容器内消费者处理
5. 成功任务产物上传 MinIO/S3，API 只返回对象存储读取链接
6. `/ready` 端点检查 `queue_consumer` 状态

## 手动验证

1. Docker 一键启动
2. 访问 `/health` 和 `/ready`
3. 提交公开视频分享链接创建下载任务
4. 确认任务由同一个 `app` 容器内消费者处理
5. 确认产物上传 MinIO
6. 通过下载链接读取对象
7. 确认任务响应不包含本地路径
