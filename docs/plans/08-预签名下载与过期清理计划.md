# PLAN08 预签名下载与过期清理

## 1. 背景

用户最终感知的是"能不能下载到结果"。下载交付和过期行为必须清楚且可预测：成功任务返回短期有效的预签名链接，过期后保留任务历史但不再提供有效下载地址。

## 2. 目标

1. 通过 API 动态签发短期有效的 MinIO 预签名下载链接。
2. 产物过期后自动清理 MinIO 对象，更新数据库状态，保留任务历史记录。
3. 对不可下载的任务返回明确错误语义。

## 3. 非目标

- 不做公开分享链接或跨用户共享。
- 不做下载链接续期或延期。

## 4. 核心内容

### 4.1 下载链接接口

接口定义：

```text
GET /api/tasks/{task_id}/download-link
```

响应：

```json
{
  "url": "http://localhost:9000/video-downloads/users/1/tasks/{task_id}/{filename}?X-Amz-...",
  "expires_in_seconds": 900
}
```

调用链：

```text
get_download_link (routers/tasks.py)
  → cleanup_expired_task_outputs(db)   # 先触发过期清理
  → get_owned_task(db, user, task_id)  # 校验任务归属
  → _assert_downloadable(task)         # 校验可下载性
  → ObjectStorage().presign_download_url(task.object_key)  # 签发预签名 URL
  → DownloadLinkResponse(url, expires_in_seconds)
```

### 4.2 预签名链接逻辑

`ObjectStorage.presign_download_url` 实现：

1. 使用 `boto3` 的 `generate_presigned_url("get_object", ...)` 方法。
2. 使用 `s3_public_endpoint_url`（而非内部 `s3_endpoint_url`）作为客户端访问地址。
3. TTL 由 `presigned_url_ttl_seconds` 配置控制，默认 900 秒（15 分钟）。
4. 签名使用 `s3_access_key_id` 和 `s3_secret_access_key`。

配置项：

| 配置项 | 环境变量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `presigned_url_ttl_seconds` | `PRESIGNED_URL_TTL_SECONDS` | `900` | 预签名链接有效期（秒） |
| `s3_public_endpoint_url` | `S3_PUBLIC_ENDPOINT_URL` | `http://localhost:9000` | 客户端访问 MinIO 的地址 |

### 4.3 可下载性校验

`_assert_downloadable(task)` 校验逻辑（按顺序）：

1. 任务状态必须为 `succeeded`，否则返回 `invalid_state`（409）。
2. `object_key` 不能为 `None`，否则返回 `retention_expired`（410）。
3. `expires_at` 不能早于当前时间，否则返回 `retention_expired`（410）。

### 4.4 过期清理机制

`cleanup_expired_task_outputs(db)` 实现逻辑：

1. 查询条件：`state == succeeded AND object_key IS NOT NULL AND expires_at IS NOT NULL AND expires_at <= now`。
2. 遍历过期任务：
   - 调用 `ObjectStorage().delete_object(task.object_key)` 删除 MinIO 对象。
   - 将 `task.object_key` 置为 `None`。
   - 设置 `task.failure_code = "retention_expired"`。
   - 设置 `task.failure_reason = "文件保留时间已过期并已清理，历史记录仍保留"`。
   - 写入任务事件：`"过期文件已清理，历史记录已保留"`。
3. 批量提交数据库变更。

触发时机：

1. `GET /api/tasks`（任务列表）— 每次请求触发。
2. `GET /api/tasks/{task_id}/download-link`（下载链接）— 每次请求触发。

### 4.5 过期后任务表现

过期任务在 API 中的表现：

| 字段 | 过期前 | 过期后 |
| --- | --- | --- |
| `state` | `succeeded` | `succeeded`（不变） |
| `object_key` | `users/{uid}/{tid}/{filename}` | `None` |
| `failure_code` | `None` | `retention_expired` |
| `failure_reason` | `None` | `"文件保留时间已过期并已清理，历史记录仍保留"` |
| 下载链接接口 | 返回预签名 URL | 返回 410 `retention_expired` |

设计要点：

1. 过期不改变 `state`，保持 `succeeded`。`state` 反映的是"任务是否成功完成"，而非"产物是否可下载"。
2. 通过 `failure_code = retention_expired` 和 `object_key = None` 标记产物已清理。
3. 任务详情、列表、事件等接口仍然可用，保留完整历史。

### 4.6 保留时长配置

| 配置项 | 环境变量 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `file_retention_hours` | `FILE_RETENTION_HOURS` | `24` | 全局默认保留时长（小时） |
| `User.file_retention_hours` | — | `24` | 用户级保留时长，覆盖全局默认 |

`expires_at` 计算方式：

```python
expires_at = datetime.now(UTC) + timedelta(hours=task.user.file_retention_hours)
```

### 4.7 存储清理与对象删除

对象删除在以下场景触发：

1. **过期清理**：`cleanup_expired_task_outputs` 删除过期对象。
2. **任务取消**：Worker 检测到取消后调用 `delete_artifact(stored.object_key)`。
3. **上传失败后清理**：如果取消发生在上传后、状态更新前，Worker 删除已上传对象。

删除使用 `ObjectStorage().delete_object(object_key)`，调用 `boto3` 的 `delete_object` 方法。删除操作幂等，对象不存在时不报错。

## 6. 验收门禁

- 成功任务的下载接口返回包含 MinIO 域名的预签名 URL。
- 预签名 URL 在 `presigned_url_ttl_seconds` 内有效。
- 产物过期后任务详情返回 `failure_code = retention_expired`，下载接口返回 410。
- 过期后任务记录仍可查询，`state` 保持 `succeeded`。
- 任务取消后 MinIO 中对应对象被删除。

## 7. 风险与边界

1. 如果预签名链接长期有效或 TTL 配置过大，会降低自部署环境的安全边界。
2. 过期清理依赖 API 请求触发（懒清理），如果长时间无请求，过期对象会滞留 MinIO。
3. `s3_public_endpoint_url` 配置错误会导致预签名 URL 对客户端不可访问。
4. 并发请求可能触发多次过期清理，但 `delete_object` 幂等，不会产生副作用。

## 8. 待确认问题

- 是否需要定时任务（cron/worker job）主动清理过期对象，而非仅依赖 API 请求触发。
- 是否需要支持保留时长为 0（立即过期）或 -1（永不过期）。
