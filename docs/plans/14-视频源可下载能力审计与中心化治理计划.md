# 视频源可下载能力审计与中心化治理计划

## 1. 目标

把当前视频源能力从“能识别/能解析”提升为“能下载并交付产物”的可验证口径，同时让项目只有一个视频源接入中心。

## 2. 当前审查结论

### 2.1 已存在的中心化链路

1. `apps/api/app/services/parse_service.py` 使用 `SourceAdapterRegistry` 选择适配器。
2. `apps/api/app/sources/registry.py` 默认注册 `DomesticShortVideoAdapter`、`BilibiliAdapter`、`YtDlpAdapter`。
3. `apps/api/app/sources/adapters/ytdlp.py` 使用 `yt-dlp` 做通用解析 fallback。
4. `apps/worker/worker/download_runner.py` 使用任务上的 `format_id` 调用 `yt-dlp` 下载，并依赖 FFmpeg 合并输出。

### 2.2 需要治理的问题

1. `apps/api/app/services/download_adapter.py` 仍保留另一套 `PlatformAdapter`、`AdapterRegistry` 和 `DownloadEngineAdapter`，与 `app.sources` 形成双中心。
2. `apps/api/tests/test_download_adapter.py` 和 `apps/api/tests/test_platform_adapters.py` 仍围绕旧中心测试，可能让 Agent Review 误判当前架构。
3. 当前平台画像列表包含多个平台，但缺少“解析成功 -> 创建任务 -> Worker 下载 -> 产物交付”的平台级验收矩阵。
4. 文档和代码需要明确：未知公网 host 只是 fallback attempt，不是正式支持平台。

## 3. 任务拆解

### 3.1 OpenSpec 变更

1. 创建 `openspec/changes/video-source-download-governance/`。
2. 在 spec 中定义支持状态：`supported_download`、`parse_only_or_unverified`、`fallback_attempt`。
3. 定义中心化架构约束：视频源选择只能从 `app.sources` 进入，不允许保留并行 registry。
4. 定义支持矩阵必须包含的字段：platform_id、host、adapter、download_engine、required_auth、known_limits、validation_evidence。

### 3.2 代码治理

1. 将 `app.services.download_adapter` 中仍有价值的 response conversion、错误分类或测试样例迁移到 `app.sources.models`、`app.sources.adapters.ytdlp` 或 `ParseService`。
2. 删除旧的 `PlatformAdapter`、`AdapterRegistry`、`DownloadEngineAdapter`，或将其改为清晰的 deprecated shim，并禁止生产路径使用。
3. 更新所有测试引用，避免新旧适配器中心并存。
4. 增加架构边界测试，断言 `app.services.download_adapter` 不再定义独立 adapter/registry 中心。

### 3.3 支持矩阵

建立 `docs/acceptance/02-视频源可下载支持矩阵.md`，至少覆盖：

| 平台 | 当前目标状态 | 验收方式 |
| --- | --- | --- |
| B 站 | `supported_download` 或 `parse_only_or_unverified` | 公开 BV URL 解析、任务、Worker fake download、对象存储链路 |
| 抖音 | `supported_download` 或 `parse_only_or_unverified` | 公开短链/长链解析、任务、下载失败语义 |
| 快手 | `parse_only_or_unverified` | 平台识别与 fallback 行为 |
| 小红书 | `parse_only_or_unverified` | 平台识别与 fallback 行为 |
| 西瓜视频 | `parse_only_or_unverified` | 平台识别与 fallback 行为 |
| 微博 | `parse_only_or_unverified` | 平台识别与 fallback 行为 |
| TikTok | `parse_only_or_unverified` | `yt-dlp` fallback 行为 |
| X / Twitter | `parse_only_or_unverified` | `yt-dlp` fallback 行为 |
| Instagram | `parse_only_or_unverified` | `yt-dlp` fallback 行为 |
| YouTube | `supported_download` 或 `parse_only_or_unverified` | 公开测试 URL 解析、format selector、Worker fake download |
| Vimeo | `parse_only_or_unverified` | `yt-dlp` fallback 行为 |
| Dailymotion | `parse_only_or_unverified` | `yt-dlp` fallback 行为 |
| 未知公网 host | `fallback_attempt` | 安全 host 校验通过，unsupported 映射正确 |

最终状态必须由验证证据决定，不能只由平台画像决定。

### 3.4 下载链路验收

1. 为 `TaskCreate.format_id` 到 Worker `YoutubeDL({"format": ...})` 增加契约测试。
2. 为推荐格式 `bestvideo+bestaudio/best` 和分辨率格式 `bv*[height<=720]+ba/b[height<=720]` 增加 Worker 下载 fake 测试。
3. 为缺少 FFmpeg、缺少 yt-dlp、平台限制、429、unsupported URL、下载后无产物增加失败分类测试。
4. 为对象存储上传和下载链接交付保留现有测试，并补充平台来源字段验证。

## 4. Scope Boundaries

### In scope

1. `apps/api/app/sources/`
2. `apps/api/app/services/parse_service.py`
3. `apps/api/app/services/download_adapter.py`
4. `apps/api/tests/sources/`
5. `apps/api/tests/test_parse_service.py`
6. `apps/api/tests/test_download_adapter.py`
7. `apps/api/tests/test_platform_adapters.py`
8. `apps/api/tests/test_architecture_boundaries.py`
9. `apps/worker/worker/download_runner.py`
10. `apps/api/tests/test_worker_jobs.py`
11. `docs/acceptance/`
12. `openspec/changes/video-source-download-governance/`

### Out of scope

1. 前端展示改造。
2. 绕过平台登录、会员、付费、DRM、版权或地区限制。
3. 承诺 `yt-dlp` 全量 extractor 都是正式支持平台。
4. 动态远程插件系统。
5. 大规模重写 Worker 队列和对象存储。

### Explicit non-goals

1. 不用兼容性包装保留两个 registry 中心。
2. 不新增只检查文案、不约束下载链路的弱测试。
3. 不把平台画像命中当成下载支持证据。

## 5. Acceptance Criteria

1. 项目只有一个视频源 adapter/registry 中心，生产代码从 `app.sources` 进入。
2. 旧 `DownloadEngineAdapter` 不再作为独立中心存在；测试不再依赖旧中心判断平台支持。
3. 支持矩阵明确列出每个平台是 `supported_download`、`parse_only_or_unverified` 还是 `fallback_attempt`。
4. 至少 B 站、YouTube、未知公网 fallback 有下载链路级测试或 fake integration 证据。
5. 国内短视频平台必须有受限/风控失败语义测试，不能承诺绕过平台限制。
6. Agent Review 能通过文档、OpenSpec、测试和代码路径确认“支持”等于可下载交付。

## 6. Validation

### Automated

```bash
pytest apps/api/tests/sources -v
pytest apps/api/tests/test_parse_service.py -v
pytest apps/api/tests/test_download_adapter.py -v
pytest apps/api/tests/test_platform_adapters.py -v
pytest apps/api/tests/test_architecture_boundaries.py -v
pytest apps/api/tests/test_worker_jobs.py -v
pytest apps/api/tests/test_task_endpoints.py -v
bash scripts/validate-repository.sh
```

### Manual

1. 对照 `docs/acceptance/02-视频源可下载支持矩阵.md` 检查每个平台的状态和证据。
2. 抽查一个公开 B 站 URL 和一个公开 YouTube URL，从 parse 到任务完成的链路记录。
3. 抽查一个未知公网 unsupported URL，确认 fallback 失败语义清晰。

### Agent Review focus

1. 检查是否仍存在两个 adapter/registry 中心。
2. 检查平台支持声明是否有下载交付证据。
3. 检查是否有 router/worker 平台分支绕开 `app.sources`。
4. 检查是否误把受限内容写成支持能力。

## 7. Deliverables

1. OpenSpec change：`video-source-download-governance`。
2. 中心化 adapter/registry 代码治理。
3. 支持矩阵文档。
4. 下载链路级测试。
5. Agent Review 审查记录和验证命令。
