## 1. 分阶段授权

| 门 | 输出 | 允许做什么 | 禁止跨越 |
| --- | --- | --- | --- |
| G0 设计评审 | 架构、契约、威胁边界、实验材料、待决项 | 当前文档与只读核对 | 不因文档完整自动批准实现 |
| G1 根因区分 | 同样本应用/引擎、当前/候选版本对照 | 用户批准后的隔离实验 | 不修补生产使实验失去对照 |
| G2 恢复可行性 | 同机重建、新主机同出口/新出口证据 | 已批准样本、私有来源、目标机器范围内实验 | 不重启有活动业务的共享服务，不擅迁凭据 |
| G3 自动来源可行性 | 单平台访客/账号维护证明与拒绝案例 | 单独批准的候选来源验证 | 不执行自动登录或扩大权益；证据不足标 No-Go |
| G4 实现批准 | 用户批准的平台与功能白名单 | 才可按下面切片实施 | 不将研究结论当用户实现指令 |
| G5 发布验收 | 全链路、重启与新机、客户端结果 | 用户批准的部署更新 | 不用单测/Runner canary 替代发布通过 |

G1/G2 可证明静态来源和路由改造的可行性，不要求先建设完整来源服务；G3 可以用受控人工步骤或临时最小验证工具证明协议，无需先实现产品模块。任何实验脚本也须在用户批准实验范围后编写/执行，不混入本次设计交付。

## 2. 可行性实验的前置材料

- 用户确认代表样本和允许处理范围；优先既有固定矩阵，正式发布用项目自有或明确授权样本。无需在聊天中粘贴 Cookie/密码。
- 部署者准备必要单平台来源的私有本地路径和使用许可，记录来源种类而不是材料值；没有有效授权则如实阻断该路径。
- 明确目标机器/OS/架构、可控出口及基础设施；没有第二台干净机器就不能完成换机门禁。
- 记录当前镜像 digest、引擎 commit、插件/运行时版本、Profile、配置摘要、来源不透明修订、出口 generation、任务预算。
- 记录活动业务任务，实验使用隔离的工作区/任务与批准的测试账号；涉及停止/切换时先排空，不共享写入两套部署。
- 不为实验另起本机 PostgreSQL/Redis/MinIO/RabbitMQ；数据库实验使用已有服务中的隔离 schema/库，生产会话不进入 CI。

## 3. 实验矩阵与裁决

| ID | 实验 | 唯一变量 | 通过或结论 |
| --- | --- | --- | --- |
| E01 | Web/API→Worker→Runner vs 同容器直接引擎 | 应用封装 | 固定版本、来源、出口、格式；引擎成功而应用失败才定位本项目链路 |
| E02 | 当前已批准引擎 vs 审核后的候选 | 引擎兼容组合 | 至少 3 次同样本对照，保存失败分类；不能把偶发成功当稳定修复 |
| E03 | 同机器进程重启/容器重建 | 可丢弃状态 | 至少 3 个冷启动循环，每次 metadata→完整 media→Artifact 均通过 |
| E04 | 新机器恢复，保留同受管出口 | 机器/路径 | 无旧缓存/浏览器依赖完成相同样本及历史 Artifact 获取 |
| E05 | 新机器使用另一个合法出口 | 出口 generation | 明确恢复或重新验证要求；不得用代理轮换绕过拒绝 |
| E06 | 访客来源首次建立、过期、重建 | 访客修订 | 第一方正常流程、无账号字段、拒绝跨域与权益扩大；无法做到则 No-Go |
| E07 | 同账号正常维护、撤销、新账号替换 | 主体/修订 | 证明账号连续性；维护后旧 context 被拒绝，新 inspection 可用；做不到则保留 manual_file |
| E08 | 更新发布各断点崩溃、并发维护、旧备份恢复 | 故障时刻 | 无半写状态、无倒退放行、无多写者、撤销不复活 |
| E09 | Web/Flutter 端到端 | 客户端 | 真实任务、MinIO 下载和本地播放；390px 不能替代真机测试 |

先做 YouTube（临时证明/引擎）、抖音与小红书（公开/访客路径），再做一个手工账号来源平台和其余固定矩阵。腾讯低速、优酷/腾讯 VIP、视频号分别保留独立裁决，不能拿前三个平台成功替代。

## 4. 实现切片（按可行性与前置条件推进）

所有切片先核对 [代码质量登记](../code-quality.md)，列出受影响项、最小修复、保留边界和验收；无关项独立排期。G4 必须包含新增结构的必要性和不实施项，CQ-009 不通过时不实施 I2。遵守 R15/T21，不为“代码洁癖”引入更大的通用框架。

### I1 访问策略与契约

涉及既有 `domain/providers.py`、`runner/provider_registry.py`/catalog、`integrations/media_inspection_pipeline.py`、inspection 用例/schema、状态视图和相应测试。先补明确策略、授权拒绝、幂等指纹的失败测试，再改路由。同步 Web/App OpenAPI 客户端，不新建平行 DTO。

### I2 来源状态与可选维护者

仅 G3 Go 的平台进入。围绕 `provider_sessions.py`、`provider_cookie_file.py` 与现有加密来源协议实现批准接口；保留 Runner 只读和操作副本。必要时在 `runner/` 增加单平台来源进程与对应 Compose profile，不搭全局 Broker。先验证原子发布、租约、主体变化、撤销与 crash safety，再接真实平台维护方法。

### I3 持久预算与状态投影

复用 download job/attempt/retry_at、canary 表与 task events；只为批准的每任务 repair_count 和路径 cooldown 调整当前态 `schema.sql`、ORM/Repository。空库和已有当前态库都验证，禁止增加历史迁移框架。公开故障分类与真实状态一致，配置故障不伪装风控。保留人工重试创建新任务及现有删除语义，验证任务删除不清除路径冷却；同一任务重启/重投不能恢复已消费的修复额度。

### I4 客户端恢复与发布闭环

复用现有平台页、解析页和下载详情页，补策略选择、来源变化重新解析、冷却和 stale 证据。保持 `frontend-visual-system` 和 App 设计规范。然后按 G5 做平台矩阵、重启/换机、Tailscale 与对象存储、真机保存播放。

每切片采用 Red→Green→Refactor，只提交白名单文件。源码/Schema/Compose/Secret 发生变化前再次核对当前工作树和业务任务；当前文档提交不是部署授权。

## 5. 上线与回滚顺序

1. 确认 I1–I4 选定范围与 G5 结果；备份必要状态，排空活动任务。
2. 基础 manual_file 路径先行；自动来源默认关闭，按平台开启，不能全平台一起切换。
3. 统一镜像、插件/sidecar、Profile 和契约版本一起交付；已持久化 context 严格比较，不用兼容分支消除失败。
4. 有失败则停用对应新策略，恢复批准镜像/配置；不恢复已撤销 Secret、不把旧修订标为 ready。
5. 用户重新解析生成新资源；原任务与失败证据保留，不写数据库“修复成功”。

## 9. 持久冷却实施进度
