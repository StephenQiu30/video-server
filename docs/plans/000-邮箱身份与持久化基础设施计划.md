# Plan 000：邮箱身份与持久化基础设施

## 1. 交付边界

本 Plan 是所有视频解析、下载、AI 与 PDF Plan 的基础前置：以 PostgreSQL UUID 用户替换安装令牌 owner，交付邮箱验证登录和可撤销会话；把 PostgreSQL、Redis、MinIO、SMTP 接入统一 Port/outbox/Saga；证明备份恢复与 OpenAPI 契约。

本 Plan 不解析或下载视频，不调用 AI/FFmpeg/Graphviz/WeasyPrint，不实现社交登录、MFA、团队、公开分享或永久存储，不保留安装 token 兼容双轨。现有 Plan 001 的已验证纯领域/rights 结果可以保留，但 owner/API 后续实现必须等待本 Plan `done`。

## 2. 前置门禁

- Design 005 与修订后的 Design 001–004、PRD 001 均为 `accepted`。
- Acceptance 002 为 `accepted/result: pending`，冻结环境、AC、故障注入与恢复证据。
- MinIO 09-07 历史镜像因缺少后续安全修复被禁止；开发/CI 从官方 tag `RELEASE.2025-10-15T17-29-55Z`、commit `9e49d5e7a648f00e26f2246f4dc28e6b07f8c84a` source build，并在 MinIO 切片前冻结 base/image digest、provenance、SBOM 与 CVE 结果。生产三选一决策尚未完成，生产 AC 预期 blocked。
- 每个切片必须先提交约束行为的 `test:` Red，再提交最小 `impl:`/`feat:` Green；不得在一个提交混合测试和生产实现。

上述设计、PRD 与 Acceptance 已于 2026-07-18 通过独立三轮复审，本 Plan 现为 `ready`；只能按下列切片逐项实施和回填真实 Red/Green，不能虚构证据。

## 3. 实施顺序与 TDD 切片

### 3.1 用户与 UUID owner

- [ ] Red：空库 upgrade/downgrade、`users.id UUID`、唯一规范化 `email`、所有业务 `owner_id UUID NOT NULL FK`、跨 owner 404；含文本 owner 数据时以命名约束 fail closed。
- [ ] Green：加入 FastAPI Users SQLAlchemy UUID 用户表、auth audit；将现有 Job/Resolution/Source/outbox owner 迁为 UUID，删除 installation principal/token schema 与无 FK 路径。
- [ ] Refactor：领域只依赖 `Principal(user_id: UUID)`/`IdentityProvider` Port，不导入 FastAPI Users model。

### 3.2 会话与邮箱认证

- [ ] Red：csrf bootstrap/no-store、register/verify/login/logout/forgot/reset/me 全契约；未验证、禁用、过期、撤销、密码重置后旧会话、签名 double-submit 配对、登录/注销后的配对轮换、受控 `TRUSTED_API_AUTHORITY` 的 exact Host/Origin/Fetch Metadata、Cookie flags 和跨用户枚举失败。
- [ ] Green：在 `pyproject.toml` 加入 FastAPI Users 15.0.5、SQLAlchemy Adapter 7.0.0、DatabaseStrategy、CookieTransport、pwdlib/Argon2id、email-validator、fastapi-csrf-protect 1.0.7、aiosmtplib、Jinja2 与 MinIO SDK 的受控范围，并由 `uv.lock` 固定实际版本；实现九个冻结端点和 canonical Problem code。
- [ ] Red/Green：生产 `__Host-video_session` 与 loopback-only `video_session_dev` 配置互斥，非 loopback 使用 dev Cookie 必须启动失败。

### 3.3 邮件意图与 SMTP

- [ ] Red：分别注入注册用户 commit 后 callback 崩溃，以及已验证用户 forgot intent commit 后 callback 崩溃；前者由未验证用户 scanner、后者由同 intent reconciler 在 1 分钟内补建唯一投递。callback 原子事务 commit 前崩溃必须同时无 outbox/ENQUEUED，commit 后必须二者同时存在；覆盖并发、新 generation supersede、generic 202、verify/reset 1h/30m 单次使用、SMTP 失败、超时与敏感日志扫描。
- [ ] Red：注入 reset 已验证但 command commit 前崩溃，证明 hash/session/intent/audit 全回滚；commit 后崩溃则四类事实全提交且旧 Cookie 不可用。verify 同样原子提交用户验证、intent 消费与审计。
- [ ] Green：建立 `auth_mail_intents` generation/state 与高熵 token 原始 UTF-8 bytes 的 SHA-256 digest/唯一约束；用显式 intent 上下文调用 FastAPI Users token codec，callback 以项目 command 原子写 outbox/ENQUEUED；verify/reset facade 复用库的 codec/parser/password helper，但用项目事务写身份事实，不挂载默认 verify/reset router。
- [ ] Green：用 cryptography `>=49.0,<50` AES-256-GCM 冻结 v1 envelope、96-bit nonce、含 format/key ID 的长度前缀 AAD、外部 keyring 与轮换；`SENT/SUPERSEDED` 立即、其他未投递行最迟 expiry crypto-shred，旧 key 仅在零引用后退役。加入受控 Jinja2 模板、aiosmtplib STARTTLS/TLS Adapter、auth audit、scanner 与 reconciler。
- [ ] Green：固定 mail 状态、attempt、next-at、dead-letter 与告警；Celery 消息只能含 `mail_id`。

### 3.4 Redis 运行边界

- [ ] Red：固定 `redis:8.2.7-alpine@sha256:223b183cbc49f5ff48728e1fc52ccf101f05072decad2bd9867281a3c9bf75fd`；验证 AOF/RDB、`noeviction`、认证/TLS/独立前缀健康检查；每个 cache/rate-limit key 有 TTL，业务表/会话/Job 状态不从 Redis 读取为真相。
- [ ] Green：配置 redis-py/Celery broker、SSE wake、认证和邮件限流；Redis 不可用时敏感入口 fail closed，已有会话只读认证仍读 PostgreSQL。
- [ ] Red/Green：清空 Redis 后缓存自然重建、SSE 从 `job_events` tail、非终态 Job 可在 15 分钟内恢复投递。

### 3.5 Transactional outbox 与恢复投递

- [ ] Red：用户/Job/资产状态与 outbox 原子；claim lease/fencing、publish-before-ack 崩溃、ack-after-publish 崩溃、重复消息、poison/dead-letter 和 Redis 完整丢失。
- [ ] Green：dispatcher 只传 ID；worker 按 aggregate/attempt 幂等；reconciler 对无有效 lease 的非终态 Job 创建新 delivery attempt，不改写历史事件。
- [ ] Red/Green：SMTP 与 Job queue 使用相同可靠投递原语但不同 kind/队列/并发和重试政策。

### 3.6 MinIO Port 与对象 Saga

- [ ] Red：私有 bucket、opaque key、owner 隔离、15 分钟 presign、multipart、size/MIME/SHA-256/version HEAD 校验、无 READY 前不可下载。
- [ ] Green：MinIO SDK 7.2.20 Adapter；实现 `PENDING/UPLOADING/READY/FAILED/DELETING/DELETED`、fencing、重试和事件事务。
- [ ] Red/Green：MinIO 超时/中断、complete 后 PG 崩溃、重复 complete/delete、过期 multipart、孤儿对象、checksum mismatch 与删除全部版本/副本。
- [ ] Gate：从冻结官方 source commit 可重复构建内部镜像并记录 base/image digest、provenance、SBOM/CVE/AGPL；09-07 与第三方镜像禁止。生产在 AIStor/维护发行版批准、书面接受归档 MinIO 精确 digest、用户放宽 MinIO 三者完成其一前保持 blocked。

### 3.7 备份、恢复与数据生命周期

- [ ] Red：pgBackRest base/differential + WAL 可恢复到目标时点；恢复后 UUID FK、outbox、session revoke 与 Job event 一致。

## 4. Red / Green 证据规则

每个 Red 必须记录命令、失败用例、失败信号和 commit SHA；“模块/文件不存在”不算 Red。每个 Green 记录同一用例转绿及全量回归，不能只跑新增测试。建议分层命令：

```text
uv sync --frozen
uv run pytest tests/unit -q
uv run pytest tests/integration/persistence -q
uv run pytest -m "contract or integration or security or retention" -q
uv run ruff check .
uv run ruff format --check migrations src tests
uv run mypy src
uv lock --check
uv run alembic upgrade head
uv run python -m video_server.openapi --check openapi/openapi.json
```

真实服务测试固定 PostgreSQL 17、Redis 8.2、SMTP test server 和两个 MinIO 隔离 deployment；测试结束只清理本次专属数据库/bucket/volume，不使用宽泛删除命令。

## 5. 完成定义

- `AC-AUTH-001/002`、`AC-DATA-001`、`AC-REDIS-001`、`AC-MAIL-001`、`AC-OBJ-001`、`AC-DR-001`、`AC-CONTRACT-001` 逐项有 `passed` 或真实外部 `blocked` 证据；任何 failed 不得完成。

## 6. 风险与回滚

FastAPI Users 维护模式通过 Port、锁定版本和季度复核控制；MinIO 归档风险不能由代码测试消除。SMTP 拒收、Redis broker 丢失和对象/数据库部分成功必须由持久化 intent、幂等 worker 与 reconciler 收敛。

应用回滚保留向前兼容 schema；含真实 UUID 用户/资产后禁止 downgrade 到 installation owner。对象 Adapter 可在 Port 后更换，但未经新 Acceptance 不得改变 key、checksum、删除或 presign 契约。
