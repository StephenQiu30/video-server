## 1. 实施顺序

1. 冻结稳定 job、run、attempt、trigger、状态机、版本、幂等键和错误码语义，明确 `201 Created + Location + 最新任务投影`。
2. 在当前态 SQL、ORM 和 repository 中增加 `analysis_runs`、`active_run_id`、任务 `version` 与幂等操作记录，将初始创建也建模为 run 1。
3. 重构 claim、heartbeat、retry wait、结果发布、取消和恢复用例，使所有执行写入同时校验 `job_id/run_id/lease/version`。
4. 实现 `RetryAnalysis` 应用用例：owner、终态、artifact、配额校验，任务行锁，run_no 分配，幂等重放和单活约束。
5. 在同一事务写 run、任务投影、task event 和 `analysis.requested` Outbox；消息显式携带 run/version。
6. 增加 `POST /api/analyses/{analysis_id}/retry` 严格空请求体、必需 `Idempotency-Key`、稳定 operationId、201 响应和 Location。
7. 扩展任务查询为当前 run、最近 run 摘要、current report 与可重试窗口；完整历史使用 owner 限制的分页资源。
8. 前端改为在原任务上调用 retry API，保留 analysisId、路由、播放器与订阅，准确展示 run_no 和 attempt。
9. 完成并发、消息延迟、租约、额度、API、前端和真实 Worker E2E 后回填 Acceptance。

## 3. 数据与并发测试

- 当前态 schema 同时覆盖 run_no 联合唯一、单活 run、幂等 key、外键和删除策略；使用空数据卷与已有当前态卷验证。
- 两个不同 key 同时重试只有一个 201，另一个稳定 409；相同 key 并发只创建一个 run/Outbox/计费记录。
- 重试与取消、lease 恢复与新 run、旧 run 结果与新 run 发布同时发生时，版本 fencing 阻止旧写入。
- 自动 retry_wait 只改变同一 run 的 attempt；Recovery Sweeper 重发也不增加 run_no。
- 删除中、artifact 过期/哈希错误、超限、非 owner 和非终态都不留下 run、事件或额度副作用。

## 4. API 与前端测试

- OpenAPI：稳定唯一 operationId/tag，必需 `Idempotency-Key`，无可变语义 body，201/409/429 Problem Details 和 Location。
- API：401、owner 404、各终态成功、各活跃态冲突、幂等重放和 artifact 不可用。
- 前端：失败/取消显示“重试”，成功显示“重新分析”；请求期间禁用重复操作但仍依靠后端幂等。
- 页面在响应丢失后复用原 key；run 创建后不清空 job、不回 create API、不更换 URL 或订阅。
- 展示第 N 次执行、本 run attempt、失败原因、上一报告和最后可重试时间，并覆盖 1280px/390×844、键盘和错误恢复。

## 5. 发布与回滚

- 013 是 012/014/015 的数据前置，先合入 schema/domain/repository，再切换消息消费者与 API，最后切换前端。
- 部署期间不保留旧“再次调用 create API”的前端路径；新后端可用后同版本生成 OpenAPI 客户端。
- 若消费者未升级，不发布携带新 run 契约的消息；回滚时暂停 Outbox Publisher，保留数据库事实并修复后恢复。

## 6. 不做项

不复制 job、不允许重试时改语义配置、不并行多个 run、不无限保留 artifact、不自动切换 Provider，也不建立旧 attempt 字段兼容双轨。
