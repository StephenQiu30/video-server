# 个人部署：自动来源恢复、重启与换机

普通用户只提交链接，不导出 Cookie、不安装桌面代理。现有 PostgreSQL 保存部署级加密来源，独立 `provider-sources` 进程发布各平台短期文件租约。Runner 只读自己的命名卷。重建或换机后本地卷由系统重建，协议见 [043](../design/043-跨宿主平台来源自动恢复.md)。

## macOS 已登录 Chrome 自动来源（实施中）

标准启动入口默认为 YouTube 声明受控路线，并以宿主当前用户身份检查 Chrome `Default`／`Profile N` 中唯一可用的 YouTube 来源；额外平台可通过部署机环境变量 `AUTO_BROWSER_SOURCE_PROVIDERS=youtube,douyin,reddit` 明确加入当前已配置的单平台 Runner。读取器只导出该平台许可域名的 Cookie，不复制完整浏览器 Profile。唯一候选自动加密登记，后续由宿主 LaunchAgent 每分钟检查并刷新，容器来源复制器继续分发最长 90 秒的只读租约。无登录、多 Profile 歧义、宿主权限被拒和上游验证失败必须分别诊断；当前仅 macOS Chrome 适配器已进入实现，Linux／Windows 不在已验收矩阵中。

从仓库根目录使用 `provider_startup start`。入口在 `.env` 没有来源密钥时于忽略提交的 `.local-runtime/provider-source.key` 创建一次 `0600` 稳定密钥，并经私有运行环境文件注入来源进程；不要删除该文件或让备份与数据库失配。已有 `.env` 来源密钥继续优先使用。`prepare` 只写受控运行配置，不读取浏览器或发布来源。`start` 会先尝试宿主同步，打印各平台的非秘密状态；成功启动 Compose 后安装当前用户的 `com.framefetch.provider-source-host` LaunchAgent。来源可读只表示可尝试，仍须按 [007](007-固定Provider探针运行手册.md) 检查 metadata、media 和完整文件。宿主浏览器与容器出口若不一致，上游仍可能拒绝该来源。

已有手工登记的密文来源保留优先权，自动维护进程不会覆盖或撤销它。若部署者明确希望改为浏览器自动来源，应先用本手册的受控撤销流程处理旧来源，再由自动维护进程重新发布。没有浏览器登录态时，公开平台继续可用；该会话平台的缺失属于部署前提，普通用户无需处理 Cookie。

## 首次部署登记

复用现有数据库与环境配置，按当前 `backend/sql/schema.sql` 初始化结构。来源表与业务表使用同一持久数据库，不在媒体 Runner 中配置数据库访问。把 `PROVIDER_SOURCE_ENCRYPTION_KEY` 作为稳定 Fernet 密钥配置在部署 Secret 中，仅注入来源进程；它与数据库备份分开保管，不能每次启动重新生成，也不能写入 Git、镜像、日志、命令参数或截图。

需要手工来源的部署者仍可一次性把已有批准的单平台文件登记到持久库。下列命令在 backend 目录执行，从根 `.env` 读取现有连接和来源密钥；生产运维应以受控进程环境注入对应值，CLI 不自动读取 `.env.prod`。文件路径仅为占位示例，不能使用所有站点的浏览器导出文件。

```bash
uv run python -m app.workers.runner.provider_source_replica status --provider youtube
uv run python -m app.workers.runner.provider_source_replica publish \
  --provider youtube --source /private/youtube.cookies.txt \
  --expected-revision 0 --valid-for-seconds 86400
```

`status` 返回非秘密修订和状态。0 仅表示此前没有持久记录；已登记、已撤销或并发更新后必须使用最新修订。有效期可设为 60 秒至 7 天，是此次批准的最长使用期限，不会延长平台登录寿命。文件必须通过单平台域、必需字段、权限和过期检查；登记成功不等于平台已经接受它。

标准 Compose 的 YouTube、抖音、Reddit 与生产 Compose 的优酷、腾讯视频均使用这条链路。此前安装在 `.provider-sessions/<provider>/cookies.txt` 的文件需要部署者首次登记；Compose 已改为读取来源进程管理的命名卷，旧目录不再直接挂载。普通用户无需执行登记步骤。

在部署环境中配置对应 Runner endpoint、profile 和默认策略，例如：

```dotenv
COMPOSE_PROFILES=youtube-operator
RUNNER_OPERATOR_BASE_URLS={"youtube":"http://youtube-operator-runner:19100"}
RUNNER_DEFAULT_ACCESS_POLICIES={"youtube":"operator_public"}
```

只启用已有批准且符合内容策略的平台。统一入口也会根据显式本地 endpoint 补全相应 profile；远端 endpoint 不启动重复本地 Runner。单平台来源暂时缺失不会删除这些声明，不静默改成另一种账号身份。默认没有受控配置时仍保留匿名能力。

## 启动与正常重建

```bash
docker compose --env-file .env.prod -f docker-compose-prod.yml config --quiet
uv run --project backend python -m app.workers.runner.provider_startup start \
  --env-file .env.prod --compose-file docker-compose-prod.yml \
  --runtime-env .local-runtime/provider-startup.prod.env
```

更新镜像或配置用上述重建入口；普通 `docker compose restart` 不应用新镜像和配置。来源初始化容器只准备平台卷的 UID 10001 私有目录，来源进程每 15 秒同步一次，自动发布有效来源。平台之间并行，不因某个平台会话不可用阻止核心 API 启动。

Compose 对可选 Runner 检查 `/health/runtime`；实际平台来源仍通过 `/health/ready` 判断。来源进程心跳只证明循环运行，不证明数据库、授权或平台媒体可用。缺少来源密钥时明确报告 disabled；统一入口发现已启用本地文件路线却未配置密钥会直接报告配置错误，不生成新密钥掩盖丢失状态。

来源采用最长 90 秒的本地租约。撤销、过期、无效密文会清除副本；数据库断开或来源进程停止后，Runner 自行拒绝到期租约。来源恢复无需重建 Runner。正常续租不会改变访问上下文；实际 Cookie 内容变化时旧 inspection 需重新解析。

## 换机

更换手机、平板或前端电脑时仍连接同一 FrameFetch 服务，平台来源不迁移到客户端。更换后端宿主时：

1. 连接原持久 PostgreSQL，或先恢复其完整备份；保持来源密钥、部署 HMAC 与需要保留的业务状态。数据库也在旧机器上时，不能仅复制仓库后启动空库。
2. 部署当前镜像、环境和稳定 HTTPS 入口，启动同一入口。本机来源卷可以为空，系统自动从持久记录恢复；不手工复制 `cookies.txt`。
3. 依据实际环境调整外部服务地址、出口与公开入口，并验证 metadata、完整 media 和制品取件。平台可能要求新出口验证，这与程序丢失配置是不同故障。

MinIO 制品、队列、进行中任务和 `runner_work` 仍按原运行手册迁移；来源副本自动恢复不等于在途下载已实现跨宿主接续。`SITE_URL`、WebSocket 和 `MINIO_PUBLIC_ENDPOINT` 使用稳定 HTTPS 边界，远端客户端不能使用各自的 localhost。不得靠清空用户登录 Cookie 处理后端迁移问题。

## 更新与撤销

从原批准方式取得新来源后，使用查询到的最新 revision 执行 `publish`。条件写入冲突时重新读取并确认，不能无条件覆盖。下一轮同步自动发布新内容，无需重建镜像。明确撤销示例：

```bash
uv run python -m app.workers.runner.provider_source_replica revoke \
  --provider youtube --expected-revision 1
```

持久墓碑阻止旧维护请求覆盖撤销；明确重新授权后，可用最新修订发布新的批准来源。正常情况下撤销在下一次轮询生效，断连时新操作最多使用剩余租约；已取得操作 jar 的在途任务可以完成。新建实例不会从本机残留文件反向恢复已撤销授权。

宿主自动来源不会生成首次登录、解决验证码或保证平台长期接受登录态。操作中的 Set-Cookie 仍只写临时 jar；普通 Web 请求不直接读取私人浏览器，由宿主维护进程按平台许可范围刷新。

### macOS 视频号专用元宝登录

在用户明确允许本机持久保存专用会话后，从 `backend/` 执行：

```bash
uv run python -m app.workers.runner.yuanbao_session login
```

新窗口仅用于腾讯元宝及其必要登录认证，不用于其他网站或 Chrome 账号同步。用户完成首次登录后窗口自动关闭；检测到字段只表示保存了会话，必须另验真实下载。登录等待预算为 10 分钟，正常关闭/超时保留目录，可以重新执行。来源在 `~/Library/Application Support/FrameFetch/provider-sessions/yuanbao`，权限 0700、锁 0600；不复制、不导出普通 Chrome Profile。登录期间后台导出有界返回不可用，不关闭用户窗口。后续操作按需复用目录，操作结束关闭浏览器；默认路线仅在真实文件验证后启用。撤销时先停用视频号受控来源，确认登录/导出已结束，再由用户清除该专用目录；本地清除不能代替平台侧撤销登录会话。不要把该目录加入 Git、镜像、日志或普通备份附件。新机重新登录，不把跨机复制浏览器目录视为验收。


## 验收与故障定位

文件状态、Runner runtime 健康和平台下载分别验收。`credential_required` 表示没有当前来源；`credential_rejected` 表示格式、域或权限不合格；`credential_expired` 表示必要会话已失效；短租约到期返回 `provider_session_unavailable`。先检查来源进程、数据库、密钥、修订和当前出口，再按 [007](007-固定Provider探针运行手册.md) 分别运行 metadata/media；不要因单次解析成功宣布全平台可用。

路由 429 冷却仍保存于 `provider_route_cooldowns`，重启、删除任务或更新 Cookie 不清除限流。各业务进程保持时钟同步。视频号动态来源、平台撤销和新出口验证需要分别处理，不通过重置整个部署解决。
