# 个人部署：无状态启动、重启复用与可选迁移

故障处理与修复交付按 [009 SOP](009-下载故障修复与持续可用性SOP.md) 执行；本页提供具体来源配置与迁移规则。发生重启后多平台失败时，先检查公共出口、部署和来源通道，不直接重新授权所有账号。

> 目标设计已经调整为“当前宿主的 clean-room 部署先启动并自动探测，本机授权按需建立”，见 [031](../design/031-Linux无人值守运行设计.md) 与 BACKLOG P6。项目不要求额外机器。macOS 本机专用浏览器 Agent v1 已交付；产品内 loopback/Unix Socket 授权事务仍未交付，因此当前状态页会提供一次性的本机命令引导。下述 Cookie 文件、CLI 采集和加密迁移是高级运维/灾备通道，不是默认安装流程。

文件来源已实现；实际平台授权是否可用仍由平台结果判定。当前运行中的容器未自动迁移。标准 Compose 的 Chrome-backed Runner 使用本机 Agent 队列，视频号保留独立元宝动态来源，优酷/腾讯视频继续使用受控文件来源；本机开发与生产 Compose 使用同一套队列边界。

## 本机浏览器授权（macOS 首选）

Chrome-backed Provider 在运行后端的 macOS 宿主上只需首次授权一次；应用不要求用户手工获取或复制 Cookie。Agent 打开 Provider 官方页面，用户完成登录或平台验证后，状态保存在按平台隔离的专用 Chrome 目录，并由按需 LaunchAgent 复用：

```bash
cd backend
uv run python -m app.workers.runner.provider_cookie_agent authorize --provider youtube
uv run python -m app.workers.runner.provider_cookie_agent install \
  --browser-root "$HOME/Library/Application Support/FrameFetch/provider-browser-sessions"
uv run python -m app.workers.runner.provider_cookie_agent doctor \
  --provider youtube \
  --browser-root "$HOME/Library/Application Support/FrameFetch/provider-browser-sessions"
```

支持 `youtube`、`douyin`、`xiaohongshu`、`x`、`instagram`、`facebook`、`reddit`、`pinterest`。视频号继续使用独立元宝登录；腾讯视频和优酷继续使用本页后面的受控文件来源。换运行后端宿主时，平台可能要求在新宿主重新完成一次第一方授权；这无法通过应用或额外机器消除，但不需要把会话手工导出为文件。不要把专用浏览器目录、命令输出或授权数据提交到 Git、日志或普通备份。

## 高级来源配置（当前过渡通道）

### macOS 视频号专用元宝登录

在用户明确允许本机持久保存专用会话后，从 `backend/` 执行：

```bash
uv run python -m app.workers.runner.yuanbao_session login
```

新窗口仅用于腾讯元宝及其必要登录认证，不用于其他网站或 Chrome 账号同步。用户完成首次登录后窗口自动关闭；检测到字段只表示保存了会话，必须另验真实下载。登录等待预算为 10 分钟，正常关闭/超时保留目录，可以重新执行。来源在 `~/Library/Application Support/FrameFetch/provider-sessions/yuanbao`，权限 0700、锁 0600；不复制、不导出普通 Chrome Profile。登录期间后台导出有界返回不可用，不关闭用户窗口。后续操作按需复用目录，操作结束关闭浏览器；默认路线仅在真实文件验证后启用。撤销时先停用视频号受控来源，确认登录/导出已结束，再由用户清除该专用目录；本地清除不能代替平台侧撤销登录会话。不要把该目录加入 Git、镜像、日志或普通备份附件。新机重新登录，不把跨机复制浏览器目录视为验收。

标准 Compose 的 `youtube-operator`、`douyin-operator`、`reddit-operator` profile 直接挂载本机 Agent 的对应队列目录；相应 `RUNNER_PROVIDER_COOKIE_SYNC_ROOT` 指向容器内 `/run/provider-cookie-agent`，不会挂载 `.provider-sessions`。默认策略 key 同平台且值为 `operator_public`；只启用已授权且验证通过的平台。视频号使用上述独立来源，登录与真实下载结果分别验收。

YouTube 还必须从已经获得 Chrome 数据读取权限的实际桌面宿主启动单平台维护器。它不要求测试浏览器登录，不维护抖音、Reddit 或其他平台：

```bash
cd backend
uv run python -m app.workers.runner.provider_session_maintainer start
uv run python -m app.workers.runner.provider_session_maintainer status
```

`start` 先完成一次同步采集，无法读取、缺少账号字段或文件校验失败时直接拒绝启动并保留旧来源。成功后进程脱离项目，每 60 秒检查一次并只在 revision 变化时原子发布；Docker、Compose、前后端和 Runner 重启均不触发重新登录。macOS TCC 不把桌面应用权限自动传给 LaunchAgent，所以不要用系统直接启动的 Python 代替该入口。整机重启或切换桌面账号后，从已授权宿主重新执行同一幂等命令。

### Linux 文件来源示例

复用已有基础设施、`.env.prod` 和镜像构建入口。保留环境文件中的密钥；不要每次启动从 example 覆盖。以下只演示 YouTube，其他平台使用对应 key。

准备仅包含该平台域的有效 Netscape Cookie 文件，使用已有授权来源；不要导出所有站点的会话。将 `/path/to/youtube.cookies.txt` 替换为自己私下准备的源文件。容器默认 UID/GID 为 `10001`，权限只在首次安装或换机恢复时处理：

```bash
sudo install -d -m 0711 .provider-sessions
sudo install -d -o 10001 -g 10001 -m 0700 .provider-sessions/youtube
sudo install -o 10001 -g 10001 -m 0600 /path/to/youtube.cookies.txt .provider-sessions/youtube/cookies.txt
```

在现有 `.env.prod` 中设置并保留以下项目，其余已有配置不变：

```dotenv
PROVIDER_SESSION_DIR=./.provider-sessions
COMPOSE_PROFILES=youtube-operator
RUNNER_OPERATOR_BASE_URLS={"youtube":"http://youtube-operator-runner:19100"}
```

多个平台用逗号分隔 profile，并在路由 JSON 中配置相同平台。例：`youtube-operator,reddit-operator`。只配置已准备会话的平台。Web 只提交链接，不提供策略选择。服务端读取 `RUNNER_DEFAULT_ACCESS_POLICIES`；未覆盖的平台在允许公开访问时默认 public，只有受控方式的平台保持受控。端点存在性不改变默认值。部署者准备好有效来源与对应 Runner 后，可设置 `RUNNER_DEFAULT_ACCESS_POLICIES={"youtube":"operator_public"}`；显式受控但端点缺失时拒绝，不静默切换身份。每条路线仍需真实验证，默认 public 不代表上游一定接受，也不自动获取私人浏览器会话。

```bash
docker compose --env-file .env.prod -f docker-compose-prod.yml config --quiet
docker compose --env-file .env.prod -f docker-compose-prod.yml up -d --build --wait --wait-timeout 300
```

从旧的多文件或九平台配置切换时，先为选中的文件会话平台准备文件，并把路由改成实际启用的集合，再执行上述部署。不要跳过文件配置后判断迁移成功。视频号需要宿主代理和 `wechat-channels-operator` profile；纯 Linux 不启用此 profile，也不把其路由指向不存在的服务。

## 正常重启

整机重启后先恢复 YouTube 维护器；普通项目或 Docker 重启时 `status` 应保持 `running`：

```bash
cd backend
uv run python -m app.workers.runner.provider_session_maintainer start
uv run python -m app.workers.runner.provider_session_maintainer status
cd ..
```

```bash
docker compose --env-file .env.prod -f docker-compose-prod.yml restart
```

仅当镜像、配置和 schema 均未变化时使用 restart。代码或配置更新时，应先验证并应用当前 `backend/sql/schema.sql`，再构建和重建整组业务服务；restart 不加载新配置。I3 内部 InspectRequest 新字段要求 API、Worker、Canary 和 Runner 同版，不允许失败后删除字段降级。重建容器同样读取原目录：

```bash
docker compose --env-file .env.prod -f docker-compose-prod.yml up -d --force-recreate --wait --wait-timeout 300
```

前端的 `BACKEND_ORIGIN` 由 `src/proxy.ts` 在运行时读取，不是 Docker 构建参数。候选部署须指定自己的 API 容器名，并在该 API 日志中确认 `/api/providers` 与实际 `/api/inspections` 请求；只看新前端页面或 `/health/ready=200` 无法排除串到旧服务。运行环境值变化后重建前端容器，保留原用户 Cookie，不需要重新导出登录凭据。

后端宿主的本机验收入口为 `http://localhost:8101`（同端口的 `127.0.0.1` 亦可），API 为 8111；不能只替换临时 8137 前端。其他手机或电脑不能使用自己的 `localhost`，必须打开同一部署的稳定 HTTPS 入口（个人私有部署使用已验收的 Tailscale HTTPS 名称），并登录同一 FrameFetch 账户。`SITE_URL`、WebSocket 和 `MINIO_PUBLIC_ENDPOINT` 必须使用该 HTTPS 边界；平台 Cookie 仍只在后端 Runner 一侧。代理在转发前去掉 API/health 路径尾斜杠，防止 FastAPI 把浏览器重定向到内部容器主机。验证 `/api/auth/me/` 应返回认证结果而非内部 Location；不要以清空浏览器 Cookie 代替修复。

会话源以单平台目录只读挂载，临时 jar 位于 tmpfs；临时目录丢失不会删除源文件。生产模式不会启动时更新 yt-dlp；平台规则变更通过正常镜像构建和既有 CI 更新。

## 可选换机迁移

先区分两种“换设备”：

- 手机、平板或前端电脑变更：仍连接同一个 FrameFetch 服务时，平台授权不应迁移到客户端，也不需要重新导入 Cookie。
- 运行 API/Worker/Runner 的后端宿主机变更：需要迁移业务状态和经批准的服务端会话来源，并在新出口上重新验证。

如果需要保留既有账号会话与业务数据，可以迁移以下私有部署状态；这不是新宿主启动核心服务的前置条件，Git 仓库也不会保存它：

1. 相同版本的代码/镜像、现有 `.env.prod` 及依赖服务地址配置。
2. `.provider-sessions/`，使用私有加密备份或可信传输，恢复 `10001:10001` 权限。目录已被 Git 忽略，不放进源码提交。
3. 需要保留的 PostgreSQL 数据、对象存储制品及相关持久卷；迁移进行中的任务时还需按原运行手册处理 `runner_work`，不可只复制 Cookie 就宣称全部任务迁移完成。

只有未来确实发生宿主迁移且需要保留旧状态时，才先恢复必要基础设施及上述状态，再运行同一条 Compose 启动命令。部署 HMAC 密钥、出口配置变化会影响旧访问上下文；平台还可能因新 IP 或设备要求重新验证。当前项目的实现与验收不依赖这类迁移场景。

换到新宿主机后，`SITE_URL`、`MINIO_PUBLIC_ENDPOINT`、`MINIO_CORS_ALLOWED_ORIGINS` 是唯一随机器变化的公开入口，其余 `.env.prod` 配置沿用。用当前节点的 Tailscale MagicDNS 名更新这三处（取当前名：

```bash
tailscale status --json | python3 -c "import sys,json;print(json.load(sys.stdin)['Self']['DNSName'])"
```

远程客户端必须使用该稳定 HTTPS 入口，不能用各自机器的 `localhost`。自包含容器模式的「全新机器一条命令」见 [001 手册](001-root-compose运行手册.md)。

### 加密迁移文件会话

不直接复制明文 `cookies.txt`。在旧宿主上创建一次独立迁移密钥，再按平台生成认证加密包：

```bash
cd backend
uv run python -m app.workers.runner.provider_session_setup \
  create-backup-key --key-file /private/separate/framefetch-session.key
uv run python -m app.workers.runner.provider_session_setup backup \
  --provider youtube \
  --directory ../.provider-sessions/youtube \
  --bundle /private/transfer/youtube.ffsession \
  --key-file /private/separate/framefetch-session.key
```

`.ffsession` 仅包含一个 Provider 的加密数据，会话密钥不在包内。密钥与加密包必须分开保管和传输，两者都不进 Git、镜像、日志或普通附件。新宿主上执行：

```bash
cd backend
uv run python -m app.workers.runner.provider_session_setup restore \
  --provider youtube \
  --directory ../.provider-sessions/youtube \
  --bundle /private/transfer/youtube.ffsession \
  --key-file /private/separate/framefetch-session.key
uv run python -m app.workers.runner.provider_session_setup check \
  --provider youtube --directory ../.provider-sessions/youtube
```

恢复时只在内存中解密，继续校验 Provider 绑定、域名白名单、必需字段和过期时间，然后原子发布为 `0600` 文件。错误密钥、篡改、跨平台恢复或无效 Cookie 都不会覆盖现有来源。恢复成功只证明私有状态完整；如果未来发生真实宿主迁移，应在当时的真实出口上重新运行 metadata 和 media canary。这不是当前交付的设备要求。

视频号的专用元宝 Profile 及其他被平台/操作系统绑定的动态来源不使用此加密包；换后端宿主后必须通过平台允许的流程重新授权。

## 会话更新与故障定位

浏览器动态来源中，`provider_session_source_missing` 表示 Profile/Cookies 数据库不存在，`provider_session_permission_denied` 表示操作系统拒绝读取；两者都不要求用户重复登录。Cookie 行存在但缺少当前平台必需字段时才返回 `credential_required`。文件来源继续以 `credential_required` 表示文件不存在，`credential_rejected` 表示格式、域或文件权限不符合要求，`credential_expired` 表示缺少当前有效的必需会话字段；其他不可读故障返回 `provider_session_unavailable`。readiness 的无凭据 probe 只证明来源代理可响应，不证明来源可读或上游接受。

到期或平台撤销后，通过原授权方式取得新文件并替换对应平台的 `cookies.txt`。推荐在同目录写好新文件、设置权限后原子重命名；下一次操作重新读取，不必重建镜像。文件内容变化会生成新的访问上下文，旧 inspection 应重新解析，避免静默换账号。

优酷/腾讯视频来源文件保持只读；Chrome-backed 平台由本机 Agent 按需同步当前专用浏览器状态，操作中的 `Set-Cookie` 更新只发生在临时 jar，结束后丢弃。Agent 只把一次性加密租约写入对应队列，不能据此宣称永久登录或全平台自动续期。视频号和平台协议变化需分别处理，不用清空整个部署状态“重置”问题。

路径 429 冷却存于 PostgreSQL `provider_route_cooldowns`，不依赖临时目录或某个任务。重启、删任务、改 Cookie/引擎不能清除同一路径限流；`route_retry_at` 是最早重试时间，到期后须单个有限探针验证恢复。数据库和各业务进程需时钟同步。配置出口标识不能证明真实公网 IP 未变，新出口必须单独验收。

部署后先在管理员运行诊断核对配置、上下文、来源状态和媒体证据，再按[固定探针手册](007-固定Provider探针运行手册.md)运行对应 metadata/media。核心 readiness 返回 200 不代表所有可选 profile 已启动。没有文件/动态来源时先保留未配置状态；不要启动空目录、扫描全部浏览器 Cookie 或清理业务数据来伪造恢复。

视频号动态来源诊断从 `backend/` 运行 `uv run python -m app.workers.runner.provider_cookie_agent doctor --provider wechat_channels`。Chrome-backed 平台使用同一 Agent 的 `doctor --provider <key>`；优酷/腾讯视频文件来源使用 `provider_session_setup check`。运行配置在启动时拒绝“默认策略选择 operator、却没有同平台 Runner endpoint”，Canary 也拒绝没有同平台 endpoint 的 operator 目标。Compose profile 和挂载仍由部署前契约/`docker compose config` 核对，不能由 endpoint 校验代替。

设计架构见 [031 可移植个人部署与平台访问设计](../design/031-Linux无人值守运行设计.md)。

## 腾讯视频与优酷个人线路

本批接入为实验状态，真实 VIP 下载尚未完成验证。腾讯和优酷普通视频可使用匿名 Runner；VIP 需启用下述个人会话线路，仅处理账号可以访问的完整非 DRM 单视频。设计与边界见 [032 腾讯视频与优酷个人下载设计](../design/032-腾讯视频与优酷个人下载设计.md)。首次私下准备各自的 Netscape 文件，按上述 UID/GID 和权限安装到 `qqvideo/cookies.txt`、`youku/cookies.txt`。

| 平台 | 文件域范围 | 当前必需 Cookie | Compose profile |
| --- | --- | --- | --- |
| 腾讯视频 | v.qq.com 及子域 | vqq_vuserid 与 vqq_vusession | qqvideo-operator |
| 优酷 | youku.com 及子域 | P_sck | youku-operator |

腾讯可选账号字段 main_login、vqq_openid、vqq_appid、vqq_access_token 由解析器读取；不要混入其他站点会话。优酷可选 cna 会复用为 UPS utid。字段存在只证明文件格式可用，不证明平台接受登录。

在保留现有其他平台配置的基础上合并以下值；只启用已准备文件的平台：

```dotenv
COMPOSE_PROFILES=qqvideo-operator,youku-operator
RUNNER_OPERATOR_BASE_URLS={"qqvideo":"http://qqvideo-operator-runner:19100","youku":"http://youku-operator-runner:19100"}
```

继续使用本页生产 Compose 的构建与启动命令。之后普通重启无需改代码或重新安装文件。本机开发 Compose 尚未提供这两个 profile；需要调试时使用生产拓扑连接已有基础设施。

`content_preview_only`：只获得试看或时长短缺；`content_access_metadata_invalid`：原始信息不足/协议不匹配；`drm_protected`：受保护媒体，不生成制品；`media_validation_failed`：下载文件与原视频时长或音视频计划不一致。平台登录失效按原有会话错误处理。遇到这些错误不会自动更换账号或在每次启动时尝试更新依赖。

## 从已登录 Chrome 建立独立文件来源（2026-09-15）

复用部署者已登录的 Chrome，不另开平台登录窗口。从宿主部署账号运行一次按平台过滤的采集；下载与重启不执行该命令：

```bash
cd backend
uv run python -m app.workers.runner.provider_session_setup capture-chrome --provider youtube --profile Default --directory ../.provider-sessions/youtube-candidate
uv run python -m app.workers.runner.provider_session_setup check --provider youtube --directory ../.provider-sessions/youtube-candidate
```

仅采集现有 Provider allowlist，调用有界子进程，结果不写 stdout 或日志。目录 0700、文件 0600，校验后同目录锁定、fsync 并原子替换；采集失败不删除旧来源。文件校验不是平台授权有效证明；通过候选 Runner 的 metadata/media、原链接完整文件与重启复验后，按本手册 UID/GID 安装生产文件。

生产持久设置 `COMPOSE_FILE=docker-compose-prod.yml`。YouTube、抖音、Reddit 的 `RUNNER_PROVIDER_COOKIE_SYNC_ROOT` 和按 Provider 队列挂载已经在该文件中定义，不再叠加 browser/session-files 覆盖；优酷/腾讯视频继续使用 `/run/provider-source/cookies.txt`。部署前用 `docker compose --env-file .env.prod config` 验证：Chrome-backed Runner 不得出现 `RUNNER_PROVIDER_COOKIE_FILE`，文件来源 Runner 不得出现 `RUNNER_PROVIDER_COOKIE_SYNC_ROOT`；视频号则只保留专用动态代理挂载。

已有独立文件可通过同一入口验证并原子导入：

