# CI 与主分支门禁运行手册

## 1. 目标与事实来源

CI 的唯一执行定义是 `.github/workflows/ci.yml`，本地与远端质量命令统一由 `scripts/ci.py` 提供。`Required CI` 不是新的测试集合，而是仓库规则、后端、前端和运行边界四项结果的 fail-closed 聚合器。

普通 PR CI 不访问真实第三方视频站点、不加载 Provider Cookie，也不调用真实 Codex/Claude 账户。外部站点 canary、授权样本和 AI 真实调用继续使用各自的发布门禁，避免网络波动或账户状态污染确定性合并检查。

## 2. 门禁分层

| 层级 | 入口 | 阻断内容 |
| --- | --- | --- |
| 本地代码检查 | `python scripts/ci.py all` | 服务、完整环境和生产 Compose 解析，后端全门禁、前端全门禁与生产依赖审计 |
| GitHub CI | `Required CI` | 上述代码门禁，加统一镜像、完整 Compose 启动、依赖就绪、SQL 二次幂等、OpenAPI 生成无漂移 |

需要手动复现时，从仓库根目录执行：

```bash
python scripts/ci.py repository
python scripts/ci.py backend
python scripts/ci.py frontend
python scripts/ci.py all
./scripts/ci-runtime.sh
```

`ci-runtime.sh` 使用临时 env 文件和独立 Compose project label；如果执行失败，会输出容器状态与末尾日志，随后删除本轮容器和卷。由于基础 Compose 显式固定了容器名，本机已有同名项目运行时应先停止它，不能并行运行两套拓扑。

## 3. GitHub 配置

- Actions 与 `setup-uv` 必须固定到完整 40 位提交 SHA；`scripts/ci.py repository` 会拒绝 tag 或 branch 引用。
- PR 标题必须符合提交规范；CI 同时检查 PR 标题、PR 提交和直接 Push 的提交范围。
- `push`、`pull_request`、`merge_group` 和手动触发共用同一 Workflow；同一 PR 的旧运行会被取消，减少无效排队。

## 4. 失败定位与恢复

1. 先看 `Required CI` 的四个依赖结果，定位 Repository rules、Backend quality、Frontend quality 或 Runtime boundary。
2. 在本地执行对应的 `python scripts/ci.py <stage>`；运行边界失败执行 `./scripts/ci-runtime.sh`，脚本会保留失败日志到终端。
3. OpenAPI 漂移时先启动当前 API、执行 `npm run openapi` 并审查 `frontend/src/services/video/` 的真实契约差异，禁止手工修补生成目录。
4. Runtime boundary 失败时优先检查 Compose health、一次性 init 服务和二次 `database-init`；不要通过移除健康检查或跳过 schema 幂等来恢复绿色。
5. 修复后推送新提交，等待新的 `Required CI`；不得重新运行旧提交来替代代码修复。

CI 绿色证明当前提交在固定工具链、确定性测试和无真实平台凭据的完整本地拓扑中成立，不替代真实 Provider canary、生产备份恢复、授权样本或人工视觉验收。
