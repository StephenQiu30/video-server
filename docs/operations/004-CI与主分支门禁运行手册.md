# CI 与主分支门禁运行手册

## 1. 目标与事实来源

CI 的唯一执行定义是 `.github/workflows/ci.yml`，本地按本手册执行对应质量命令。`Required CI` 不是新的测试集合，而是仓库规则、后端、前端和运行边界四项结果的 fail-closed 聚合器。

普通 PR CI 不访问真实第三方视频站点、不加载 Provider Cookie，也不调用真实 Codex/Claude 账户。外部站点 canary、授权样本和 AI 真实调用继续使用各自的发布门禁，避免网络波动或账户状态污染确定性合并检查。

## 2. 门禁分层

| 层级 | 入口 | 阻断内容 |
| --- | --- | --- |
| 本地代码检查 | 按下方分模块命令执行 | 业务和生产 Compose 解析、已有服务健康检查，后端全门禁、前端全门禁与生产依赖审计 |
| GitHub CI | `Required CI` | 上述代码门禁，加统一镜像、完整 Compose 启动、依赖就绪和 SQL 二次幂等 |

需要手动复现时，从仓库根目录执行：

```bash
cd backend && uv sync --frozen --dev && uv run --frozen ruff check app tests && uv run --frozen mypy --strict app && uv run --frozen pytest -q
cd ../frontend && npm ci && npm audit --omit=dev --audit-level=high && npm run lint && npm test && npm run build
cd .. && docker compose --env-file .env -f docker-compose.yml config --quiet && docker compose --env-file .env.prod -f docker-compose-prod.yml config --quiet
```

GitHub 托管 runner 没有本机已有服务，因此 CI 使用 `docker-compose-env.yml` 作为一次性隔离夹具，并与正式业务 Compose 组合验证。CI job 显式设置四个基础服务的容器 DNS 名称；业务环境模板始终默认连接 `host.docker.internal`。失败时仅清理 CI 自己的容器和卷。

本机验证直接复用当前 `.env` / `.env.prod` 和已运行的基础服务，不运行 CI 的环境启动、初始化或 `down --volumes` 命令，不停止现有项目来腾出端口。涉及写入的测试只能使用已有服务中的隔离测试数据库；真实业务库不作为可清理测试库。

## 3. GitHub 配置

- Actions 与 `setup-uv` 必须固定到完整 40 位提交 SHA；GitHub Actions 的仓库检查会拒绝 tag 或 branch 引用。
- `push`、`pull_request`、`merge_group` 和手动触发共用同一 Workflow；同一 PR 的旧运行会被取消，减少无效排队。

## 4. 失败定位与恢复

1. 先看 `Required CI` 的四个依赖结果，定位 Repository rules、Backend quality、Frontend quality 或 Runtime boundary。
2. 在本地执行对应的后端、前端和 Compose 命令；运行边界失败时按工作流中的环境 Compose 与业务 Compose 步骤定位日志。
3. OpenAPI 变化时先启动当前 API、审查 `/openapi.json` 与 `frontend/src/services/video/` 的契约差异，禁止留下未同步的客户端。
4. Runtime boundary 失败时优先检查环境 Compose 的 health、一次性 init 服务和二次 `database-init`；不要通过移除健康检查或跳过 schema 幂等来恢复绿色。
5. 修复后推送新提交，等待新的 `Required CI`；不得重新运行旧提交来替代代码修复。

CI 绿色证明当前提交在固定工具链、确定性测试和无真实平台凭据的完整本地拓扑中成立，不替代真实 Provider canary、生产备份恢复、授权样本或人工视觉验收。
