# PRD02 平台识别与平台画像

## 1. 背景

“万能视频下载器”容易被误解为对所有网站都做出成功承诺。首版必须清楚区分“正式支持的平台”和“理论上可能被 yt-dlp best-effort 处理的平台”，避免产品边界失控。

## 2. 目标

1. 系统在接收合法 URL 后，能识别其来源平台。
2. 首版明确 5 个正式支持平台：YouTube、Bilibili、TikTok、X、Instagram。
3. 每个平台都有可展示的平台名称、平台分类和合规提示。

```gherkin
Given 用户提交一个合法的公开视频 URL
When 系统完成平台识别
Then 系统返回统一的 platform_id 和平台展示信息
And 正式支持平台有明确合规提示
```

## 3. 非目标

- 不承诺 yt-dlp 支持的所有网站都进入正式支持清单。
- 不在本 PRD 中定义任务执行或对象存储。
- 不做私密内容、会员内容或 DRM 内容的支持声明。

## 4. 核心内容

### 4.1 正式支持平台

| platform_id | display_name | category | compliance_note |
| --- | --- | --- | --- |
| `youtube` | YouTube | overseas-video | 仅支持公开可访问内容，不承诺绕过登录、年龄验证或会员限制 |
| `bilibili` | Bilibili | cn-video | 仅支持公开可访问内容，不承诺绕过登录、大会员或区域限制 |
| `tiktok` | TikTok | overseas-short-video | 仅支持公开可访问内容，不承诺绕过登录或私密账号限制 |
| `x` | X | social-platform | 仅支持公开可访问内容，不承诺绕过登录或私密账号限制 |
| `instagram` | Instagram | social-platform | 仅支持公开可访问内容，不承诺绕过登录、私密账号或限时动态限制 |

### 4.2 平台画像要求

1. 每个平台至少定义 `platform_id`、`display_name`、`category`、`compliance_note`。
2. 每个平台都必须提供 `compliance_note`，且不得承诺绕过登录、验证码、会员或私密访问限制。
3. 平台画像既用于 API 返回，也用于 UI 和验收样例。

### 4.3 API 平台字段

API 在任务创建和任务详情接口中返回统一的平台字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `platform_id` | string | 平台唯一标识，如 `youtube`、`bilibili` |
| `platform_display_name` | string | 平台展示名称，如 `YouTube`、`Bilibili` |
| `platform_category` | string | 平台分类，如 `overseas-video`、`cn-video` |
| `platform_compliance_note` | string | 平台合规提示 |

任务详情接口返回示例：

```json
{
  "task_id": "uuid",
  "url": "https://www.youtube.com/watch?v=...",
  "platform_id": "youtube",
  "platform_display_name": "YouTube",
  "platform_category": "overseas-video",
  "platform_compliance_note": "仅支持公开可访问内容，不承诺绕过登录、年龄验证或会员限制"
}
```

### 4.4 产品边界

1. 平台识别成功不等于下载一定成功。
2. 对未列入首版清单的平台，只允许 best-effort 提示，不做正式承诺。
3. 产品文案不得表达规避平台限制或主动去水印能力。

## 6. 验收门禁

- 5 个正式支持平台均有稳定平台画像。
- API 对外返回统一的平台字段。
- 合规提示不承诺绕过登录、验证码、会员或私密访问限制。

## 7. 风险与边界

平台页面结构和策略会变动，平台画像要绑定首版声明，不要把产品支持范围和第三方工具能力混为一谈。

## 8. 待确认问题

- 是否在首版中额外输出 `platform_category`。
- 是否将非正式支持平台也暴露为 `recognized_but_unsupported`。
