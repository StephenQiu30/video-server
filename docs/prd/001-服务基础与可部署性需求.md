# PRD 001 服务基础与可部署性需求

## 文档状态

- 状态：Accepted for Planning（2026-07-19）。
- 上游：[Design 001](../design/001-服务边界与总体架构设计.md)。
- 输入：正式上线、前后端分离、独立长任务和最小基础设施要求。
- 输出：服务基础、组件边界和可部署性验收需求。
- 下游：[Plan 001](../plans/001-服务基础与可部署性计划.md)。

## 1. 背景与价值

视频解析、下载、媒体合并和 AI 都可能持续较长时间。服务必须在业务功能开发前建立清晰的 API、Worker、数据库、消息队列和对象存储边界，避免把上线项目退化为单机脚本。

## 2. 产品目标

1. API、下载 Worker、AI Worker 和 Scheduler 能独立启动与停止。
2. PostgreSQL、RabbitMQ、MinIO 是首版唯一基础设施。
3. API 不执行下载、FFmpeg 或 AI 长任务。
4. 所有组件通过环境配置连接，不把密钥写入仓库。
5. 服务提供可用于部署探针的存活与就绪状态。

## 3. 非目标

- 不建设 Kubernetes、微服务注册发现、Redis、Kafka 或独立监控平台。
- 不在本需求实现具体下载、AI 或 Web 页面。
- 不提供账号、权限、计费或运营后台。

## 4. 用户故事

- 作为部署人员，我希望通过一套明确的容器配置启动全部依赖，以便重复部署环境。
- 作为 API 调用方，我希望服务未就绪时返回明确状态，而不是接受必然失败的请求。
- 作为维护人员，我希望下载与 AI Worker 可独立扩容，以免不同资源任务互相阻塞。

## 5. 业务规则

- API、Worker、Scheduler 使用同一服务端代码与镜像，但运行不同入口。
- Liveness 只判断进程；Readiness 必须检查 PostgreSQL、RabbitMQ 和 MinIO。
- 配置缺失时服务必须启动失败并给出安全、明确的配置错误。
- RabbitMQ 和 MinIO 必须使用持久化存储；PostgreSQL 必须支持迁移和备份。
- API 仅通过受控 CORS Origin 对 Web 开放。

## 6. 首版验收门禁

- `S001-AC-01`：在完整依赖可用时，API、两个 Worker 和 Scheduler 均可独立启动。
- `S001-AC-02`：任一必要依赖不可用时 Readiness 返回 503，Liveness 仍准确反映进程。
- `S001-AC-03`：配置和 Secret 不出现在源码、日志、镜像默认值或 API 响应中。
- `S001-AC-04`：下载 Worker 只消费 `download`，AI Worker 只消费 `ai`。
- `S001-AC-05`：Docker Compose 配置可验证且持久卷边界明确。
- `S001-AC-06`：不存在 Redis、Kafka、Kubernetes 或第三条业务队列依赖。

## 7. 风险与约束

- 单节点 PostgreSQL、RabbitMQ 和 MinIO 不提供基础设施高可用；首版接受该限制，但必须可备份和恢复。
- FFmpeg 与模型运行资源差异大，Worker 并发必须由部署配置控制。

## 8. 待确认问题

无。新增基础设施或高可用要求必须先更新 Design 001。
