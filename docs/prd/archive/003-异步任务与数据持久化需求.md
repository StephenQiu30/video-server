## 1. 用户价值

下载是长任务。用户需要在刷新页面、Worker 重启或依赖短暂故障后仍看到真实任务状态，不能因为重复点击或 RabbitMQ 重投递生成多个任务和多个文件。

## 2. 必须能力

1. PostgreSQL 是 source、format、job、artifact 和状态的唯一事实来源。
2. 空数据库经 Alembic 创建 `media_sources`、`media_formats`、`download_jobs`、`artifacts` 四张业务表及约束/索引。
3. 状态只允许 `queued → running → succeeded|failed` 与 `succeeded → expired`。
4. RabbitMQ 只承载持久 `job_id` 消息，API 使用 publisher confirm，Worker manual ack。
5. `client_request_id`、状态条件更新和唯一 artifact 共同保证并发与重投递幂等。
6. 发布前崩溃、重复消息、Worker 崩溃和失联 running 由补发、heartbeat 与 housekeeping 收敛。
7. source URL、对象和元数据按冻结期限擦除或删除，不形成用户历史。

## 3. 状态与可见性规则

- queued 不伪造进度；running 只报告真实 stage、字节和可得百分比。
- failed、expired 为终态；MVP 不暂停、取消、恢复原任务或自动业务重试。
- RabbitMQ 与 MinIO 不保存第二套业务状态；重启后从数据库恢复判断。
- 终态立即擦除原始 URL；文件过期后立即禁止签发新地址。

## 4. Product Acceptance Criteria

| 编号 | 验收行为 |
| --- | --- |
| `S003-AC-01` | 空 PostgreSQL 可经 Alembic 重复升级到仅含四张业务表的目标 schema |
| `S003-AC-02` | 合法状态转换、会话归属、幂等键和一任务一产物在并发下仍成立 |
| `S003-AC-03` | RabbitMQ 只有一个 direct exchange/queue/routing key，持久消息仅含 job_id |
| `S003-AC-04` | 发布失败、发布前崩溃、重复消息和 Worker 崩溃不会造成永久卡住或重复产物 |
| `S003-AC-05` | queued/running/终态及 stage/progress 始终来自数据库真实值，不存在第二套队列状态 |
| `S003-AC-06` | source URL、24 小时产物和 7 天元数据在边界时刻准确擦除、过期与清理 |
| `S003-AC-07` | PostgreSQL、RabbitMQ、MinIO 或 Worker 重启后，已接收任务和对象可恢复且不重复 |

## 5. 冻结决策

1. 直接使用 RabbitMQ 与 aio-pika，不使用 Celery、Result Backend、DLQ 业务框架或 Redis。
2. 数据库固定 PostgreSQL；schema 只经 Alembic 前向迁移。
3. housekeeping 位于 `worker.py`，不增加 scheduler 服务。
