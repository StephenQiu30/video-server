# PRD10 中心化单服务运行时

## 1. 背景

当前项目把 API 与 Worker 表达为两个代码入口、两个 Docker target 和两个 Compose 业务服务：

1. `apps/api/app/main.py` 是 API 入口，Docker target `api`，Compose 服务 `api`。
2. `apps/worker/worker/main.py` 是 Worker 入口，Docker target `worker`，Compose 服务 `worker`。
3. 两个服务共享 `python-base` 镜像层，但各自安装依赖、各自启动。

对个人自部署用户来说，两个业务服务意味着：
- 需要同时管理两个容器的生命周期。
- 排障时需要分别查看两个容器的日志。
- 扩容或调整资源时需要分别配置。
- 健康检查只能覆盖 API，Worker 没有内置端点。

## 2. 目标

1. Docker Compose 中只有一个业务服务 `app`，一键启动即可运行完整系统。
2. 代码层只有一个部署入口（中心化 runtime），内部同时启动 API server、队列消费者和下载执行器。
3. 消息队列（Redis/RQ）保留为同一项目内部机制，不作为独立业务服务暴露。
4. MinIO/S3 是唯一最终产物存储和读取入口，本地路径禁止泄漏。
5. 分享视频链接必须能完成解析、任务创建、队列消费、下载、上传、读取链接的完整链路。

```gherkin
Given 部署者使用 Docker Compose 启动系统
When 执行一键启动命令
Then 系统拉起一个 `app` 业务容器和基础设施容器
And `app` 容器内部同时运行 API、队列消费和下载执行
And 健康检查覆盖所有组件
```

```gherkin
Given 用户分享一个视频链接
When 系统处理该链接
Then 系统完成解析、创建任务、队列消费、下载、上传到 MinIO/S3
And 返回预签名下载链接
And 不泄漏任何本地临时路径
```

## 3. 非目标

1. 不移除 Redis/RQ。
2. 不让 API 同步执行长耗时下载。
3. 不把本地目录作为最终交付方式。
4. 不绕过平台限制。
5. 不引入 Kubernetes 或多服务编排。

## 4. 核心需求

### 4.1 单业务服务

1. Compose 中 SHALL 只有一个业务服务 `app`。
2. `app` 服务 MUST 使用单个 Docker target 构建。
3. MUST NOT 保留 `api` 和 `worker` 两个独立 Compose 业务服务。
4. 基础设施服务（PostgreSQL、Redis、MinIO）保持独立。

### 4.2 中心化 runtime

1. 代码层 SHALL 只有一个部署入口。
2. 中心化 runtime MUST 在同一个进程内同时启动 API server、队列消费者和下载执行器。
3. MUST NOT 保留两个独立部署入口。

### 4.3 队列内部化

1. Redis/RQ MUST 保留为同一项目内部的消息队列机制。
2. 队列消费 MUST 在 `app` 服务内部运行。
3. MUST NOT 因为单服务化而移除 Redis/RQ。
4. MUST NOT 因为单服务化而改为 API 同步执行长耗时下载。

### 4.4 MinIO/S3 唯一交付

1. MinIO/S3 SHALL 是唯一最终产物存储和读取入口。
2. 所有用户可访问的视频下载链接 MUST 通过预签名 URL 从 MinIO/S3 获取。
3. MUST NOT 把本地临时目录路径暴露到 API 响应、数据库记录或分享链接中。

### 4.5 Readiness 规则

1. `GET /ready` MUST 检查全部组件：数据库、Redis、队列、对象存储、媒体工具、下载工作目录。
2. 任一组件不可用时 MUST 返回 HTTP 503。
3. 响应 MUST 逐项报告每个组件状态。

### 4.6 端到端链路

分享视频链接 MUST 能完成：

1. URL 解析（`/api/parse`）。
2. 任务创建（`/api/tasks`）。
3. 队列消费（RQ Worker 在 app 内部）。
4. 下载执行（yt-dlp + FFmpeg）。
5. 产物上传到 MinIO/S3。
6. 预签名链接生成和读取。

## 5. 产品边界

1. 部署者只需执行一个命令即可启动完整系统。
2. 部署者只需管理一个业务容器的生命周期。
3. 排障时只需查看一个容器的日志。
4. 健康检查覆盖所有组件，启动失败可通过 `/ready` 定位。

## 6. 验收门禁

1. Compose 中只有一个业务服务 `app`。
2. 代码层只有一个部署入口。
3. 消息队列保留为内部机制。
4. MinIO/S3 是唯一最终交付入口。
5. 端到端链路可完成。
6. 本地路径不泄漏。

## 7. 风险与边界

1. 单容器运行 API 和 Worker 意味着资源隔离减少，一个组件的异常可能影响另一个。
2. Dockerfile 和 Compose 的收敛是破坏性变更，需要一次性切换。
3. 中心化 runtime 的进程管理需要确保 Worker 异常不影响 API。

## 8. 待确认问题

1. 中心化 runtime 使用什么进程管理方式（线程、子进程、asyncio task）。
2. Worker 异常时是否需要自动重启。
3. 是否需要支持只启动 API 或只启动 Worker 的调试模式。
