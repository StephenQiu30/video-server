# PRD08 后端工程规范与架构治理

## 1. 背景

video-server 当前代码结构基本遵循 `routers → services → models` 的三层模式，但缺少正式的架构治理规范。随着功能增长，以下风险逐渐暴露：

1. `services/` 层同时承担业务编排和数据库读写，职责边界模糊。
2. 错误码、状态枚举和常量分散在各模块，缺少 shared 真相源约束。
3. 新增模块缺乏明确的层级归属和依赖方向约束，容易出现跨层依赖。
4. 重构和扩展缺少测试门禁保护，容易引入回归。

PRD08 为后续改造建立治理边界，使每次变更都可追溯到层级、依赖方向和测试门禁。

## 2. 目标

1. 定义 router、schema、service、domain、repository、infrastructure、worker job 的职责和禁止事项。
2. 确立 shared 包（`packages/shared/`）作为状态枚举、错误码和跨模块常量的唯一真相源。
3. 要求新增或重构模块必须说明所属层级、依赖方向和测试门禁。
4. 以渐进治理为原则：只约束真实变更和扩展点，不要求一次性重排全部代码。

```gherkin
Given 开发者需要新增或重构一个后端模块
When 查阅 PRD08
Then 能明确该模块所属层级、允许依赖方向、必须遵循的契约和测试要求
```

## 3. 非目标

- 不要求一次性重写全部目录结构。
- 不引入大型治理平台或自动化扫描工具链。
- 不覆盖前端工程规范。
- 不为了形式抽象而引入无真实调用者的接口层。

## 4. 核心内容

### 4.1 分层架构定义

| 层级 | 路径 | 职责 | 禁止事项 |
| --- | --- | --- | --- |
| Router | `apps/api/app/routers/` | 协议层：接收请求、调用 service、返回响应 | 不含业务逻辑、不含数据库操作 |
| Schema | `apps/api/app/schemas.py` | Pydantic 契约：请求/响应模型定义 | 不含业务逻辑、不直接引用 ORM 模型 |
| Service | `apps/api/app/services/` | 业务编排：协调 domain、repository 和 infrastructure | 不直接写 SQL、不直接调用外部 API |
| Domain | `apps/api/app/domain/` | 纯业务规则：状态机、校验、计算 | 不引用数据库、不引用外部服务 |
| Repository | `apps/api/app/repositories/` | 数据库读写：封装 SQLAlchemy 操作 | 不含业务逻辑、只做 CRUD 和查询 |
| Infrastructure | `apps/api/app/infrastructure/` | 外部服务封装：Redis、MinIO、队列 | 不含业务逻辑、只做适配 |
| Worker Job | `apps/worker/worker/jobs/` | 异步任务入口：从队列拾取任务并编排执行 | 不直接操作数据库、通过 repository 更新状态 |

### 4.2 依赖方向约束

```text
Router → Service → Domain
                  → Repository → ORM/DB
                  → Infrastructure → 外部服务
Worker Job → Service → Domain
                      → Repository → ORM/DB
                      → Infrastructure → 外部服务
```

**规则**：

1. 上层可以依赖下层，下层不得依赖上层。
2. 同层之间避免循环依赖。
3. Domain 层是纯函数，不引用任何基础设施。
4. Repository 和 Infrastructure 不互相依赖。

### 4.3 Shared 真相源

`packages/shared/video_downloader_shared/` 是跨模块常量和枚举的唯一来源：

| 内容 | 当前位置 | 目标位置 |
| --- | --- | --- |
| `TaskState` 枚举 | `packages/shared/video_downloader_shared/states.py` | 保持不变 |
| `failure_code` 常量 | 分散在 services 和 worker | 迁移到 `shared/codes.py` |
| 平台 ID 常量 | 分散在 services 和 worker | 迁移到 `shared/platforms.py` |
| 跨模块 DTO | 各模块自定义 | 迁移到 `shared/dto.py` |

**规则**：

1. 新增错误码必须先在 `shared/codes.py` 定义，再在业务代码中引用。
2. 新增状态枚举必须先在 `shared/states.py` 定义。
3. 禁止在业务模块中硬编码错误码字符串或状态值。

### 4.4 契约优先

1. API 请求/响应模型通过 Pydantic schema 定义，schema 变更先于实现。
2. OpenAPI spec 通过 `scripts/export_openapi.py` 导出，作为前端集成的契约。
3. 新增或修改 API 端点时，必须同步更新 schema 和 OpenAPI 导出。

### 4.5 测试优先治理

1. 新增模块必须有对应测试，测试覆盖核心业务规则和边界条件。
2. 重构已有模块时，必须先有保护测试，再做结构变更。
3. 测试不得为兼容旧行为、灰度双轨或临时兜底补写兼容性测试。
4. 架构边界测试：验证依赖方向约束，防止跨层引用。

### 4.6 复杂度控制

1. 单文件长期目标不超过 200 行；超过时按职责拆分。
2. 单函数不超过 50 行；超过时提取子函数。
3. 圈复杂度不超过 10；超过时重构条件分支。
4. 新增模块必须在 PR 中说明所属层级和依赖方向。

## 6. 验收门禁

- PRD08 路径存在并能独立说明后端工程治理边界。
- 分层架构表格完整，每层有职责和禁止事项。
- 依赖方向约束清晰，无歧义。
- Shared 真相源规则明确。
- 治理要求不要求一次性大规模重排所有代码。

## 7. 风险与边界

过度治理会拖慢迭代速度。PRD08 的原则是"治理只服务真实变更和扩展点"——如果一个模块没有被改动，不要求为它补充治理。渐进治理意味着短期内会存在新旧代码风格并存的情况，但每次变更都向治理目标收敛。
