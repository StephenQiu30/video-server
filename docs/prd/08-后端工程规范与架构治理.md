# PRD08 后端工程规范与架构治理

## 1. 背景

视频下载后端已积累 router、service、core、schemas、models、worker 等多层职责。随着下载能力扩展（更多平台、更多处理流程），职责可能继续堆积到 router 或任务脚本中，导致耦合加深、测试困难、新贡献者无法快速定位职责归属。

当前后端目录结构：

```
apps/api/app/
├── core/          # 配置、错误码、日志、安全、响应封装
├── db/            # 数据库会话
├── middleware/    # 请求上下文中间件
├── models.py      # SQLAlchemy 模型
├── routers/       # API 路由层
├── schemas.py     # Pydantic 响应/请求模型
├── services/      # 业务逻辑层
├── utils/         # 工具函数
└── main.py        # FastAPI 应用入口
```

## 2. 目标

1. 明确 FastAPI 后端目录职责与模块边界。
2. 约束 router/service/repository/adapter/task 的依赖方向。
3. 确保共享状态、错误码、平台选择器、响应模型拥有单一事实来源。
4. 建立架构边界测试防止跨层依赖回归。
5. 将治理规则纳入 OpenSpec、PRD、Plan、Agent Review 归档闭环。

```gherkin
Given 后端代码库已存在 router、service、core 等分层
When 开发者新增功能或修改现有模块
Then 代码必须遵循分层依赖方向约束
And 架构边界测试必须通过
And 文档和规范必须同步更新
```

## 3. 非目标

- 不做大规模代码重构或目录迁移。
- 不引入新的 `repositories/`、`sources/`、`tasks/` 目录（当前代码规模不需要）。
- 不改动前端工程规范。
- 不改动 Worker 内部实现。
- 不改动与当前下载链路无关的基础设施。

## 4. 核心内容

### 4.1 分层职责定义

| 层 | 目录 | 职责 | 允许依赖 |
| --- | --- | --- | --- |
| Router | `routers/` | 请求路由、参数校验、依赖注入、响应封装 | service、core、schemas、utils、adapter |
| Service | `services/` | 业务逻辑、并发检查、配额校验、状态流转 | models、core、utils、shared |
| Adapter | `services/download_adapter.py` | 外部 SDK 封装（yt-dlp、平台解析） | core、schemas、utils |
| Core | `core/` | 配置、错误码、日志、安全、响应封装 | 无业务层依赖 |
| Schema | `schemas.py` | Pydantic 请求/响应模型 | 无 |
| Model | `models.py` | SQLAlchemy 数据库模型 | 无 |
| Shared | `packages/shared/` | 跨项目共享状态枚举 | 无 |

### 4.2 依赖方向约束

```
Router → Service → Model/Core/Shared
Router → Adapter → Core
Router → Core
Service → Model/Core/Shared
Adapter → Core
Core → (无业务层依赖)
```

**禁止的依赖方向**：
- Service → Router（反向依赖）
- Core → Service/Router（反向依赖）
- Router → 外部 SDK 直接导入（yt_dlp、minio、redis）

### 4.3 单一事实来源

| 事实 | 定义位置 | 引用方式 |
| --- | --- | --- |
| TaskState | `packages/shared/video_downloader_shared/states.py` | `from video_downloader_shared.states import TaskState` |
| ErrorCode | `app/core/errors.py` | `from app.core.errors import ErrorCode` |
| 响应模型 | `app/schemas.py` | `from app.schemas import TaskRead, ...` |
| 配置 | `app/core/config.py` | `from app.core.config import get_settings` |

### 4.4 架构边界测试

维护 `apps/api/tests/test_architecture_boundaries.py`，使用 AST 分析验证：

1. router 层不直接导入 `yt_dlp`、`minio`、`redis` 等外部 SDK。
2. router 层不直接导入 `SessionLocal`（应通过 `Depends(get_db)`）。
3. service 层不从 router 导入。
4. core 层不从 service/router 导入。

### 4.5 大文件治理

超过 200 行的 Python 文件 SHALL 按职责拆分，或在 PR 中给出保留理由。

## 6. 验收门禁

- router 层不直接依赖外部下载 SDK、数据库细节或平台解析实现。
- service/repository/adapter/task 职责边界清晰，并符合设计文档约束。
- 共享状态、错误码、selector、响应模型拥有单一事实来源。
- 架构边界测试通过。
- `scripts/validate-repository.sh` 能覆盖 PRD08/PLAN13 存在性检查。

## 7. 风险与边界

- **风险**：AST 分析可能误报注释中的 import 语句 → **缓解**：只检查实际的 import 节点。
- **风险**：未来引入新目录时需要更新规范 → **缓解**：在 PRD08 中明确目录扩展流程。
