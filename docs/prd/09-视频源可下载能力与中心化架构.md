# 视频源可下载能力与中心化架构

## 1. 背景

项目已经引入 `app.sources`、`VideoSourceAdapter`、`SourceAdapterRegistry` 和 `ParseService`，用于把 URL 解析能力集中到视频源适配器链路中。当前代码事实是：

1. `ParseService` 通过 `SourceAdapterRegistry` 选择适配器，并将结果转换为 `ParseResponse`。
2. B 站、国内短视频等具体适配器底层仍复用 `yt-dlp`，主要承担平台识别和错误语义包装。
3. Worker 下载链路直接调用 `yt-dlp`，使用任务中的 `format_id` 下载并合并媒体文件。
4. 旧的 `app.services.download_adapter` 仍保留另一套 `PlatformAdapter`、`AdapterRegistry` 和 `DownloadEngineAdapter`，且测试仍覆盖旧中心。

因此，项目目前不能只用“可解析”来宣称支持视频源。支持必须以“能下载下来并交付产物”为准，否则会造成产品口径、测试口径和代码架构三者漂移。

## 2. 支持定义

一个视频源只有同时满足以下条件，才算当前项目支持：

1. URL 能通过安全校验和平台画像识别，或被明确允许进入通用公开视频 fallback。
2. `/api/parse` 能返回至少一个可下载 format，且 format 与 Worker 的 `yt-dlp` format selector 兼容。
3. `/api/tasks` 能创建任务并保存用户选择的 `format_id`。
4. Worker 能完成 `yt-dlp.extract_info(..., download=True)` 下载。
5. 下载产物能通过 FFmpeg/FFprobe 校验。
6. 产物能上传到对象存储，并通过预签名链接交付。
7. 对登录、会员、付费、版权、DRM、地区限制、风控和私密内容，不绕过限制，只返回明确失败语义。

## 3. 当前视频源支持口径

### 3.1 明确平台画像

当前平台画像包含以下来源：

| 平台 | 平台 ID | 当前适配器路径 | 支持口径 |
| --- | --- | --- | --- |
| B 站 | `bilibili` | `BilibiliAdapter` -> `YtDlpAdapter` | 仅公开视频；不支持番剧、会员、付费、版权受限、需登录内容 |
| 抖音 | `douyin` | `DomesticShortVideoAdapter` -> `YtDlpAdapter` | 仅公开视频；不绕过风控、私密、登录态和付费限制 |
| 快手 | `kuaishou` | `DomesticShortVideoAdapter` -> `YtDlpAdapter` | 同国内短视频口径 |
| 小红书 | `xiaohongshu` | `DomesticShortVideoAdapter` -> `YtDlpAdapter` | 同国内短视频口径 |
| 西瓜视频 | `ixigua` | `DomesticShortVideoAdapter` -> `YtDlpAdapter` | 同国内短视频口径 |
| 微博 | `weibo` | `DomesticShortVideoAdapter` -> `YtDlpAdapter` | 同国内短视频口径 |
| TikTok | `tiktok` | `YtDlpAdapter` fallback | 仅 `yt-dlp` 可公开访问内容 |
| X / Twitter | `x` | `YtDlpAdapter` fallback | 仅 `yt-dlp` 可公开访问内容 |
| Instagram | `instagram` | `YtDlpAdapter` fallback | 仅 `yt-dlp` 可公开访问内容 |
| YouTube | `youtube` | `YtDlpAdapter` fallback | 仅公开且 `yt-dlp` 可下载内容 |
| Vimeo | `vimeo` | `YtDlpAdapter` fallback | 仅公开且 `yt-dlp` 可下载内容 |
| Dailymotion | `dailymotion` | `YtDlpAdapter` fallback | 仅公开且 `yt-dlp` 可下载内容 |

### 3.2 通用 fallback

未知但安全的公网 host 可以进入 `YtDlpAdapter` fallback。该能力不等同于“平台已正式支持”，只能表述为“通用公开视频尝试下载”。如果 fallback 成功，任务可完成；如果 `yt-dlp` 无 extractor、平台限制访问或下载失败，必须返回统一失败语义。

## 4. 产品目标

```gherkin
Given 用户输入一个公开视频 URL
When 系统宣称该视频源被支持
Then 系统必须能完成解析、创建任务、下载、校验、上传和下载链接交付
And 如果平台限制导致不能下载，系统必须返回可理解的失败原因
```

```gherkin
Given 开发者新增一个视频源
When 该视频源进入支持矩阵
Then 开发者必须通过中心化 adapter/registry 接入
And 不得在 router、worker 或旧 adapter 中新增分散平台分支
```

## 5. 非目标

1. 不绕过 DRM、付费墙、会员、登录态、版权或地区限制。
2. 不承诺 `yt-dlp` 所有 extractor 都是项目正式支持平台。
3. 不在本 PRD 中实现远程动态插件加载。
4. 不把“平台可识别”误写为“平台可下载”。

## 6. 核心需求

### 6.1 支持矩阵必须区分三种状态

1. `supported_download`：已有平台画像、可解析、可创建任务、可由 Worker 下载并交付产物。
2. `parse_only_or_unverified`：能解析或能识别，但缺少真实下载验收证据。
3. `fallback_attempt`：未知公网 host，仅通过 `yt-dlp` fallback 尝试，不列为正式支持平台。

### 6.2 架构必须中心化

1. 视频源接入的唯一中心应是 `app.sources` 下的 adapter、model、registry 与 parse service。
2. `app.services.download_adapter` 中的旧 adapter/registry/response conversion 不应继续作为并行中心存在。
3. Worker 下载可以继续使用 `yt-dlp`，但下载能力、错误语义和支持矩阵必须与 `app.sources` 的中心化模型对齐。
4. 新增视频源不得通过 router 或 worker 中的 host 分支实现。

### 6.3 支持声明必须有证据

每个正式支持平台必须至少有：

1. 解析 contract 测试。
2. format selector 到 Worker 下载选项的契约测试。
3. 下载执行 smoke 或可替代的 `yt-dlp` fake integration 测试。
4. 成功产物进入对象存储并生成下载链接的链路验证。
5. 失败语义覆盖：受限内容、风控/429、unsupported、网络异常。

## 7. 验收门禁

1. 文档中不得再把“平台画像列表”直接等同为“已支持下载平台列表”。
2. 代码中只能保留一个视频源 adapter/registry 中心。
3. `DownloadEngineAdapter` 旧中心被删除或降级为兼容 shim，并且生产代码不依赖它。
4. 支持矩阵必须列出每个平台的支持状态、依赖、限制和验收证据。
5. Agent Review 必须核对真实下载链路，而不是只看 parse 单元测试。

## 8. 风险与边界

1. `yt-dlp` 平台能力会随上游变化，支持矩阵需要周期性复核。
2. 国内平台风控和分享短链可能导致同一平台不同 URL 表现不同。
3. 需要登录或 cookie 的内容只能作为用户授权配置能力，不能作为默认绕过能力。
4. 如果下载环境缺少 FFmpeg，则解析成功也不代表任务可下载完成。

## 9. 待确认问题

1. 是否需要把支持矩阵以 API 暴露给前端展示。
2. 是否允许在自部署场景配置 cookie 文件，并如何在文档中说明合规边界。
3. 每个平台的 smoke 测试样例 URL 是否由维护者定期更新。
