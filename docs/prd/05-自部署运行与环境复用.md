# PRD05 自部署运行与环境复用

## 1. 背景

这个项目的目标用户是个人自部署用户。相比 SaaS，首版更重要的是”容易启动、容易调试、容易复用已有 Redis/Postgres/MinIO 环境”，而不是多租户或团队协作。

系统依赖 5 个运行组件：FastAPI API、RQ Worker、PostgreSQL、Redis 和 MinIO。部署者可能已有其中部分服务，也可能从零开始。PRD 必须覆盖这两种路径。

## 2. 目标

1. 支持本机开发模式。
2. 支持以 Docker Compose 为主的一键部署模式。
3. 优先复用部署者已有的 Redis、Postgres、MinIO 环境。

```gherkin
Given 部署者已有或没有基础依赖服务
When 选择本机开发或 Docker Compose 方式启动
Then 系统都能给出稳定的运行路径和健康检查方式
```

## 3. 非目标

- 不做 Kubernetes、云原生多集群或 SaaS 运维设计。
- 不做浏览器端 Cookie 上传、托管或共享。
- 不在本 PRD 中定义业务接口细节。

## 4. 核心内容

### 4.1 用户故事

| 用户 | 场景 | 验收标准 |
| --- | --- | --- |
| 部署者 | 使用本机已有 Redis/Postgres/MinIO 启动开发 | `npm run dev` 或 `./scripts/start.sh local` 成功启动 API |
| 部署者 | 使用 Docker Compose 一键启动完整系统 | `npm run docker:up` 拉起所有 5 个组件并健康 |
| 部署者 | 确认系统各组件是否就绪 | `GET /health` 返回存活，`GET /ready` 返回各组件状态 |
| 部署者 | 启动失败时定位问题 | `GET /ready` 返回 503 并逐项报告哪个组件异常 |

### 4.2 运行方式

1. 本机开发：复用已有 Redis、Postgres、MinIO，通过 `scripts/start.sh local` 启动 API，通过 `scripts/start.sh local:worker` 同时启动 Worker。
2. Docker Compose：通过 `scripts/start.sh docker:up` 拉起 API、Worker、Postgres、Redis、MinIO 全部服务。
3. 依赖探测：`scripts/check_local_services.sh` 读取 `.env` 并打印各依赖连接信息，供部署者确认。
4. `scripts/start.sh` 还支持 `worker`（仅启动 Worker）、`docker:down`（停止 Compose）等子命令，详见 `scripts/start.sh help`。

### 4.3 产品边界

1. 本机开发路径优先考虑研发调试体验，支持热重载。
2. Docker Compose 是推荐的个人自部署交付路径。
3. 所有环境变量必须有明确来源：本机开发从 `.env`（首次自动从 `.env.example` 创建）读取，Docker Compose 从 `.env.production` 读取。
4. `.env.production` 必须替换所有 `CHANGE_ME` 占位符，由 `scripts/validate_prod_env.py` 强制校验。

### 4.4 可观测性要求

1. 存活检查：`GET /health` 返回 `{"status":"ok","app":"<app_name>"}` 表示 API 进程存活。
2. 就绪检查：`GET /ready` 逐项检查 database、redis、queue、storage、media_tools、download_work_dir，任一失败返回 503。
3. 启动失败时通过 `/ready` 响应定位是哪个组件异常。
4. 对缺失依赖（如 ffmpeg）给出可操作提示。
5. **已知限制**：Worker 服务没有内置健康检查端点，Docker Compose 中无法直接探测 Worker 存活状态。

## 6. 验收门禁

- 本机开发路径能复用已有依赖启动。
- Docker Compose 路径能一键启动完整系统。
- 健康检查和启动说明完整可验证。

## 7. 风险与边界

运行文档不清晰会导致”功能其实存在，但用户跑不起来”。本 PRD 的验收必须包含真实启动路径。本机开发路径和 Docker Compose 路径的配置来源不同（`.env` vs `.env.production`），如果两者行为分叉，排障成本会显著上升。

`docker-compose.prod.yml` 中 MinIO 默认凭据使用了占位值，部署者必须在 `.env.production` 中覆盖 `S3_ACCESS_KEY_ID` 和 `S3_SECRET_ACCESS_KEY`，否则存在安全风险。

## 8. 待确认问题

- 是否为 Docker Compose 提供最小 profile（不含 MinIO）和完整 profile 两套方案。
- 是否为 Worker 服务添加健康检查端点以支持 Docker Compose 健康探测。
