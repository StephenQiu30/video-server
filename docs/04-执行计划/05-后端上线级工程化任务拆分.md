## 推荐执行顺序

1. E1 + E2：先补生产安全基线。
2. E3：把门禁放进 CI，避免后续回退。
3. E4：保护解析接口资源。
4. E5 + E6：提升任务可靠性和排障能力。
5. E7 + E8：沉淀长期运营能力。

## 本轮执行范围

本轮只执行 P0：

- E1 生产启动门禁。
- E2 请求安全基线。
- E3 CI 与部署门禁。
- E4 解析接口限流。

P1/P2 保留为后续 issue，不混入本轮 PR，避免一个 PR 同时承担架构重构、监控平台化和任务系统重构。

## 审核确认

- P0 任务之间没有循环依赖：E1/E2/E4 都可独立测试，E3 只把验证命令纳入 CI。
- P0 不引入新基础设施：不需要 Redis 限流、Prometheus、OpenTelemetry 或迁移框架即可上线。
- P0 保持 API 兼容：`/api/parse` 只新增可能的 429 错误，不改变成功响应结构。
- P0 遵循 TDD：每个行为先写失败测试，再实现，再跑局部和全量测试。
- P0 PR 可以一次性关闭 4 个 issue，因为它们共同组成“上线级工程化基线”这一完整 feature。
